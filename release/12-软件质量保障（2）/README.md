今天我们继续讲软件的质量保障。上一次课，我们讲了一个我以前上课也会说的调试理论：要心疼一下程序员。以前上计算机系统基础，给大家讲怎么调 NEMU 的时候，都会说要心疼程序员。因为程序员写的是程序里的 bug，也就是 Fault。你可能手滑把一个地方写错了，或者算法设计错了，有各种各样的 Fault。

这些 Fault 沿着程序的运行，需要一个合适的测试用例，把它运行起来，才能观测到一个 Error。但是有些 Error 其实是 silent 的，可能有一个数字“CP”了，或者有一个内存地址不小心被覆盖了，但覆盖的内存地址刚好没有导致后续计算再出错。可能你就觉得看起来挺对，没有观测到错误。所以即便程序的状态已经违反了 spec，你可能仍然有一种幻觉：程序可能是对的。

只有这个有 Error 的状态，最终比如像我上节课讲的，程序 hang 了，一直没有结果，你觉得这个程序可能 0.01 秒就应该运行完，但它运行了一分钟，你才知道这是一个 Failure。比如程序 crash 了，也是一种 Failure；输出的结果不对，也是一种 Failure。

程序有 bug，不代表就能触发 Error，你需要有很好的测试；触发了 Error，也不代表一定就能看到 Failure。所以这个链条的传递，需要用 testing，需要用 specification 和 assertions 去保证软件的质量。

表面上我讲了测试的故事，但最终还是软件的架构决定了系统怎么测试、架构好不好测试。当你有了一个真正的软件系统，还需要聪明才智，才能写出最合适的测试用例。好像现在真正好的 system design，还是一种 AI 模型没有完全掌握的东西，可能这也是我们现在还要上这门课的主要原因。

我举个例子。假设你们要实现一个稍微大一点的软件系统，比如上上节课看我许愿做了一个 CS:GO，可以在这个教室里突突突。一个很自然的问题是：怎么给这个 CS:GO 做测试？假设架构也做得比较好了，比如肯定会做一个游戏引擎，包括碰撞判定、射击、角色这些。游戏引擎一定和整个游戏的界面分开，因为游戏有一个状态。

比如 CS:GO 的状态，在我们玩游戏的人眼里，好像是一个 Dust II 的地图，有人在拿着枪。但实际上，这个状态里绝大部分的元素，比如子弹，是有坐标的。当前子弹有 $x,y$ 坐标，有速度，有 type，是 AK 的子弹，还是 AWM 的子弹。

有爆音，这个我很担心。喂喂喂，我的话筒看起来还 OK。

CS:GO 的状态会随着往前一个 frame 或者一个 tick、一帧，游戏就会模拟。即便渲染速度跟不上，游戏的各种状态更新也得跟上实时玩游戏的节奏，或者这个世界里，比如网络另一端玩游戏的人的节奏。

这个状态每次更新，甚至可能是 deterministic，完全确定性的。如果这一帧的逻辑就是子弹向前飞多少、碰撞会怎么样，那从同一个状态出发往下走一步，就一定到同一个下一个状态。当然，里面不仅可能有自发的子弹移动，还可能有人的指令。比如 player 1 现在按了 left key，按左的时候，player 1 又有什么样的反馈？

这是游戏底层的引擎，没有任何图像，不需要截图。所以它的测试，可以是每个函数都有足够多的单元测试，也可以在游戏引擎里有一些 replay 的测试。

当然，游戏最重要的，还是要把游戏场景绘制出来。所以其实有一个函数，会把游戏内的状态——没有任何图形，但可能有人手臂的状态等等——投射成一个显示的状态，再把它渲染成你看到的沙盘上的模型。

所以会看到，现在游戏都支持 replay、OB 视角这样的功能。OB 就是在这个状态上有一个不一样的投射。所有人在这个时间轴上、游戏的状态上，要达成绝对的一致，但不同人有不同的视图。玩家看到的是自己的第一人称视角，OB 可以看到全局的上帝视角。

如果这样的系统要测试，很自然，我就问了一下 GPT。这也是你们的 practice：做完以后，你不满意。DeepSeek 上一次在做的过程中，如果你看 trajectory，它到某一个时间点以后，就开始疯狂截图，小修、截图、小修、截图、小修。它就开始浪费你的 token，你的钱就浪费掉了。所以你想停下来，做一个比较好的测试框架，就问 GPT：“能不能做一个？我想把单元测试、模块级测试和 system test 分开来。”

GPT 给了我一个合理的答案，这当然是工程意义上非常合理的答案：比如项目源代码在这里，test 有三个层级，unit、module 和 system，外面有一个 `justfile`。

有多少同学用过 just？Just do something。你可以理解成这是一个退化版的 Makefile，让你执行一些命令，是命令的入口。你可以用 just 执行 system test 或者 unit test 之类的。目录分好以后，让它实现就行了。

但是，为什么说 testing，或者软件设计需要聪明才智？每个项目的规模不一样。如果这两天你就想让 DeepSeek vibe code 一个 CS:GO，发到 B 站上，起一个什么“震惊”“瘫坐”的标题，说现在 DeepSeek 模型也能做得多好，可能这样做就已经很好了。但如果我要维护一个现在可能已经十万行、未来可能变成一百万行的项目，就不能再用这个方式组织测试。虽然这个方式没有任何错误，我会做得稍微不一样。

我干了这样一件事。因为我们的项目还是维护文档的，我就在 `docs/testing.md` 里写了这个东西。我希望什么？我的框架本质上和刚才有好几个目录、有一个 `justfile` 或者 Makefile，没有本质区别。但是我希望有一个 Single Source of Truth，一个单一的事实来源。

在这个单一的事实来源里有一张表，列出所有测试。这张表在 Markdown 里，就是一个 Markdown 表格。比如我希望对每一个 Rust 的 crate 下的每一个东西——我甚至可以扩展我的 DSL，觉得不够用的时候——做 unit test，怎么做？比如 `cargo test`。打个比方，实际上我们不是这样做的。我就把命令写在这里，参数、tag 也可以写在这里，就得到了一个可扩展的架构。

每当系统里要增加一个测试，我就往这个表里添一项。任何开发者来了以后，都可以通过文档知道这个系统到底要跑多少测试，它们怎么跑。不需要维护额外的配置，不需要额外维护一个机器或者人写的 `justfile`。虽然背后的原理和 `justfile` 没有任何本质区别，但是我不需要双向同步它。

因为当 test 膨胀、架构膨胀以后，一定需要一个地方写文档。这时文档和 `justfile` 这些东西就形成了 cross dependency，形成了依赖关系，需要维护。维护着维护着，有时候模型不听指令，这边改了，那边没改，就比较糟糕。所以我们有一个 Single Source of Truth，时刻可以看到到底要做哪些测试，以及它是怎么同步的。

相当于后台有一个编译器，会把 Markdown 表格编译成一个统一的框架。它不仅可以编译这个东西，还可以编译别的东西。比如我可以声明，每次 pre-commit 时，某个 tag 的所有测试都要运行。可以声明每次 pre-commit 都要做完 unit test，才可以 commit；或者跑 CI 流程时，需要做一次完整的 system test，这个 merge request 才可以 merge。

我就可以在文档里，用另外一种代码的方式把它写出来。所有文档都写在一起，不会散落在各个地方。比如现在要有 commit hook，就会多一个 YAML；有 CI，就会有一个 `.github`。我非常讨厌那个 `.github`，因为它和 GitHub 绑定在一起。我希望在项目里写得很干净，用什么 tag，就用自己定义的合适的术语体系。

你会发现，这样的设计和工业界比较成功的一些系统，比如 Bazel 这样的构建系统，底层的想法很相似。或者说，我可以把它编译成 Bazel 的各种 rules。

所以本质上，我们谈软件工程，在概念上都是：我们要做测试，要做 unit test、module test、system test，都对。但这件事到底怎么做？到现在来说，这个工程智慧还是大家在实践中不断看更多系统，看别人怎么做，慢慢才能有自己的感受。

所以这个反馈信号比较弱，或者说反馈信号特别长。它有一种 tension：强化学习里的模型希望尽可能快地完成任务，但做这种事，其实是在比较慢地完成任务。我们先构建基础设施，可能复用一部分别人的基础设施，会浪费很多 token，但最终对人来说，这样一个相对比较大的项目可能更好维护一些。这是测试。

上节课我们引用了 Dijkstra 非常著名的话：“Testing shows the presence, not the absence of bugs.” 我们可以用 test 找到很多 bugs，并且修复它们，让软件质量变得更好，这是当然的。那有没有可能真的去证明，做出一个绝对正确的软件？

现在我们谈软件工程、做一个相对复杂的软件，比如从大二做 NEMU 实验，做操作系统内核、数据库、rewrite engine 的时候，好像写一个绝对正确的系统就是不可能的事情。因为你们已经默认了：我不可能写一个绝对正确的东西，它一定有 bug。我们总是，不管人还是 Agent，写出一段代码，堆一个十万行的屎山。堆出来以后可以运行，大概是对的，再不停测试，让它更对。

但其实更早，到 Alan Turing 的时候，就想过这件事。这是谁的 paper 里的？“Instead of debugging a program, one should prove that it meets its specifications.” 我们应该证明一个 program 就是对的，而不是去 debug。这应该是 McCarthy 的。“And this proof should be checked by a computer program.” 也就是说，就像写一个数学证明一样，这个数学证明应该由 computer 去 check。

所以大概 1962 年的时候，John McCarthy 就说：“For this to be possible”，我们就需要 formal system，有形式化方法，需要能够写证明。

你们在哪门课上会学怎么证明？离散数学。离散数学刚开始学的是逻辑，然后是各种证明、思维体操，被思维体操折磨得死去活来。每当想到那个五个学分的离散数学，每个字都听懂了，但面对一个看起来非常简单、又非常奇怪的题目，无从下手，因为在这门课上要 write proofs。

然后就没有了。离散数学结束以后，你们有一种如释重负：我终于再也不用处理这个非常复杂的数学系统，而是可以直接 rush 一个 CS:GO 出来。CS:GO 就可以运行，又回到计算机的世界了。

但其实在很长的实践里，从 1962 年 John McCarthy 说要用数学 specification 描述计算，到 Turing、冯·诺伊曼，他们都在说：有没有可能用一个严格的数学对象，像自然数一样？

你们知道怎么定义自然数吗？零是自然数；任何一个数，如果是自然数，那么它加一也是自然数。所以 $0+1$ 也是自然数，因为 $0+1$ 是自然数，所以 $0+1+1$ 也是自然数。这就是皮亚诺公理，这个规则叫自然数。当然，我们给它一个名字：零现在叫零，$0+1$ 叫一，这个东西叫二。这是在十进制意义上，也可以在二进制上给它一个名字，这叫零，这叫一，这叫一零。

这是我们熟悉的、离散数学课里讲过的相关内容。在自然数上，可以定义加减乘除等各种运算，其实可以在 Peano 算术上定义出程序、递归、函数这些东西，它就可以当成一个严格的数学对象。比如要证明 $x^2+2x+1=(x+1)^2$，大家初中的时候都会证明这样的东西，那是数学意义上严格的。有没有可能把程序也变得这么数学严格？这就是所谓的形式化方法。

人类其实走了很长的形式化方法路线。尤其因为他们是做逻辑、数学的数学家过来的，其实很早，1960、1970 年代，就做出了非常卓越的成果。

Tony Hoare 这篇论文，我看一下，我有论文。这个论文的标题就写得很厉害：An Axiomatic Basis for Computer Programming，计算机程序的公理基础。他说，在这个 paper 里面，“An attempt is made to explore the logical foundations of computer programming by use of techniques which were first applied in the study of geometry.” 就像几何一样，有公理和规则。你们初中学平面几何。“And a formal proof of a simple theorem is displayed.”

好像也没有特别多。你看这个表格里，还是你们相对比较熟悉的数学。短短的一小篇论文，但它创立了一整个……甚至我觉得，某种程度上，也没有带歪吧，让形式化方法走上了一个……可能还有另外一条对程序员来说发展更快的途径。

Hoare 三元组，你们可能听说过。我们有一段程序，程序是什么？程序是 state transition，Everything is a state machine。一段程序可能有很多输入，对于输入一，会有输出一，打比方说有输出。或者说，从输入和一个状态，有一个 $S_1$、input，然后 $S_1$ 如果到 input 2，它就会到 $S_1'$，等等，这是有 input 的情况。

我们要把程序所有可能的行为都压起来，去证明它，有一个公理的推理系统。假设程序在运行之前满足什么，就可以推出程序执行完以后，前置条件加程序可以得到一个后置条件。如果这个程序能终止，就可以把程序一步一步的执行串联起来，包括循环。

最难处理的其实是循环。对于一个顺序程序来说，执行这个程序，希望执行完以后，它的结果是这个程序执行的结果。说了一句废话。但是如果有一个 `while`、$P$，直觉是什么？条件循环结束以后，一定可以 assert 一个 not condition。

所以基本上要在循环里找到一个不变的东西：不管循环多少次，这一段程序满足的状态，或者说满足的数学性质都不会变的一个定理。再加上出来时知道这个条件不再成立，去证明程序的性质。

我不会讲这个，讲一讲要讲半天，因为它是数学。你们大概有个感觉就行：需要一个很好的定理，说明这个循环每次循环都满足什么，就可以把程序的执行串起来。程序可以先执行这个，再执行这个，可以把两个顺序的执行串起来。

比如现在知道 $x>0$，现在 $x$ 加一了，可以推出执行完以后 $x$ 还是大于零。类似地，可以把程序的数学性质变成证明的目标，包括数组不会越界、指针不会飘飞、数据结构不会损坏。

还记得今天要讲什么？讲软件质量保障。如果你写了一个非常复杂的软件系统，比如写一个带 parent 指针的树结构，这就麻烦了。有同学肯定写过，比如一个 balanced binary search tree。这棵树要求根上的值，比如五，一定比左边大、比右边小，比如九、七、十，这就是一个合法的树。

每个节点有一个 parent 指针。如果要维护这个 parent 指针，并且要做树的旋转，就非常容易写错。谁写谁知道，第一次写，如果不抄书，非常容易写错，写着写着就丢了。这背后有很多东西，如果要做这样的程序质量保障，有经验的话一定会写很多 assert。回想写错的过程，对于任何节点都要 assert。

假设这个，我就不写“GU”了。比如这个节点合不合法，左右可能是空的，parent 也可能是空的，我就假设它不空。你会要 assert，任何一个 `p`，`p.parent.left == p` 或者 `p.parent.right == p`。这是一个想要证明的性质，当然是以 assertion 的方式写在代码里。

这样，每次运行到这个节点时，一旦树结构，比如旋转时被你拉坏、扯坏了，很正常，指针比如指向下面的节点，parent 指向下面，数据不合法，这样的 assert 可以给你逮到。你可以写很多这样的 assert，比如 `p.value > p.left.value`，假设在合法的情况下。可以写出很多这样的东西。

程序里每一句话、每条语句，其实也都自带一些这样的 assertion。比如希望程序永远不 crash，就希望指针访问永远合法，永远不会在除法时除以零，这些都可以写。比如有一个 `return p / q`，你们都会写这样的代码，其实就隐含了 `q != 0`。写一个程序的 assertion，对程序当前状态的一个断言。

当然，我们也可以证明，不仅仅是在程序里写 assert，只能证明程序的当前状态，也可以证明程序从一开始执行到现在的性质。理论上可以用一个列表收集所有执行过的语句，再证明当前状态的性质，这也是可以的。但形式化方法就是要做这样一件事：希望能写的所有这些数学性质，最终都被证明是真的，无可辩驳地是真的。程序带一个证明，那这个程序就是对的。

我觉得这是一个非常美好的愿景，但是在当时，尤其考虑编程语言的发展速度，希望让每个程序都带有一个证明，这件事情真的有点生不逢时。

比如这个程序很好，是说现在要模拟一个投票过程，要选出得票最多的人。你手上会有一张纸，写一个名字，还有他有多少票。如果拿到一个选票，和手上的名字一样，就加一；如果不一样，就减一。减到零以后，下一次拿到下一个人的时候，就要换人。要找出的是票数严格超过一半的。这个算法是对的：如果有一个人票数超过一半，最后手上拿的那个就是对的。

你要证明它，就完了。因为在循环过程中，只有两个变量，一个是 candidate，一个是 vote，就是现在手上的人是谁、现在是几。它把历史丢掉了，程序是一个有损的压缩，把算法正确性留给了后人的智慧。你需要构造一个非常巧妙的、能够 capture 所有可能的情况到当前状态的循环不变式。那就不要谈证明数据结构、指针算法这些更复杂的东西了。

所以我觉得，在那个时候的形式化方法把大家带歪了。他们用大量人类智力去证明，比如能不能证明一棵平衡树确实是对的。可能到 1990 年，这还是一个很困难的研究问题。你可以提出一种新的逻辑，声称这种逻辑对于证明一个 binary search tree 更好。

当然，你想一下，没有程序员会干这件事。首先没有程序员懂数理逻辑，他学完离散课，就不想再学逻辑了。而且你还强迫他学一种新的逻辑，只是声称它证明红黑树，比另外一种证明系统稍微简单一点点，你不会用它。

那个时候，人类的智力是不 scale 的。今天的情形发生了根本性的变化：今天有 AI，PhD level 的智力是可以 scale 的。只要把模型权重复制一份，就多了一个 PhD level 的 intelligence。所以这些先驱做得太早了。形式化方法一直理论做得非常漂亮，而且非常好，反而是另外一条路，意外地在程序员群体里变得更 popular，所以他们其实也拿了一个图灵奖。

虽然他们走的也是在这种数学、数理逻辑的形式化，和一个完全暴力的方法之间的平衡。还是 Everything is a state machine，那为什么不能用暴力计算来证明程序正确？

程序总有一个初始状态。比如初始状态第一个是 `x = 1`，执行完了不就是一个 $x=1$ 吗？我就解释执行它，为什么不能证明程序是对的，或者说为什么比较麻烦？因为可以 `read x`、`read y`，就是 `y = input()`，写一个 Python 的 `y = input()`，然后把它 cast 成 int。

如果有一个外界输入，就惨了。可以 $x=1$、$y=0$，可以 $y=1$，可以 $y=1$，等等。哪怕只是限定 $y$ 的值在 $-10$ 到 $10$ 之间，也一下创建了一大堆可能的下一个状态，虽然这个过程完全是确定性的。

如果先不计代价，能够把状态转换图构建出来，就相当于在每一个状态上都判断一个 assert。比如要 assert $y>0$，就可以在每一个状态上直接用 assert 判断这个状态到底合法还是不合法。比如这个不合法，就找到了一个错误，好像这些都是合法的。

这是不是对程序员来说，心智负担就小多了？不需要学 Hoare 三元组，也不需要再把平面几何的噩梦重现一下。你看 Hoare 那个 paper，做了一个公理系统。如果能穷尽整个状态空间，确实也得到了一个正确性的证明。

所以我们讲一些内容时，会用到 proof by brute force。我上课时有一个很有意思的例子：如果有好多个线程，每个线程都会执行一个 `sum++`，最后能得到什么奇怪的结果？我们可以证明，不管有多少个线程，不管每个线程循环多少次，最终都有可能得到 `sum == 2`。这是一个非常奇怪的线程调度，但同样也是一个状态。

我们有一个程序，比如这个程序一开始是顺序执行的，顺序执行完了以后有好多状态。接下来，每个状态都有可能并发执行：有可能选 T1 执行一步，也可能选 T2 执行一步，每一步都可以这样选。状态空间很快就发生了状态爆炸，叫状态空间爆炸。

但从理论上说，用枚举的方式解决问题是可以的，这个概念更容易。你只要能够写出这个程序的解释器，就可以用暴力的方式证明这个程序是对的。后面几十年的时间里，人类就不停地沿着这条路径改进。我觉得有很多有意思、你们可能不知道、只有我这种做软件工程的人才知道的方法，我有必要跟大家科普一下。

如果我们要证明一个程序，先不谈什么 Hoare 三元组，我这儿已经被擦掉了。如果想做一个 proof by brute force，但这个程序真的很大，做不了 brute force，怎么办？有没有可能把程序里最核心的逻辑拿出来？

这是 model checking 领域里非常喜欢的例子：现在做一个自动售货机。仙林这边有自动售货机，现在的自动售货机都非常复杂。你可以看到一个图片展示的东西，点一下，会弹出一个二维码，甚至扫一个脸，然后把东西拿走。在那个年代，比如 1980 年、1990 年，大家讨论做自动售货机时，考虑的是它可能有一个纸币入口。你们多久没有用过纸币了？它不仅有纸币入口，还有一个硬币入口、一个退币口，按了以后要能够退出来。

这里面肯定有一个控制程序。控制程序可能要识别纸币、识别硬币，中间会涉及，比如硬币是称重的，如果重量不对，或者怎么分，它会有逻辑。所以这可能有几千、上万行代码。但如果想证明这几千、上万行代码正确，或者给它做质量保障，这个方法还不行，尤其在那个计算机很慢的时候。

我们能不能做一个状态机，把状态做一个抽象，或者说做一个建模？我们的程序想要的是：一开始总是零，如果收到一个一元硬币，就变成一；如果收到一个五元硬币，就变成五；五元时再收到一个一元硬币，就变成六。假设这个自动售货机里卖的饮料只有几种，价钱非常有限，状态转换图就可能不是很大。退币有一个专门的状态，可能退币，再按一个钮，比如按一个选择，它才会回到零，等等。这是一个不是很好的状态机建模方法，他们还提出了其他各种各样的状态机。

如果能够把一个自动售货机变成有几十个、几百个状态的状态图，就可以 proof by brute force 了。我们变成在这个状态图上遍历路径。有些状态，比如卡住的状态，就是不行的。我只要证明不存在从初始状态到坏状态的路径，用 breadth-first search 或者 depth-first search 就可以找到这样的路径。实际发生的事情比这个复杂，我只是说，conceptually，你可以这样理解。

很好，你很开心，先得到了一个正确的模型，再把这个正确的模型实现到自动售货机上面。你们有没有感受到，在这条路线上它做的 trade-off？它没有证明代码是对的，只证明了模型是对的。但模型的行为和代码的行为到底是不是一样？如果代码第一行就写一个 `return`，它就不是这个模型了。

所以，它把正确性分成两步。第一步要证明模型正确，这个没问题，是机器保证的。接下来还有一份代码，要保证代码确实实现了模型，模型的正确性才能在一定程度上体现为代码的正确性。

当然，即便模型正确，也不能代表代码就一定正确。比如中间算重量时有一个除法，除以 `y`，自动售货机 crash 了，这显然是你不想要的。即便模型正确，也没有完全证明系统的正确性。

我还遇到过比较有意思的事。我在自动售货机上买一个东西，东西没有掉下来，它就自动退款了。退款以后，我又买了一个，结果掉下来两个，我就赚了。这种实际中可能发生的情况，就是代码可能发生的。因为代码可能会检测物体掉下来、没掉下来，但你的模型可能没有建模，这都是有可能的。

有一个非常开创性的工作，我就不点开看了，也是 Lamport 的工作，叫 The Existence of Refinement Mappings。它在数学意义上证明了总是存在这样的……他们说麦炸了。

The Existence of Refinement Mappings，也是 Lamport 的 paper。它证明了你永远可以一层一层地把模型变成更复杂的模型，最终证明到代码的正确性，可以通过一层一层的方式来证明。

所以，即便最终没有资源证明代码是对的，你也可以在某种程度上相信它。比如可以测试，让代码在每次模型迁移时都用 `print` 打一个 log。让模型和代码执行同一个测试用例，看到代码打印出来的日志，比如从哪个状态到哪个状态，和在模型里执行这个测试用例的状态完全一样，就建立了一个信心：代码不是完全错的，没有在第一行就 `return`，大概实现了这个模型。

不能百分之百保证，但这就给了你对系统很大的信心。首先，模型经过了非常严格的验证，枚举了所有可能的路径；并且代码一定程度上还是实现了模型。代码可能会用别的方式检查，比如有没有除零、会不会有 memory corruption。可以选一个永远不会有 memory corruption 的编程语言，那就解决了 memory error。

所以，可以通过一层一层、越来越复杂的模型证明程序的正确性。TLA+，Lamport 的代表性工作，证明了很多，比如分布式共识协议的正确性。

而且，它不仅可以用来证明正确性，在这样的模型上，也可以用来指导生成测试用例。我可以证明系统、协议是对的，但实现到底对不对，我不知道。我可以通过形式化建模的模型采样出各种奇怪的测试用例，再把测试用例送到代码里运行。并且因为我在模型里，知道最终会停在哪个状态上，或者说，我就是一个对的模型，它会停到这个状态上，我会检查代码是不是也落到了这个对的状态上。

所以这是 refinement mapping。我可以把代码的状态投射回模型的状态时，你就拥有了对程序正确性更好的信心。这是一整条线的研究工作，你们会觉得还是很有智慧的吧？前人非常有智慧。虽然他们可能在几十年里都是研究一些很小、几十个状态的状态迁移系统，但这些想法 eventually 可以用到真实的、非常大的软件系统上。

以及，我们人类其实从来没有放弃过 proof by brute force。比如现在 `y = input`，从外界得到一个输入，有没有可能不要现在就把搜索树展开？它本质上是一个搜索树。有没有可能用一个数学公式来表示当前的搜索状态？

比如 `y` 是 input，我是不是可以有一个数学表示：`x = 1`，`y` 是任何一个整数。如果下面再执行一条语句，`z = x + y`，那就变成 `x = 1`，`y` 还是一个整数，`z = x + y` 怎么表示？它是一个方程。

所以可以想象，我可以把程序的每一个状态都列成一个方程。比如 `x`、`y`、`z` 都是整数，现在知道的是 `x = 1`，`y` 没有约束，`z = x + y`。刚才说，程序的每一步都是确定的，执行一个语句就会到下一个状态。如果执行一条这种语句，我就去列方程，搜索树不就少了吗？

如果下一条语句执行的是 `if z > 5`，就有两种情况了。还是 `x`、`y`、`z` 一样的方程，一种情况是 `z > 5`，进入这个分支。相当于 PC，比如这是第 8 行，`else` 第 12 行，那 PC 就等于 8，这是 if taken。

另一个也是同样的方程，比如 `x = 1`，`z = x + y`，这是 if not taken。两个的区别就是，这里有一个 `z > 5`，这里有一个 `z <= 5`，或者说 `not (z > 5)`，不就把 `if` 的两个分支分开了吗？通过不断往上加方程的形式，就可以建模这个程序很多条、可能非常多条路径。

我就把搜索的过程延后，变成问一个问题：这个方程有没有解？如果有解，就解出了一条从头到尾的路径，不就找到了一个测试用例吗？

然后就可以问，程序里写了 `assert`，比如要 `assert y != 0`。我有一个很长的程序，现在有 `assert y != 0`，就把这个 `assert` 写成 `if-else`：`if y == 0`，就 `abort`。那不就是问，能不能存在一条从程序开头到这里的路径？如果能找到这条路径，不就找到一个反例的测试用例吗？

当然，这是一个非常复杂的工程实现。如果想要证明一个模型，这是很早以前就有的技术。但如果想证明一个真实的程序，那就惨了，要建模每一条。首先需要一个代码的中间表示，比如 LLVM IR，需要一个可以执行、像指令集一样的东西。可以选 WM，可以选 LLVM IR，需要一个指令集。然后要模拟执行指令集里的所有指令，并且为每一条指令都列出方程，包括跳转指令。这是实现上很大的麻烦，但带来的好处是可以运行真正的程序，在真正的程序上跑路径，这也很有趣。

还有一会儿我要真正说的，我觉得可以说是整个人类在软件可靠性方法上的一个巅峰。其实人类从来没有真正放弃证明一个程序是对的，从逻辑意义上证明代码是对的。一开始只能做很小、几个状态的模型。然后 model checking，模型检验这条路，因为有 refinement mapping，可以做映射：做一个小模型，再做一个复杂模型、再做一个复杂模型，证明模型之间存在对应关系，最终走向证明代码是对的。

我们也可以直接用更暴力的方法，用解方程的方法解出，可能所有程序路径上都是对的。这种方法依赖于有一个很好的方程求解器，这也是这样的工作能够成功的原因：我们的求解器到某一个时刻，变得可以用了。

但真正疯狂的事情，我觉得还是想证明真正的程序从公理意义上就是对的。而且疯狂的事情还是有人做的，他们都被历史记住了。这里有两个非常值得大家了解一下，可能技术细节也许不那么重要。

一个是 CompCert，一个被证明的编译器。什么叫被证明的编译器？编译器其实是可以有 bug 的。你写一个合法的程序，编译它，编译器就 crash 了，没有把程序编译出来。它也可能做不正确的翻译。比如你写一个 `int f`，`return 1`，这个程序你相信它是对的。你知道它到底翻译出了什么指令吗？万一把 2 放到返回寄存器里，你能控制吗？你不知道，能相信吗？我们是选择 blind trust 这个编译器。

但人类真正做到了证明一个编译器，它编译出来的东西一定是对的。编译器就是个 transition，是个函数，输入一个字符串，输出另一个字符串。它证明的是：对任意输入字符串，只要这个字符串是个合法的 C 程序，输出的东西就一定和它语义等价。这是一件多么疯狂的事情。

2009 年完成，而且那只是一个非常初步的版本，它有很多，比如到机器语义的东西，没有证明。3 人年，4.2 万行证明代码。然后到 2009 年，它可能是 2006 年，这个可能要早一点，2007 年。一个永远不会 crash 的操作系统内核，25 人年，20 万行证明脚本。

他们试图去做非常疯狂的事情。因为你的编译器是用来编译上月球的代码的，如果编译器错了，编译出一个不正确的代码，月球车上去执行到这个代码时就挂了。他不希望用测试或者什么方法来解决，而是有没有一种可能，我们能证明程序是对的？在这样非常多人力的、先驱性的工作之后，OpenAI 就丢下了那个 722 篇的数学核弹，一举杀死了数学工作者。

所有这些背后，不管是刚才说要证明编译器永远不会编译出错误的程序，还是证明操作系统内核永远不会 crash，还是证明黎曼猜想的一部分，背后的机制都是一个叫 proof assistant 的东西。它给了我们真正证明一个东西的信心，是一个铁面无私的反馈机制。就是因为有这样的反馈机制，OpenAI 才可以用强化学习训练大规模模型，解决数学问题。

我们都说数学非常严格，但其实中学数学不够严格。想想，你们的选择题是可以猜的。当然，选择题、填空题某种程度上是培养数学直觉，让你直觉一下。但当真的要把它做对，并且很快做对时，可能需要猜。我们经常用各种奇怪的方法算出、猜出一个结果，然后怎么着掩饰一下，让改卷人改得快的时候，可能就给我批过去了。

你的草稿纸也可能是骗人的，计算过程可能是错的，但最后负负得正，结果又算对了。怎么样让数学杜绝一切可能的错误？还是用草稿纸，但要求草稿纸上的每一小步都是证明系统可以检验的。就像做平面几何时，就那几个公理来回整。不如把每一小步推导都严格写出来，而且只允许写用的是什么规则，让计算机帮你完成内部推导，这样就不会犯错误了。

你只写规则。比如你说用一个乘法分配律，但表达式里没有乘法，计算机会直接拒绝你。如果不说清楚到底对哪一个乘号做分配律，可能下一步推导就做不下去了。

所以 proof assistant 就是让你自己写一个证明，然后检查这个证明对不对的东西。它叫 assistant，你得手写一个 proof，但它能帮你省掉很多事情。

基本上，你要干这样的事：有一些已知，有一些待证，想要证明从已知可以推出待证。比如已知 `1 = 1`，可以推出 `1 = 1`。当已知和待证完全相同，每一个字符意义上都相同时，这个证明就是成立的。你想证的所有性质，逻辑性质、程序性质、数学性质，最终都要归到两个东西严格相等、逐字逐字符相等，这个证明就 check 好了。

比如我可以举些例子，我们怎么证明？现在有一些已知，当然可能可以从别的地方再搬一些 theorem 或者公理过来。比如想证明存在一个 `x`，`P(x)`。如果要证明这个班上至少有一个同学得了满分，已知的可能是同学们的成绩，或者有好多定理、好多公理。我可以通过变换证明目标的方式，让证明更容易。但变换以后，不代表这个证明就一定能证过去。

我可以尝试什么？可以选一个 A，用一个叫 choose 的规则。比如 A 考了 90 分，B 考了 100 分，C 考了什么，有一些已知。现在待证的是存在一个 `x`，`x100`，这个叫“x 考了 100 分”。可以把“存在 x，x100”里的 x 换成任何一个东西。比如可以声称，想把待证改成 `A100`。这是可以的，因为如果知道 A 考了 100 分，那么存在 x，x 考 100 分，这个命题就是成立的。所以可以这样改写，这个改写不改变证明的正确性。

但到这里就证不下去了，再也做不了任何变换，找不到两个东西相等。因为知道 A 考了 90 分，它和 `A100` 不是逐个字符相等的，所以这时选 A 就不对，选错了。还是存在 x，`P(x)`，得选 `B100`。选了以后，就跟已知的对上了，对上以后证明就 check 了。所以就可以证明，存在一个同学考了 100 分。

如果要证明对任意同学，比如都及格了，所有同学都及格了，就麻烦一些。对于 proof system，可以做的叫 `intro x`，就是说任取，可以把这个 `∀x` 去掉，x 就变成一个自由变量。这还是可以的，因为没有改变证明的正确性，还是需要它都成立。但想证明这个，就需要其他东西来继续把命题证明了，可能需要一些领域的定理。

比较有意思的是，如果有任意的自然数 n，比如要证明 `P(n)`，可以怎么改写？可以把它改写成 `P(0)`，首先 `P(0)` 是真的，就变成两个待证的。然后，对于任意 n，`P(n)` 都 imply `P(n + 1)`。当然，这个任意 n 也可以去掉。现在只要证明这两个，base case 和 inductive step 是正确的，就能证明整个命题正确。

所以它就不停地改写。一开始只有一个定理，怎么样通过合法改写，把所有证明都证过去？比如想证明所有保研的同学都及格了，怎么改写？可以把 `P(x)` 移到已知的地方，再去证明 `Q(x)`。

所以本质上是一个 proof state，是一个状态。但现在的 proof assistant 基本上设置的就是一个 proof stack，相当于一个栈的模式。刚才如果有一个 induction，要做归纳，比如有一个 `∀n`，当执行一个 proof system 的指令时，会把它变成 `P(0)`，以及对任意 n，`P(n)` 推出 `P(n + 1)`，做这个改变。

接下来，如果已知里直接有一个 `P(0)`，两个能对上，就可以把它清掉。它没有了以后，下一个就到 proof stack 的顶上，可以继续证明。因为我们有皮亚诺算术、有归纳法，能递归定义：零是自然数，0 + 1 是自然数，任何自然数加一都是自然数。就可以用它构建在 Computer Science 里看到的几乎一切东西。这个证明系统的能力非常强。

而且 proof assistant 还可以在这个基础上构造各种语法糖，比如把 Hoare 逻辑放进来，让你用 Hoare 逻辑里的公理推导，但用的是同一套逻辑体系。

这里面我觉得是人类文明真正的高光时刻，也是整个计算机科学里我最喜欢的东西之一，叫 Curry–Howard correspondence，说的是“命题即类型，证明即程序”。这个也有点递归，可能有一点绕，我不确定能不能讲好，我第一次讲 Curry–Howard correspondence。但在南大可以上到一门课，叫《程序设计语言的形式语义》，这门课专门讲这些。你们上到最后应该比较痛苦和折磨。我不确定有没有上过，上过应该非常痛苦和折磨，因为每天处理这种非常奇怪的函数。

Curry–Howard correspondence 告诉你什么？每一个命题，比如所有保研的学生所有的课程都及格了，它可能是一个 for all，`∀x`，什么符号 x、符号 y，什么 `P(x)`、`Q(y)` imply `R(x, y)`。反正任何数学上可以成立的，比如哥德巴赫猜想，任何一个大于等于 6 的偶数，都可以写成两个奇素数的和；或者程序不会 crash，对于所有 step，程序都不会到达 crash 状态。

我可以对任何状态图，哪怕无限状态图，写出这样的逻辑公式。只要有一个计数器不断往前加一，就可以像动态规划一样，知道在第 x 步时程序运行到哪里。想要证明的是这个逻辑公式成立，相当于想证明程序是对的，不会 crash。

或者，对于任意一个程序，想象程序就是一个自然数。可以把程序变成字符串，就意味着可以用一个整数编码它，可以把所有字符串投射到自然数集上，这两个是等势的。你们还记得离散数学里学过这个吗？Cardinality。两个自然数的 Cartesian product，集合的 product，还是可以和自然数做一一对应。可以把字符串和自然数做一一对应，所以可以写出 for all program，对于任何自然数，我的一个函数满足某个性质，这个函数就是编译器，永远是对的。

它可以非常复杂，但再复杂，构成它们的基本元素都是这种 P、Q、R，最终都会归到皮亚诺算术上。比如两数加起来，这里一个数输出是几，这个东西输出一定也是几，等等，这样的逻辑表达式。

最有趣的地方在于，这里面最重要的是蕴含，implies。如果要证明在前提成立的条件下，比如想证明对于任意 program，这个 compile 是正确的，那么就 imply，比如编译器生成的东西会怎么样。所以可以写出非常复杂的东西，但里面最关键的是：想证明在某个前提成立的情况下，后置条件是成立的。那怎么证明它？

它找到了一个 Curry–Howard correspondence，找到一个非常优雅的方式。你需要写一个程序。这个程序很有意思，它可以把每一个谓词都映射成一个类型：type of P，一个 P 对应的类型；Q 也对应一个 type of Q，一个 Q 对应的类型。

你要做的是实现一个函数。这个函数可以随便实现，甚至不会真的去运行它。你只要能够一步一步地把收到的一个 P 类型的对象，用公理系统和定理里面允许的操作去变换，不能强制类型转换。比如有一个整数，就可以构建一个整数的二元组，从一种类型得到另一种类型。你有与、或、非的条件，比如 P 或 Q、P 且 Q，就可以得到别的类型的东西，做一个类型体操。刚才说的 proof stack 里面的各种操作，都变成了类型的转换。

只要在一个类型安全的系统里面做完类型体操，能把一个 P 类型的对象变成一个 Q 类型的对象，给出这样的一个程序，就能够证明 $P \Rightarrow Q$，非常有意思。

它和 proof stack 的关系是什么？我们想最简单的 case：刚才说，如果知道 $x = 1$，这个 $x = 1$ 就可以合上。如果这是 P，这是 Q，P 和 Q 完全相同，也就是说我自己可以推出我自己，这是显然的。我只要给一个什么样的函数？只要构建一个 lambda，直接返回输入参数自己。这是 TypeScript 的写法，如果写 Python，就是 `lambda x: x`。这个 x 的类型是 P，是要证明的类型，输出的类型经过推导以后肯定和它完全一样，所以这个证明就过去了。

所有这些都和 proof system 里面的公理系统一一对应。每一个操作，包括归纳法，都可以写出来。最有意思的其实是归纳法，它会写成一个递归程序。

为了得到一个 induction 的证明，我首先需要一个 base case，就是 $P(0)$。比如证明 $a + b = b + a$，对于所有的 a、所有的 b，都有 $a + b = b + a$。先不管能不能证，归纳时，比如对 a 做归纳，那 base case 就是 $P(0)$：对于任意的 b，$0 + b = b + 0$，需要证明这个。第二个，要对于任意的 a，把这个式子抄进去，相当于 $P(a) \Rightarrow P(a + 1)$。平时在离散数学课上写数学，也是这样写的。

到了程序里面，在构造的那个 f 里面，其实写一个递归。输入任何一个 n，在里面构造一个函数：如果是零，就会调用 base 的情况；如果不是零，就会调用 step 的情况。最后把这个函数的类型返回回来，这个函数就和证明合上了，和 induction 的公理合上了。这其实给了一个递归计算的过程，所以递归和归纳又是等价的，这是一个非常美妙的事情。

但确实需要花很多时间一点一点地做。第一次证这个都会觉得很困难，$a + b = b + a$ 看起来如此显然，却得用归纳法把它拆成一个一个的，非常有意思。

我学 proof assistant 已经是好久以前的事情，一晃好多年过去了。我觉得应该在离散数学课上给大家教一点 proof assistant。其实我们设计这个课程时，我有这个考虑：既然你们已经可以在南大上到计算机程序设计、编程语言的形式语义，为什么不能在大一的时候就学？甚至不要到大一，也许小学的时候就可以学。我觉得反正小学生也不会数学，也许可以在高年级时给他洗脑：“来，这个就叫数学。”

比如那天我就 Vibe 了一下，把上课时讲过的那个 Python playground，可以移汉诺塔碟子的，改造成 Lean 的 playground，也就是 proof assistant 的 playground。你可以在里面定义函数。Lean 是一个很好的语言，不仅是一个证明语言。在这里，如果是 theorem，在 tactic mode 底下，它允许你写证明，有些奇怪的什么 `simplify only`，你也不知道它是怎么证的，anyway。

但也可以把它当成一个普通的函数式程序设计语言来用。我可以定义函数 f x y，让它等于布尔，写任何计算函数。C 里面能写的，在 Lean 里面也能写。小朋友、小学生可能学 Scratch、Python、C++，那我们也可以学另外一种能够编程的语言。

它是一个 functional programming language，就可以用它来定义，比如你要画一个图，不就可以定义一个函数？我是把 f 画在了右边。我自己会让它生成 Lean 可执行的代码，再把代码链接到我的 JavaScript 世界里面，把这个世界里面一个真实的 $100 \times 100$ 的分形，谢尔宾斯基三角形，给画出来。小朋友不就说：“哦，原来我就是定义了一个函数。”它不仅可以定义函数，还可以证明函数的正确性，证明对于所有整数都成立，不仅仅是检查一万个点。也可以证明，比如画布外面全部都是白色，等等。所以我觉得，我们可能有一个前所未有的机会，可以让大家都去学一点 proof assistant。

这是 proof assistant。接下来给大家讲一个和它相关的鬼故事。其实我的博士论文烂尾了。这里有一个我读 PhD 的回忆录，你们可能有同学看过，感觉好久以前了。

我的论文怎么烂尾的？因为当时有一个发现：如果要观测一个程序的执行，你记得越多，恢复的 cost 越小；记得越少，cost 越大。我发现人类做了三十年，这个地方都没有东西：不可能做到记录的 cost 又小，恢复的 cost 也小，两个 cost 没办法同时做小。我就猜，这个地方是不是真的没有？盲猜一个没有，我的论文就烂尾了。

因为这很难证明。我要的是对于任意的 program，一个什么什么 imply……[公式不清]。如果我能在 polynomial time 做一件什么事，P 等于……[公式不清]。我证明的是，对于任意的 program、对于任意的某种修改，做了修改以后，如果能在 polynomial time 做某件事情，我就知道 $P = NP$。所以这个东西我不会处理，不仅要对任意的程序，也要对任意的修改。我就搁置了，只证明了一个非常受限的情况。

那个时候我还不会用 proof system，所以有一个 informal 的 proof，大概看了一百遍。每天都在想，万一这个错了，我就彻底晚节不保了。还很担心这个 conjecture 有一天被推翻了，我也晚节不保，相当于立了一个 flag，这个 flag 倒了。

今年的某一天，我发现还有重置卡，用不掉了，就想起了一个不属于我的力量。好消息就是没有晚节不保：GPT 先给我写了一个 informal 的 proof。它中间还放弃过一次，说好像证不出来。我就鼓励它一下，说我觉得在直觉上这个什么什么，我也不知道怎么证，但根据一些印象和直觉推了它一把，它就证出来了，又给了一个 informal proof。

之后我让 Claude 交叉检查了一下，Claude 说好像没什么问题。又写了两万行 Lean，烧了更多 token，就把这件事情给弄过去了。当时那个 Lean 写完以后，因为我知道这个题目，又顺着它往后推了一些有用的结论。GPT-6 出来，说可以投一个论文了。

这叫 Principles of Distributed Computing，分布式，是一个理论计算机的 top conference。我不是做理论计算机的，一点也不懂。GPT 认为已经过了它的 bar，Claude Opus 认为在 borderline 上。Anyway，这已经不重要了，我已经不想投它了。这是一件多么可怕的事情：我有一个不属于我的力量，竟然可以用它来产生一些有用的、稍有用的东西。

现在我们面临形式化方法最好的时代。之前像 seL4，形式化验证的操作系统内核；CompCert，形式化验证的编译器，它们需要的都是顶级的人类智力。现在突然从软件构建的角度，这个人类智力有了，而且无穷无尽。

如果要做一些新的、创新的东西，不知道你们会不会去证明，不管写毕业论文还是想发表论文，都需要证明一个不存在的创新点，所以需要付出很多 storytelling tax，包装你的东西；需要 engineering tax，写代码、做实验，证明方法有效。Engineering tax 显然已经被 Coding Agent 碾平了。还需要把它提炼成一些数学表达，formalization tax 之前也碾平了，可以让它写很好的数学 formulation。到了今天，不管证明一个证明本身，还是证明一个软件，也成 tax 了，就是说也不难了。

只要知道有个概念，这个世界上有一个东西叫 Curry–Howard correspondence。你看，我曾经推过，现在也推不下去了，也翻车了。但不妨碍我大概知道，这个世界上有一个不属于我的力量，可以借过来解决一些还属于我力量范围里面的东西。

前两天 Anthropic 的 blog，Anthropic 没有被墙，叫“LLMs are making formal software verification feasible at a much larger scale”。它证明了一个……[名称不清]，在 64 兆的 RAM 上面不会有任何 crash，就是一个证明。里面有一句话耐人寻味，叫“This is just the beginning”，这只是开始。

我不知道这件事情真的什么时候会来，因为我觉得 Lean、Coq 本身的设计，proof stack 的设计，是为数学设计的，不是为了程序设计的。我们可能需要一个更好的语言，也许也不需要，反正 AI 也能写汇编，它有点像汇编语言。但这件事情真的来了，我们可以证明数学性质，而且不再害怕大型软件系统的数学性质，它会大幅增强我们的信心。

以前，对于程序员来说，能理解到这个已经是凤毛麟角了。知道形式化方法，知道一些软件验证方法里面的基本原理，就真的已经是凤毛麟角了，它是非常 involved 的数学。但当数学突然变便宜时，这个事情就彻底变了。

当然比较难受的是，像那家融了很多钱的……[公司名不清]。他们当时融资时就说，我们看到数学是一个很好的手段，可以提升软件可靠性，可以对齐人类世界里面的东西，所以要做数学证明。结果发现，模型直接把数学证明给碾过去了，最难受的是他们。

但是数学解决了，剩下的是什么？剩下的是模型如何和人类世界对齐。或者说，我确实可以写一个数学证明，但是如果数学证明之外还有另外一份代码，这个代码是 implementation。还记得软件工程最基本的 gap：有 implementation，还有 spec，还有 intent，中间是有 gap 的。我们人最终还是在这一层。

我确实有一个 formalized 的 theorem，这个 theorem、proof 现在公理化地证明了这是对的，但这个 theorem 是不是真的对应了我的 implementation？Implementation 又是不是对应了 spec？Spec 是不是又真实反映了人类意图？当所有这些都变便宜以后，又回到软件工程最根本的 gap 上。

实际上之前闹过很多笑话，证明了一个寂寞。我记得之前有人声称证明了 $P \ne NP$，还是 $P = NP$？应该是 $P \ne NP$。他声称有很长的 Lean 证明，最后大家发现中间有一个定义是错的。形式化的东西，你可能不会去检查每一个细节。

打个比方，我声称 $P = NP$，因为找到了一个 P 的算法。但他声称找到的算法，可能不是原来那个问题的算法，而是原来问题的一个非常小的特例，这个特例刚好能在多项式时间里解决。就是说我 propose 一个问题，这个问题可能有非常少的一部分不好解决，但他说：“好，我解决大部分。”然后以为自己解决了这个问题。你的 theorem 中间断掉了，虽然看起来有些东西证明了，但最终因为核心的 theorem 写错了，所以就是错的。

当然，因为我有一些领域知识，知道可以一定程度上防止形式化验证变成“证了个寂寞”。因为这里面有程序、有程序的执行，所以我可以测试它，可以模拟，就像 model checking 一样。我可以在一个模型上生成很多程序的执行，要求所有看起来正确、好的执行，都要在我的机器模型上通过；所有不合法的执行，都要能够拒绝。这样一定程度上，我知道你的程序确实解决了原来的问题。并且可以检查一些定义，至少增加一些对形式化的信心，这叫 autoformalization。

所以今天给大家讲一个故事，是告诉大家：你们可能必须一定程度上去掌握没有办法掌控的力量，去体验那些超出能力边界的事情，一点一点把它收纳到自己的能力边界里。

我今天真正想说的，其实是软件质量的未来。我讲了形式化方法，讲了人类的终极目标还是证明，但突然之间，证明这件事情变得可以了。我又翻出一篇很老的论文，叫 Proof-Carrying Code。它在 1997 年又重新写了一篇 POPL 的文章，就叫 Proof-Carrying Code，这个名字被大家记住了，而且广为流传。实际上，它在 OSDI 96 的时候发布了这样一张图。

它说，我有一个愿景：希望源代码给你以后，你可以不相信它。就像刚才说的，我们所有人都盲信编译器，假设编译器不会编译出错的东西，但这件事情其实不对，可以找到很多编译器里面的 bug。只是我们常见的代码，bug 都已经触发过，开发者基本修掉了，而且有海量的 regression test，一定程度上保证了编译器的质量。

那能不能在源代码旁边带一些证明，有一个 checker，proof validation？你看，这里有一个 proof validation。我们要到什么程度？它证明的其实也不多，比如不会 memory corrupt，不会 crash。就像今天的 eBPF，它有个编译器。eBPF 和 Proof-Carrying Code 有点像，但不太一样。我要做一个绝对安全的东西，可以安全地把它插到操作系统内核里面，不会 corrupt 操作系统世界里面的别的东西。

这样想，我们的 specification 在哪里？代码里面很多 specification、很多性质，都可以直接写一个 `assert`。刚才讲的平衡树例子，我们的 parent 指针，要知道任何一个节点，它的 parent 的 left 是自己，或者 parent 的 right 是自己，这就是一个 specification。

写 `assert` 时，它是在运行时被校验的。理论上也可以在程序运行时 collect 程序运行的 trace，一边 collect，一边用 `assert` 断言：从程序执行的一开始到现在的状态上，有什么东西是正确的。

如果今天能做 Proof-Carrying Code，是不是意味着以后写一个 `assert`，大语言模型不能把它翻译成正确的 proof system 代码，你就过不了编译？代码就自带 specification、自带 assertion，编译器自带校验功能。我觉得以前在 LLM 之前，可能会说三十年有没有希望，现在觉得很快就要实现了。整个软件可靠性的所有教科书，上课讲的所有东西都要重写。

因为以前会认为，证明是一个非常需要数学能力、数学智力的东西，这也对。你想证明链表是个链表，证明树是棵树，太难了。但如果今天它不难了，所有 `assert` 都能证明，故事可能就完全变了，很有意思。

这个 paper，nothing new，这边是 nothing new。它是 OSDI 96 的 best paper。但你看前面讲的 Curry–Howard correspondence，或者逻辑，这些真正优雅的东西早就有了。为什么它能得 best paper？其实 PL 和 OS 一直有一个鄙视链，互相鄙视。做 programming language 的说，我做这个东西，不 care 有什么用，我只管做，不管用。OS 人士说，我只管用，不管怎么来的，只要这个东西有，就可以拿过来用，只要有用就有用。这是两个完全不同的逻辑。

一个 PL 的人，总觉得你们这帮做操作系统的人，一天到晚就做我们已经做过的东西。做操作系统的人就鄙视他们，说你们一天到晚就做自己也不管有没有用的东西。然后软工人在后面瑟瑟发抖，开玩笑。

这节课随便讲一点未来可能要发生的事情。我昨天发了个小红书，又稍微读了一下那些可能好多年以前读过的老文章。我觉得所谓的 SOTA，可以叫 State of Trivial Arrogance，也可以叫 Slop Optimized To Ascend，也可以说 Science of Trivial Advances。当我们谈 SOTA 时，当然你们要毕业，肯定要发一篇 SOTA paper，但也可以回头想一想，历史上的人做过这么多很了不起的工作，我们也许可以在他们的肩膀上往前多走一点。

最后，形式化方法当然一定会在未来有非常蓬勃的发展。但是 There is no Silver Bullet，还是没有银弹。刚才说软件工程的本质，intent、spec、implementation 的 gap。现在就算 implementation 里面所有能写出来的细碎性质，我都能证明：证明它不 crash，证明数据结构是对的，甚至证明 performance 能达到某个程度，cache miss rate 能到某个程度，只要有足够多算力，都可以证明。

但形式化的价值依赖于，我们能不能用比实现更简单、独立的方式表达正确。比如对于任意的程序状态、任意的 memory access，这个 memory access 都不能越界。这就是用一个非常简洁、独立于程序实现的方式，表达程序要满足的正确性，它不 crash。

但不是人类世界里的所有东西都能用这种方式表达。刚才说的两种是容易表达的，构建软件里面最困难的部分，其实是决定到底要造什么。这个问题叫 autoformalization，就是怎样把 informal 的东西翻译成 formal 的东西。

前面讲的那些例子，autoformalization 都比较容易，不管是 crash、越界，还是定理。像要证明数学定理时，autoformalization 其实已经开始有问题了。OpenAI 里面有一个证明，那个证明其实应该是对的，但有点图文不符：Lean 证明的东西，实际上不是自然语言里面写的那个东西。我不知道是大语言模型翻译时出了幻觉，还是别的原因。虽然可能最终那个定理，如果陈述时依赖的公理系统没有问题，最终的证明应该还是成立的，但中间确实有了自然语言和形式语言之间的不一致。

如果要证明的不是这种还算比较干净的数学性质，给你两个例子。第一个，想做一个领导满意的教务系统。这就比较麻烦，到底什么是领导满意？这是一种艺术，要猜领导到底想要什么。也许他对性能不感兴趣，甚至对 crash 也不感兴趣，但向上交账时，对那个界面、dashboard 比较感兴趣，所以要把界面做得比较好。这个就开始偏离形式化方法搭的这个，从霍尔逻辑到 Curry–Howard correspondence 整个大厦的地基就动摇了。

还有，我要一个用户满意的折叠屏关闭特效。就在那个……[型号不清]出来的时候，大家看到合上时有一个毛玻璃效果，窗口缓缓地好像折上一样，又在正面屏上有一个等价效果。啪，合上，你觉得很好。我相信这不是唯一好的折叠屏关闭特效，而是万千合理的关闭特效中的一个。你其实想要的是自然、舒适、符合预期，但这些事情都 grounding 到人类的心理世界当中，我们人内心所想是我们想要的。

模型学了无限的语料，在强化学习当中、在数学领域里，真正大杀四方。但它毕竟不是一个人，还是没办法完全彻底地共情我们人类那些细小的、chemical-driven 的思想。所以这显然是 autoformalization 有困难的案例。当然还有很多介于中间：可能其实可以 autoformalize，但那个形式化表达很长，人也很难检查。像这样的东西，明显不太好做形式化验证。

但这给我们一点很有意思的启发。我有一个暴论：人类，尤其人类的推理系统，System II，就是用来做数学的系统，是完全理性的。也就是说，我认为我的所有行为都可以解释。很多人认为自己有创造力，自己的行为是某种上天赋予的，但我不这么认为。

至少从我看来，你们可能认为我有一定创新性，能写出有一定创新性的论文，上出有一定创新性的课，以及在小红书上发抽象的帖子，这都是创新性的体现。但我依旧认为，我的所有输出都是由某一个接近于 deterministic 的系统，一个形式推理系统，在各种 grounding 到人类世界的、可能是神经网络或者打分的网络，加上形式推理系统完成的。

因为人类的 autoformalization 有随机性。我说它好，今天觉得它好，明天就觉得它不好，它会在当前感知到的环境上注入一些随机性。以及人类推理时会出现错误，这些错误会把整个系统引向另外一个不太一样的方向，然后就表现得好像发现了什么新的东西，有了创新性，想到了别的什么。

所以当 AI 今天已经解决了 formal 世界的问题以后，其实也一定程度上能 autoformalize。如果下一步能够让 AI，我相信 OpenAI 和 Anthropic 想做的，就是把人类意图和模型真正对齐，再用好模型的 formalization 能力，它就可以真的像一个人一样。我觉得那天 AGI 就来了。
