今天我们来讲软件的质量保障。上一节课讲了一个造航母的例子。一艘真正的航母，如果你直接上去，会觉得非常震撼：人类怎么可能造出如此复杂的系统？不仅是航母，今天的操作系统、编译器也是这样。我相信同学们，尤其是学 Computer Science 的同学，都有这样的经历：听说应该了解操作系统内核、应用服务器架构这些大型软件系统，于是把 GitHub 上的代码克隆下来，一看五六十万行代码，直接就懵了，不知道从哪下手。README 好像还能看懂，马上又不知道从哪下手了。

某种程度上，现在能够在工业级使用的东西都是航母。它在演化过程中不断加入新的需求，为了满足这些需求，肯定会越来越复杂。比如航母要能起降飞机、能容错。但如果回头看一个演化模型，最开始只是一个小独木舟，具有在水上漂浮的功能，是功能最小、最简单的模型。这就是整个系统的状态，repository 的状态。

在这个 repository 上，可以想象人类发明航母的历程：不断 commit，加 feature。有时加了一个 feature，大家会做思维链推导，和今天 Agent 做事情很像。做思维链推导、Multi-Agent，多个人协作，甚至社会当中会有相应的组织来改进航行的船。状态不断演进，最后就得到了今天非常复杂的软件系统。

为什么今天许愿编程好用，但总觉得差一点？其实和许愿要一个航母一样。你说：“我想要一个能够起降最先进喷气式战斗机的航母。”就这一句话，让 AI 去造。AI 不知道你真正的意图是什么，虽然理论上知道这个过程，但没有经历过从简单到复杂、一次次思考的完整流程。它直接上手造各种东西，所以许个愿，造出来的东西大概率不能符合预期。让 AI 造航母，它造不了；甚至让它造一个相对小一些的东西，造一个教育系统，也造不好。Intent、Specification 和 Implementation 之间的 gap 一直存在。

我们也教大家怎样理解复杂的软件系统。比如今天想知道系统里的某个 feature 怎样工作，可以看这个 feature 从什么时候引入，带着引入这个 feature 的提交，从软件最开始的时候 rebase。可以想象，最简单、还是独木舟的时候，让独木舟起降飞机是不是合理的需求？那时不合理。等到有一天船足够大，起降飞机突然就成为合适的需求。再去看怎样在采矿船、运煤船上加一层甲板，改造出能够起降飞机的装置，甲板又是怎样演化的。

软件演化是一个连续过程，所以一定要从某个能理解的历史时刻开始 rebase。这也是为什么我们上学时这么痛苦，要做那么多大作业，实现各种软件系统。对精简系统有了深刻了解，就可以 rebase 现在的特性，通过理解小东西来理解更大的东西。

所以我觉得，用 AI 写大作业，肯定会丧失对软件系统的理解。自己上手做过一遍，和 AI 告诉你所谓的坑点在哪里，还是有很大不一样。我们这些古法编程过来的人，有些细节是在不断试错中，可能一个 bug 真的调了好几天，才得到这样的经验。现在我们都许愿编程，我也许愿编程，一旦网断了，甚至不知道应该怎么办。

许愿编程的后果就是，人类不再掌控软件。以前软件生产很慢，由人来生产时，不停地提交，每个提交都很小。Git 非常重要的 best practice 是，每次提交只做一小件事。这样就可以审计、追踪，可以 `git blame`，知道谁加的特性，怎样引入了 bug。某种程度上，这也提供了可以 rebase 的基础。

但当 AI 每个 commit 都改动一两万行代码，两三百个提交就造出一个航母，人类就失去了对软件的掌控，已经不知道这个软件是什么了。反正看起来测试通过了，运行起来基本功能正常，看起来是那么一个航母，叫它起飞一架飞机，真的能起飞。除此之外，我对它一无所知。

AI Agent 回头说：“我构造了一个高质量的设计、优雅的软件。”它到底怎样高质量，高到什么程度？设计到底好不好，还有没有可能扩展？只要不真正把新需求交给它做，就没有办法评估。等真正把需求加给它，它会向你道歉：“对不起，是我错了，我对架构的理解没有想的那么好。”它会给一个非常诚挚的道歉，但屎山又扶不起来了。许愿编程的后果，就是人类不再掌控软件，只了解它的一些表象。

所以这门课还是开给 Computer Science 的同学们的。尤其在这个时间点，你们接受过相对专业的训练，写过操作系统、编译器、数据库的实现。这些经验还是有用的，至少学了这个专业还是有用，可以静下心来学一学。

今天要讲软件质量保障。刚才说，许愿编程的后果是人类不再掌控软件，但依然需要对软件质量作出某种承诺。所以某种意义上，软件质量保障在 AI Agent 时代变得更重要了。

今天主要讲测试，还有一个比较重要的调试理论。我上操作系统课时可能也会讲，不确定，因为每年课时安排有些变化，可能不是每次都会讲。但这个内容一直以来，从上计算机系统基础时就会讲。

什么是软件里的缺陷？可以想一想，什么是软件？软件是物理世界的过程在信息世界里的投影。那什么叫 bug？每天都在写 bug，到底什么是 bug？我们就要从调试理论讲起，实际上它是整个软件质量保障里非常重要的基础理论。

进入这部分内容，首先要清醒地认识到：任何程序员都有幻觉，任何程序员都不可信，代码写出来天生就有 bug。上计算机系统基础时讲软件设计的公理：“未测代码永远是错的。”第一条是“机器码是对的”。不真正保证质量，人类的幻觉其实远远比 AI Agent 的幻觉大。

古法编程过就知道，写一个期末考试题，调半天，好像对了，又调两个小时。相比古法编程，今天的 AI 真是神技。我们这么快就对 AI Agent 习以为常了，甚至经常嫌 GPUSSRA 跑得慢，说 Tibo 又给我们降速。但真的是神奇。

想一想，在 GPT-3.5 和 GPT-4 的时代，这两个模型其实已经很强了，博古通今，虽然大家都诟病它们幻觉严重。这是上节课的截图。它们在 SWE-bench 这一组维护软件工程的任务上，你把代码贴给它，问能不能给一个 patch，打进去就能修复程序。它兴致勃勃地写下一个 patch，放进去其实不能修复。可以看到，resolution rate 非常低。ChatGPT-3.5、Claude 2、Claude 3 Opus，还有一些小号的开源模型，那个时候基本只有 Llama 系列的模型。

写程序会写出很多类型的 bug，最常见的就是手滑。相信你们已经熟练掌握 Shell 命令，尤其用多了以后，但依然经常 typo。把一个命令、参数、文件名打错，都是非常正常的事情。

在 pre-LLM 时代，甚至还有这样的项目，你们应该没有用过，那时还是很火爆的。看它的 commit history，10 年、11 年以前的 configure，现在已经基本死了。这个东西怎样用？我没有装，今天翻车了，没有来得及装。大概是在 Shell 里打一个命令，可能错了，比如编译东西时报告找不到什么，或者 typo，某个命令打错了。你直接在 Shell 里骂粗口，说一句脏话，它就会根据 Shell 的 history，找到上一个问题，用一系列匹配模式找到常见错误，把它修复。

所以，人类程序员在 blame AI，比如写 SWE-bench paper，说 AI 幻觉严重时，没有想到人类的幻觉也极度严重。但人类是一个 ReAct 的 Agent，在幻觉之后，立即根据输出反馈调整行为，快速修复。写代码也一样，如果不给编译器，不允许运行程序，要求你写对，还能写对吗？肯定写不对。

当然，人类幻觉的分布不一样。经受过良好训练的人，在架构设计上不容易出现像 Agent 那样偏离的情况，可能会做比较好的架构设计。但写代码时就是会偏移。好像让你从 1 数到 300，基本一定会数错。看起来是非常简单的任务，但因为短时记忆的问题，人类有幻觉。

比如这样一份代码，你们都写过这样的 bug：`for (i = 0; i < n; i++)`。人和 AI 模型很像，人也有 self-attention。写第二重循环时，写了 `j = 0`、`j < n`，结果眼睛不小心往上一瞟，self-attention 把那个权重错误地加大了。正好边上有什么东西干扰一下，觉得“这是对的”，就写错了，写成 `i++`。

这样一段代码放在这里，你写了一个 bug，我们给它一个名字，可以叫 bug，我们叫它 Fault。这样的 bug 有千千万万种。这是一个 self-attention 出错的 typo，也有可能漏了某种重要情况、忘了考虑，甚至写算法题时算法本身就是错的。有很多类型的 Fault。

但就这么写在纸面上，人眼可能看不出来。尤其当代码埋在 100 行代码里，会感觉好像挺对，因为脑袋里的模型是：第一步把数据读进来，做预处理，预处理完用二重循环把事情干了，再输出结果。视觉系统扫一眼，非常符合架构设计，所以会倾向于认为代码和脑袋里的架构设计保持一致，可能是对的。

这才是谈软件质量保障时，真正要在程序里找到的东西。不管是人犯的 bug，还是 Agent 犯的 bug。一会儿有 Agent 的 trajectory，也是各种看起来非常傻、人会嘲笑它的 bug，但 Agent 就是会犯。

程序里到处都是 bug。每天 GitHub 上有那么多 patch，号称修复了很多 bug，也就是说，满世界都是 bug。那为什么 bug 这么难找？

因为人或者 AI Agent 看起来觉得代码基本满足要求，但只有把程序执行起来以后，才会发现问题。比如初始时 `i = 0`，PC，Program Counter 在这里，程序是程序。执行起来以后，`i = 0`、`j = 0`，第一次循环可能是正确的。比如这里有个 `sum++`，第一次循环时 `sum = 1` 是对的。接下来 `i = 0`、`j = 1`，第二次循环可能也是对的，只有到 `i = 0`、`j = n` 时……哦，不对，看，我已经幻觉了，我也幻觉了，是 `i++`。它第一次循环就错了，是 `i = 1`、`j = 0`。

这个时候程序已经出问题了。为什么？因为要求是做一个二重循环，希望从 `i = 0`、`j = 0`，到 `i = 0`、`j = 1`，`i = 0`、`j = 2`，一直到 `j = n - 1`，再 `i = 1`，做一遍。所以什么是 bug？Bug 是程序的实现和 Specification 不一致。Specification 可能不存在，或者存在，但没有说清楚。所谓 bug，就是实现和真正的要求——程序到底要干什么——发生了不一致。

但从纸面上经常很难读出这种错误，尤其是安全漏洞、缓冲区溢出，很隐蔽，可能只是坐标算错，或者某个整数溢出了。我上课时讲过一个例子，两个人同时支付宝扣 100 块钱，如果用无符号整数存钱，从零块扣 100 块，就会变成一个无穷大、花不完的钱。

代码的实现和 Specification 不一致，这个时候其实已经发生了，我们叫它一个 Error，erroneous state。这几个词，Fault、Error 和 Failure，在中文里可能都是错误、失败、失效，比较难区分意思。在英语里，Fault，这个 bug，必须经过程序执行，才能变成这样的 Error。这时状态已经不对，明确有一个状态不满足 Specification。

代码有很多种执行，有的可能是对的，有的可能是错的。你可能做过单元测试，甚至把系统跑起来，看到航母上的飞机起飞了。在那条路径上，可能整个执行都是对的，都符合 Specification。只有某次具体运行时，看到状态错了，才触发了 Specification 的违反。

真正困难的是，发生 Error 是 silent 的，没有任何报告。它不会说“这个地方已经错了”，没人告诉你错了。CPU 是一个无情执行指令的机器，才不管是什么：这是 load，就 load；这是 store，就 store。它不断往后执行，`i = 1`、`j = 0` 等等。什么时候才知道程序出错？

只有程序运行了很久，运行了几秒钟，可能 `i` 已经变成什么，而这里还是零，你才感觉不对。这个程序在这次测试输入上应该 0.0001 秒就结束，为什么运行三五秒还没结束？这时才观察到一个真正的 Failure。

错误有一条传播路径，所以要心疼一下程序员。程序员写的是 Fault，但写的时候完全不知道。可能已经尽了最大努力，还是写出 bug。Bug 只有在合适的输入下才能触发。有可能上面还有一个 `if`，比较极端地说，如果一个随机数等于 1234567 才执行，那可能测试很多次，这段代码都不会触发。

所以首先需要一个合适的执行，能够触发 Error。即便触发 Error，很可能对最后的结果也没有影响。比如只是 corrupt 了栈上某个没用的地址。平时像 buffer overrun 这种安全问题，不用特别的工具检查，就算内存真的被覆盖了，也可能没有人用那块内存，它是空的，或者这次执行没有用到，整个程序的执行和输出看起来都正常。

所以，程序有 bug 不代表触发 Error，触发 Error 不代表能看到 Failure。软件质量保障中 Specification 和 Implementation 的 gap，是一个老大难问题。甚至最小心的程序员也会犯这样的问题。

很有意思，它起飞时运行了一段没有用途的对准代码，但浮点数转成 16 位整数的操作缺少越界保护，相当于那个整数溢出了，溢出后触发异常。这个 bug 肯定在代码里，但各种审计，反正最后没发现。火箭上天后，只有运行足够长时间才会遇到。我相信他们可能在地上做了一些测试，可能没做完整的模拟测试，肯定测试不够充分，没测出这种情况。

它往后跑，和这个例子有点像，要跑很长时间，直到 counter 溢出。Counter 溢出后产生异常。火箭有容错，整个系统不会 crash，有错误恢复流程。最后反正弄错了，错误的控制指令让火箭方向变了，最后炸掉了。

最有意思的是，主备惯性导航使用了相同的软硬件。它做了备份，如果有偶发错误，比如计算机计算不稳定，或者两个惯性导航读到的传感器数据不同，执行的分支也可能不同。结果它们几乎在同一时刻溢出、停机，真正导致了一个非常大的 Failure，非常严重。

所以程序员不是故意不维护 Specification 和 Implementation 的一致性，而是 Specification 本身不存在，或者不够清楚。哪一条 Specification 覆盖了“程序不应该 crash，不应该有任何浮点数异常”？也可能传感器真的读错了，或者发生别的事情，确实可能有异常，而异常要正确处理。

对于开放的软件系统，尤其与外部有交互时，Specification 到底是什么，并没有那么清楚。道理简单，实现非常困难。承认软件很困难，测试、调试、找到 bug 都很困难，才能知道怎样系统性地让软件质量变得更好。

讲任何软件质量保障的测试、验证方法之前，首先要知道，提高质量最有效的方法，还是更好的架构，使用不容易伤害你的编程语言，使用更加防御性的编程方法。架构和设计永远是决定软件系统质量的第一因素，而不完全是用了什么、写了多少测试用例。我相信，火箭上的软件已经尽了团队最大的努力，但依然不能消灭这些问题。

为什么用 Java，为什么 Java 这么快取代 C++，成为主流面向对象编程语言？因为它消灭了所有 pointer-based undefined behavior，所有 pointer 访问都是 defined 的。C 是指针一时爽，`*p = 1`，可以把任何整数 cast 成 pointer，再用星号 dereference。可以存函数指针，用函数指针实现面向对象。这个能力看起来给了开发者一个机制，同时也非常容易犯错。

指针可以随便指 memory，每个 allocation 都要有一个配对的 `free`，这也是一个 Specification。只要有一个 `malloc`，我知道你们不喜欢 `free`，对这个 `malloc` 的 Specification 就是：分配以后可能有很多执行路径，最常见的是 return 时忘记释放。Return 还是比较正常的控制流，甚至还可以 `setjmp`，有个 `longjmp`，再跳回去。它有无穷多条执行路径，要求在每条路径上，这个 `p` 刚好有一个配对的 `free`。

这就知道事情困难了，因为你们从来没有严肃想过，对一个 `malloc` 的 Specification 到底是什么。而且不只要求有一个 `free`，还要求 `free` 以后，这个 `p` 就再也不能存在。再 dereference `p`，就是 use-after-free，非常危险，因为别人可能会用你的内存。

比如浏览器，假设操作系统里有个 use-after-free 问题，操作系统可能把关键数据结构、用户页面分配到你持有指针的那块内存上。通过读取这块内存，就能读到非常敏感的信息，比如密钥。所以 use-after-free 是一种非常严重的漏洞。

这个 Specification 看起来容易：每个 `malloc` 必须有对应的 `free`，每次 `free` 以后就再也不能访问这个 `p`。就这一点，把所有信任交给程序员就不对，不应该把这种信任交给连 Shell 命令都会打错的人类。尤其系统复杂以后，控制流很复杂。同一个函数看起来简单，但如果有不同入口、不同调用方式，里面有分支，还可能返回不同地方，程序员自己也搞不清。

所以 memory error 成了人类研究几十年的问题：怎样在 legacy system，比如 Linux 内核里找到 use-after-free。到今天，依然可以做这方面的质量保障研究，比如去 Linux 内核里捞几十、一百个 use-after-free 问题。

Java 这种 managed runtime，牺牲一点性能，却可以保证不存在这种 undefined behavior。它仍然可能有空指针，就是那个 billion-dollar mistake。Tony Hoare 说自己发明了空指针，这是一个 billion-dollar mistake。Java 没办法阻止空指针，但空指针是 defined behavior。当你试图访问空指针时，Java 程序就 crash，或者外层可以把 `NullPointerException` catch 住，继续执行。

所以 Java 是一个非常伟大的进步，让这件事从 Java 程序员脑袋里永远去掉了，这是一个幽灵。我理解同学们是本科生，所有作业都允许出错，错了无非被老师扣点分，也许助教还看不出程序有错。但如果是给火箭写程序的程序员，显然不能对自己要求那么低。

当要求变成每写一个 pointer dereference 都要想到刚才那件事，甚至有一些 best practice，告诉你指针应该怎样用，`malloc`、`free` 应该怎样写，像 Linux 里的 `goto release`，用编程风格防止这种错误。这些是质量保障的内容，最重要的就是选择正确的技术路线。Safe Rust 几乎消灭了所有内存安全问题。但质量保障或者人类经验告诉我们，bug 不可能全部消除。

怎么办？今天主要讲测试，还是回到刚才的路线图，假设 bug 到处都是。当然，今天有一个可能立即从中获益的好方法，在 Agent，甚至大语言模型时代刚来时，就有人开始这么做。我现在非常确信，应该有人发大财了。

可以找一个成熟项目，再找一个像字典一样的 bug 数据库，把代码丢给大语言模型，说：“现在有一个项目，请帮我审查代码，我非常想提高它的质量。我知道世界上有一种 bug，叫 use-after-free，你能不能审查这段代码有没有 use-after-free？”当然可以把好几个问题一起 pick 起来，取决于想投入多大成本，找到多大的 bug。

你就用暴力的方法，让 Agent 去爆破现在的软件。你会发现，程序员没有那么多注意力，Agent 的注意力和能力远远高于世界上的程序员。就算程序员有经验，也没有办法百分之百避免，任何程序员都会写出这样的代码。哪怕是最好一档的程序员，因为他是人类，假设他还是人类，他都可能以某个概率写出这样的代码。当这种问题发生在需要特定条件的逻辑 bug 上时，你就可能找到一个漏洞。这是今天的版本答案。

你们也可以用这种方式。如果真的要写一个非常 safety-critical 的软件，你会希望有一个滑杆：拨到右边，就愿意付出更多钱；拨到左边，就付出更少钱。比如拨到左边，说：“你帮我看看有没有问题吧。”Agent 自己也会看。不要笑，比如让 GPT 写一份代码，再让 Claude 看一遍，它还真有可能找出里面的问题。或者让 Claude 写代码，让 GPT 看一遍，也有可能找到问题。这是比较轻量的。比较重量的，就是对照问题的数据库，让它更严苛地审查代码。

如果质量保障的目标是找到各种各样的问题，有没有系统化的方法？这些问题可能是这样的，也可能不是这样的，应该怎么办？这个循环里有两个链条，这就是理论有用的地方。看起来是句废话：Fault 要变成 Error，Error 要变成 Failure。但理论告诉你，从 Fault 到 Error 的暴露是有条件的，需要好的输入；从 Error 到 Failure 也是有条件的，需要好的检查。想增强这两件事，就要在这两个地方下功夫。

所以 Fault、Error、Failure 给我们的启发，first principle 是：如果想尽可能多地把 Fault 变成 Error，就希望 specification 尽可能完备。Specification 代表程序所有的执行都要满足某个性质。你要生成尽可能多的输入，覆盖 specification 的方方面面，才有可能触发潜在的、隐藏很深的 Error 状态。

同时，假设所有 Error 状态都能触发，运气最差的情况是一个 Failure 都没有。假设选择了一门永远不会 crash、没有 undefined behavior 的编程语言，或者没有用 memory，只有整数的数值运算，它就是不会 crash。但你没有办法检查输出对不对。

所以我一直说，很多算法题很难调，动态规划很难调，就是因为看起来样例对了，也可以生成很多测试用例，这非常容易。一个动态规划题可能输入一个整数序列：先输入一个 $n$，再给它 100 个随机整数。背后的测试用例也就是输入一个数，再有 100 个整数。但输入一串随机数以后，程序输出了 1384，到底对不对？它没 crash，输出 1383 对不对？你需要找到合适的检查。

这就有一点 art 的味道：你要知道在什么时候，程序可以做出检查。这个今天应该讲不到，因为我会专门有一节课讲各种检查，今天主要讲测试。

测试不用我多讲，你们都会测试，也都不会测试：你们都会运行一下样例，然后就结束了。它是最便宜的软件质量保障方法，因为运行样例很便宜。说到这里，又想到我经常上课会讲的例子。你们大一刚开始学编程，运行程序时，一定面对一个框框。不管是 VS Code 或 IDE 里面的终端，还是用更简陋的 IDE，弹出一个命令行、command line 的窗口，这时你会输入。你们是什么时候才摆脱往输入框里复制粘贴的？

刚开始学时一定是复制粘贴。复制粘贴了 100 次、1000 次、10000 次，终于意识到，可能是在上计算机系统基础课时，突然发现有个东西叫管道。所以可以写一个 build rule，或者在 IDE 里配置一个自动的 rule，使得按一个键就能自动完成编译、运行样例，或者运行自己写的测试数据。

这其实就是你们在大学里的成长。刚开始没有意识到这件事很重要，一旦意识到了，就发现质量保障流程被更好地加入了软件开发流程。顺着这个方向想，可以想到之前讲过的 CI/CD、持续集成：最好程序编译完，就自动运行一下测试。测试通过，什么也不用干；测试不通过，就报告。

我不知道你们有多少同学会用，这个技巧绝对有用。你们保研时还得机试，我估计机试在短时间内还不会消失。如果保研需要机试，做这样的自动化流程和脚本非常值得。花一分钟把编译和运行配置好，之后只管写代码。写完甚至可以做个 hook，保存后立即编译运行。如果运行结果正确，就比较方便，能省下很多宝贵的考试时间。这就是最便宜的质量保障。

但对于实际的软件系统，质量保障没有那么简单。实际软件不像动态规划题，specification 规定输入什么序列，再求序列里的什么东西，而是要在真实的软件环境里运行，得到真实的结果。这个结果还要符合我们对软件的定义：软件是物理世界的一个过程在信息世界里的投影。

这就麻烦了，因为你的环境不是别人的环境。能保证在 Windows 上写的代码，在 macOS 或 Linux 上还能正常运行吗？现在你们不谈这个问题了，以前我上学时会遇到。如果写网络编程，你们还会遇到：有些机器是大端的，有些是小端的。还记得吗？你们死去的计算机组成原理又开始攻击你们了。

如果有个 `int x`，在计算机系统里占四个字节，内存是一个数组，是一个 `int8` 的 `memory`，比如有 64 GB，这是 memory 地址空间的模型。内存就是一个数组，比如位置 1、2、3、4。一个 `int x`，比如 `0x12345678`，到底在哪里存？是 12、34、56、78，还是 78、56、34……？78 是一个字节。

如果用了一些位运算，做了假设，比如想取它的低位，可以模 256，这是比较安全、可移植的。但如果直接用位运算，比如 `& 0xFF`，假设它是小端的，去取它的位，就埋下了一个坑。到了大端机器上，这个程序就不工作了。所以在网络编程时，经常涉及大小端转换，`host to host` 这样的转换。

尤其在写 C 的时代，你根本不知道对面的编译器是什么、库是什么，很有可能在那个平台上不能运行。所以编程语言很大程度上解决了环境问题，JavaScript 至少让你不用担心对方是 Windows、macOS 还是 Linux。我在 Mac 上 vibe code 一个 three.js 游戏，在 Linux 上应该也能正常运行，基本上是正常运行。

这里面的问题非常多，以至于 Java 也解决不了。因为有大量第三方库，每个库的每个版本，行为都有点不一样。我记得有段时间，很讨厌 Python 里一个叫 lxml 的库。至今也能看到很多 Agent 使用它，它可以解析 XML。什么东西是 XML？Word、PowerPoint、Excel。在搞不定时，它就会去改 Word 的 XML，可以编辑你的文档，所以会用这个库。

这个库有过几次版本变化，处理某些 emoji，还是 Unicode 字符的行为变了，导致我原来能工作的程序 crash。但我的程序就是一个 `import lxml`，它的行为悄悄发生了改变，这也是环境的一部分。

真正的测试，说起来简单，就是在任何环境、任何输入下都符合 specification。光是运行环境，就足够你付出非常大的 effort 去探索。

而且，就算你的环境和别人的环境完全一致，从程序初始状态开始，后面调用的 API 也可能和别人不一样，或者两次运行就可能不一样。系统负载不同，程序执行的时间就不同。我们假设顺序程序没有时间轴，就是执行一条，再执行下一条。除了所谓 real-time、实时操作系统有保证以外，操作系统不保证：今天在 $t$ 时刻执行这段代码，到了 $t+1$ 秒或者 $t+1$ 毫秒，下一条指令一定会被执行。

虽然对于现代操作系统，你几乎会隐含地假设，程序一旦开始执行，隔一段时间一定会往前进。如果程序执行得太慢，可能触发 timeout 机制，或者队列满了。比如分配了一个有限的队列，程序运行得足够快，队列一直没满；运行得不够快，队列就可能满，扔掉一些东西，程序行为就不一样了。哪怕输入完全相同，时间不同，行为也可能不同。

网络延迟、中断，甚至线程调度，这就很恐怖，情况很多。我每年操作系统课都会讲一个伤人性命的并发 bug，这里不带大家看了。有一个放射性治疗仪，在并发时，你点得快，它的两个东西就处于不一致状态，造成过量剂量的照射。所以非确定性也是输入的一部分。

想在任何环境、任何输入下，用测试找到程序里的 bug，本身就非常困难。需要找环境、找输入，还要验证各种 functional correctness，这也很难。退一百万步，能够生成 specification 规定的输入空间里的所有输入，拿去跑，有时也不能说，这次跑出的结果到底对不对，和 specification 一不一致。

还有额外的要求，比如永远不能 crash，永远不能有 memory safety error，甚至性能、安全性要达到某些标准。这些叫 non-functional requirements，非功能性需求。在任何环境、任何数据下，都要符合所有这些要求。测试就难在这里。

正因为测试难，Dijkstra 在《The Humble Programmer》里讲自己的编程哲学时说，testing shows the presence。如果这个流程走通，能找到一个 Failure，确实就能让软件质量提升一点。但很可能永远都不能用 test 的方式来证明 the absence of bugs。

虽然刚才说了很多测试的困难，实际上测试仍然是非常有用的方法。怎么理解测试？刚才说的肯定都对：程序有各种小问题，要考虑环境、portability，考虑功能、非功能，甚至还要考虑 accessibility。如果真的要发布产品，它对听障人士和视障人士是不是友好？这些都有统一的国际标准，只有满足了某个标准，网页才能算对听障或者视障人士友好。

为什么大家还这么喜欢测试？如果把所有 specification、所有输入和环境都画出来，画成一个个点，实际上测试，尤其跑系统测试，关注的是最符合软件作为物理世界过程在信息世界投影的、最重要的那些案例。如果这些案例跑出来是对的，就给你一种信心：在正常情况下，至少应该有一定正确的结果。如果有错，应该是细小的，比如 typo、代码审查的错误，或者因为大脑的 self-attention 不够，导致一些细枝末节的小错。

而如果你对功能理解错误，不太可能跑了许多典型场景以后，结果还都是对的。这里基于程序是可以泛化的，你写程序天生就是为了泛化。理论上的最坏情况，什么样的程序能够通过 test case？比如对 `n == 1` 的输入专门处理。你们期末考试都干过这事吧？这种程序没有任何泛化性，只能 overfit 测试用例。

但正常人写程序是带着泛化去的，本身就带着整个需求说明书，因为你是软件工程师，收了钱，就是干这个需求的。程序天生能泛化，在典型场景下表现正确，同时又是为了泛化设计的，就 imply 你的程序至少在很大范围内，可能都能做对。

只是那些犄角旮旯，比如极限的性能场景下还能工作吗？并发调度器发生很大变化时还能正常工作吗？程序和其他程序交互，或者换到另一台机器上时，还能正常工作吗？这些案例缺乏测试用例，可能就没有信心。但因为程序能泛化，每当一个测试通过，都会感觉，很多相关的、能泛化的部分应该也能通过，这就建立了一点信心。

所以，虽然刚才把测试说得很绝望，测试永远只能 shows the presence，not the absence of bugs，但它还是在不断增强你的信心。

而且，尤其是失败的测试，提供了非常有价值的反馈。它告诉你，这个测试错了，运行到哪里时错了。这时就可以回到这个循环上。测试能告诉你，程序里存在一个 Fault。根据 error message，比如正好有一个 null pointer exception，通过 exception 的 call stack，就知道大概率和空指针那一行附近的东西相关。

如果有一行代码出现 null pointer，一般来说，你不太会把一个东西存进去，很久很久都不用它，直到经历了非常多代码后才暴露。也有这种 bug，但相对少。更多的是有个地方写错了，有个数值算错，很快用到它时就立即暴露问题。

所以测试的 Failure 不仅能告诉你存在一个 Fault，而且有点像告诉你一个条件概率：已知有 Fault，并且看到这样的测试 Failure，就可以更好地猜 Fault 在哪里。有些部分就排除了，它可以帮助排除很多与这次 test failure 无关的部分。

有了这个 test，还可以逐个检查每个状态是不是 Error。调试的理论告诉我们，可以二分这个 trace。假设状态一旦出错，后面就一直带着错，就可以二分找一个位置，看现在状态是不是对的。如果对，就往后找；如果不对，就往前找。找到第一次进入 Error，从看起来正确的状态，到下一次错误状态时的代码。

Everything is a state machine，还是 state transition，你总是从一个状态到下一个状态。从对的状态到错的状态，那个代码应该就和 bug 相关。看这个例子，代码做了什么？把 `i` 从 0 变成了 1，但我想要的是把 `j` 从 0 变成 1。所以这个东西错了，`i` 的状态错了，修改 `i` 的语句错了，正好就是 bug 的 root cause，把它修了就修好了。不是百分之百，但很大概率，失败的 test case 会给你很多有用信息。

这里又有一些有意思的论文。你看，这是 2024 年，arXiv 上 2405 的 SWE-agent，在 Claude Code 这个产品开始设计之前。所以我相信，Claude Code 肯定借鉴了这些文章。这很早，2024 年，GPT-4 展现了很强的能力后，大家突然发现，能不能让 Agent 试一试？于是有很多这样的工作。

结果首先一定是正向的。它可以通过 ReAct Loop，比如把测试用例运行失败的结果告诉 Agent，Agent 再修改 patch。随着尝试数量增加，它能够修复问题的成功率确实越来越高，虽然还达不到今天的效果，但非常有前瞻性。

其实当时我们也不知道谁能成功。我那时看这个工作，并不是特别看好。我觉得那个时候还没有看到 scaling law，没有 scaling law 的 vision。但相信这个 vision 的人，会赌有一天这条曲线随着模型增长不停往上，scaling law 还没有到头。那时做 Claude Code 的人赌，他们能训练出更好的 coding 模型，通过强化学习和后训练，越来越好地从一个 test fail 找到哪里出错。

大模型就是一个概率分布，可以不断通过强化学习，让它越来越接近正确的概率分布，理解测试和调试的过程。这一切都是数据驱动，完全透明的。

这是测试。在大模型之前，软件工程领域其实已经对测试了解得非常明白：测试得从局部到整体做。这非常 make sense。想想做 OJ 题时，每道题都只做 system test，或者验收测试：把动态规划题一大串输入拷进去，看结果对不对，这是一种 system test。但 bug 可能是非常低级的小错误。

理论上，如果有一百万行代码，每个小模块都能单独测试，小模块里的问题就可以立即暴露，不需要 system test 去暴露非常简单的小问题。System test 应该暴露的是几个模块接起来以后，协同工作的机制正常不正常。不应该用 system test 去测试小模块的功能。

虽然人都有这种倾向，喜欢偷懒，就想把整个东西跑一遍再看。今天模型也会偷懒，为了更快完成任务，它觉得有自信时，跟人一模一样，一把梭两三千行代码，也不写任何 unit test，然后就跑 system test。它认为 system test 跑完，这个东西就对了，一把梭就完了，甚至没有留下任何测试用例。它截个图看一眼，说：“好，给你搞定了。”

但真正做软件工程时，做单元测试的成本更低。用一次 system test 去发现一个 unit test 就能找到的问题，肯定浪费更多的钱和时间。

测试还分黑盒测试和白盒测试。做 OJ 就是非常典型的黑盒测试，只管程序输出对不对，或者一些可观测行为对不对，最后有没有 hang、有没有 timeout，这都是黑盒测试关心的。如果一切正常，就认为至少这次测试通过了，对这个测试附近的输入也应该有一定信心。因为程序能泛化，相信类似的东西可能也能做对。

还有一系列测试方法，比如在各种容易出错的边界值上测试：数组长度的 0、1、允许的最大值，决策表、转换表等。你想让测试越来越充分。测试的本质是有一把枪，每次生成一个测试输入，相当于可以打一颗子弹。子弹要钱，设置好的测试用例，像 unit test，子弹成本比较低，可以多打一些；system test 成本比较高，就少打一些。最终要打到输入空间，或者程序所有可能运行空间上足够多的东西，使你建立对软件还能正常工作的信心。

后来就有更多自动化方式，比如从代码出发。程序运行一个测试后，就得到这次运行的所有覆盖，或者说碰到的所有语句的集合。程序就是状态迁移，每次从一个状态到下一个状态，就执行一条语句。比如 test 1 执行了第 1、3、6 行，test 2 执行了第 1、3、9 行。所有测试都跑完，发现第 7 行从来没覆盖过。根据计算机系统公理，未测代码永远是错的。如果第 7 行有不能编译的问题，编译器可能帮你找到；但如果在第 7 行写了这么一个东西，对不起，至少你没有建立对第 7 行的信心。

所以希望有各种覆盖：语句覆盖、分支覆盖、路径覆盖。希望所有语句至少被一个测试用例覆盖，所有分支条件的两个分支都要覆盖，甚至有些路径，比如循环一次和两次都要测试到。因为 `for` 或者 `while` 循环，循环一次和两次确实可能导致不同结果。

有个经典的测试工程师笑话，反映了我们对测试的理解。不过今天，生成各种测试用例对大语言模型已经比较简单。你们现在知道测试的概念和 first principle，就可以为项目许愿：“我现在要给这个项目构建测试套件，请构建合适的单元测试。单元测试完了以后，要统计覆盖率，对没覆盖的代码报警；或者不断添加单元测试，直到覆盖率达到百分之百。”

你只要许个愿。以前只有大公司，或者真正严肃的软件项目，manager 才会提出这些要求。其实这是很大的 overhead，人很难受，写完代码必须写测试用例。但有时一个测试用例真可能救你，因为程序会组合。这次看起来代码没问题，没覆盖好像也没什么，但别人调用时，另一条路径上真可能出错。所以这些防御性的指令都有道理。今天许愿就行，有了概念，就说测试要做到什么。

这个笑话总结了软件测试经常遇到的问题。一个 QA engineer 进入酒吧，先点了一杯啤酒，又点了零杯啤酒，再点了 99999999 杯啤酒；然后点了一杯，点了一个蜥蜴，再点了一杯啤酒，又点了一个奇怪的东西。酒保应对自如，测试工程师高兴地离开了酒吧。

第一个顾客来到酒吧，问洗手间在哪里，突然酒吧就开始崩塌、起火，程序 crash 了。它说的是什么？测试工程师的准则肯定对：没测的代码肯定不对。比如一杯啤酒，都是点一个东西，测试的都是 order something。

当然，order something 也有好和不好。显然这还是个非常尽职的测试工程师，测了这些边界值。你们写的程序很有可能一杯时就出错。GPT 写的程序又会有过度防御性，写大量检查。这些检查对你可能也不必要：所有不合法的，统一扔一个异常可能就好了，它却一定要把每个不同异常分开。

他测试了点某些东西的情况，在这里打了很多子弹。但程序输入空间可能非常大，还有没考虑到的情况。所以对于整个测试空间的信心，是建立在物理世界过程在信息世界投影中，可能遇见的各种情况上的。

这是软件工程里讲的测试。我自己是专业做测试的，他们说得都对：大量快速的单元测试，适量集成测试，少量端到端测试。这取决于你有多少钱，成本有限，子弹有限。

在合适的时候，你就可以用 stub 或者 mock 来替代一些真实场景里面会发生的事情。你的软件可能必须在真实系统里面才能运行，比如要 get time，或者 read 一个文件，receive 一个 packet。比如你做了个视频直播机，要给智慧教室开发软件，可能会 receive a packet，得到摄像头发过来的数据。这就麻烦了：必须要有个摄像头，才能做系统测试。你们作为初级软件开发者，就会很不情愿做这样的测试，因为麻烦，costly，连接它又需要时间。

这时软件测试的经验就告诉你：需要 mock 它。可以做一个假的设备，不断给你供图像。比如 Android 的虚拟机，我们做安卓开发时，哪怕没有安卓手机也可以开发。它有个 AVD，Virtual Device，这个 Virtual Device 就有 mock 的摄像头。后来到某个版本时，就可以真的给它传一个视频了，但最早打开摄像头时，永远只能读到一个静态的数据。这可以使很多需要摄像头的应用运行起来。有的应用要获得摄像头权限，打开摄像头，拍张照片，再关掉摄像头的权限。如果这样的代码没有真机就没法测试，显然不是一个合适的 practice。AVD 帮你做了这样的 mock。

理论上，你只需要知道：我们需要做尽可能好的测试，尽可能把每一份成本最大化地变成对正确性的信心。还有一些理论，比如 regression test，回归测试。你每改过一个地方，原来测试对它的知识就不成立了。这行改过了，所有和这行相关的测试都要重跑，从单元测试开始，一点点建立对软件的信心。

这是软件工程课本里面的内容。这个 section 是我让 AI 给我生成的，连这个笑话都是因为我记得它，所以让 AI 直接帮我生成这个笑话图。但是真实软件系统的测试，我不是这样理解的。我理解的是：你只要记得这个图，从 first principle 出发就行了。

现在许愿编程的时代来了。比如我前两天就许愿了一个 UI，仿照 Apple Watch 的小界面，是一个 ESP32 的小设备，里面有节拍器、To-do List，还有可以和 AI 聊天的工具，给小朋友做的。我就许个愿。我们一天到晚都在许愿，比如我昨天许了这个。

DeepSeek Harness，不是……用我的，应该是我 macOS 上的。效果还是很不错的。稍微有点卡，我不知道为什么，但这不重要。

我们来看一下 Agent 做了什么。这里有 Agent 的 trajectory，从中看到它做了不少测试。我觉得每个同学回去都可以学到这个技能：当 Agent 干完以后，可以让它帮你复盘，看看做了什么。有些东西可能能够沉淀成你自己喜欢的 skill。我是在自己的 Mac 上面 Vibe 的，放到 Linux 上面完全可以运行，而且感觉体验没什么区别。

它开始做，有很多 bug，写的时候就不停修复，也写了很多测试：写玩法脚本，跑 12 秒看 AI 交火，写多机位截图，写测试检查。它做了大量截图，最后截到每一个 response 50 兆，直接给我 413 了，Agent 已经跑不下去了，必须再开一个新的 Session 才能继续跑。

你看，又是看截图、测试、修复。Agent 已经进入一个非常低效的循环。基本上我觉得在前五六十轮，就已经搭出一个可以玩的东西了，有比较多的修复。修完以后，后面就是检查、写测试检查。这基本上已经不是 bug 了，是因为我自己启动了一个实例。这是它中间截图的检查，看起来做了非常详尽的测试。

但是实际进入游戏以后，我的肉眼就立即发现了一些问题：这个漂浮的旗子。我昨天试玩后还发现很多问题，比如栏杆是可以穿过的。也没有多么恶性，这个人感觉像浮空的，切枪的动画好像也有一些问题，但这不是很重要。

当然，我没有任何提示，就说要做一个什么样的 CS:GO。你看到 DeepSeek Flash 真的是后训练仙人。比如上一个版本的 DeepSeek Flash，绝对做不到这个效果。突然间大家发现 GPTSTRA、像 office5.5，对审美有了自己的要求以后，所有家的模型都学会了。无非就是你有视觉能力，有美和丑的判断：这是太简陋的，还是精美的？不停用精美的去奖励，强化学习模型就能学到：我多做几步，应该能做得更精美。这个游戏，尤其所有素材都是 Agent 生成的，效果还是相当惊艳的。

Prompt 我回去整理一下吧，这台电脑上应该没有，不在我的 Session 里。你想知道我的 prompt，大概就是“要实现一个相对比较精美的 CS:GO”，最多一句话。我没给任何东西，真的什么也没有，而且是一个基本没有 skills 的 pi。它做得还是不错的，但是你也看到，充满了 bug，这个质量显然不能交付。相比之下，我这个 ESP32 的东西，当然可能更简单一点，但交付质量相对要高很多。

对我来说，谈软件质量保障，其实不是说要做多少测试，而是你的软件系统越大，做一次系统整合测试的成本就越高。很多问题几乎一定必须用整合测试，或者跨模块边界一起协作，才有可能测试出来。所以真正的软件质量保障就这一句话：架构决定了质量。

你的软件里面有好几个部分。比如我要做一个智慧教室的人脸监控、到课监控，这是最近最热的话题，但好像不是我们学校，我没有收到任何官方消息。我打个比方：如果要做一个 Event Bus，这个是适合用延缩型的，那我一定要把人脸模块和到课模块的接口分得非常开，使每个子系统都可以单独测试，单独对它有非常好的信心。

我希望对一个人脸模块，可能有一万张或者一百万张的 benchmark，在这些人脸上几乎都能达到很好的效果，而且不出任何问题。对各种输入格式、输入帧率，都能达到性能预期，这是人脸模块。人脸模块和到课模块之间，可能只有一个接口：不停把人脸向量传到这个模块里。到课模块的正确性，就是输入任何向量数据，依然能够产出正确结果。最后可能还接到 Event Bus 上。也就是说，每个模块的接口都非常清楚，每个模块都可以在某种意义上单独验证，这就需要很好的架构。

因为我没有给它任何提示词，这个游戏引擎就是它自己做的。我们来看一下：“为什么我观察到了浮空箱子、穿过……”我可以这样问它，问它是不是有设计的问题。它肯定有设计，但我相信应该不是一个为了质量优先而做的、非常好的带物理的游戏引擎，因为我只是让它做这个。如果要我来设计，我一定会设计成所有物体、所有部分都能单独用代码检查，不需要截图。它从某一时刻开始，就疯狂截图了。

让它直接下个结论。你看，它是一个 three.js 加手写的极简 AABB 物理，没有碰撞。没有碰撞不要紧，我依然可以用建模的方式告诉你：栅栏不能穿，箱子不能过，墙就是不能过，而且子弹也可以打到墙上，这才是正确的。但因为架构的问题，有些东西是硬编码出来的，比如箱子是硬编码拿出来的，所以很容易出错。而且必须做大量截图，才能修复这些问题。

我举一个有点意思的架构失败的例子，是我童年回忆的一个老游戏里会发生的现象。当我把基地收起来之后，你会发现基地突然消失，变成了一条狗。这个游戏里面有无穷多的 bug，而且很多是后来才被开发出来的，包括船厂可以修飞机、维修厂可以卖步兵。在游戏引擎里面，你不能想象这种情况。

“如果说这个单元格上，在基地收起来之前，就已经有单位在这里，这个 bug 是这样产生的。理所当然，我们可以想到，基地就会因为这个单元格被其他单位占据，导致自己直接卡没。怎么办呢？有对面的工程师来，防守的话就不会出现敌人工程师已经半只脚踏进我们的基地，然后狗再把工程师咬死的情况。这个时候你会发现，狗直接卡在基地中间。恰好它卡的位置，就是基地收起之后出现的位置。我们把基地收起来之后，你会发现，我的基地直接被狗吃了。”

一些非常有意思的 bug。这个游戏最后会有各种匪夷所思、你不能想象的 bug，是因为引擎里面硬编码了很多东西。比如假设地面有层，用 2D 模拟 3D，每个单位有一个高度。引擎设计之初，并不是说对于任意可能的游戏进展都某种程度上对，那这个设计好像就会崩溃。

今天是 Agent 的时代，你们许愿编程时，当然可以用我们之前说的软件工程 practice：每个地方都要做单元测试，覆盖率达到 100%；单元测试完了，每个模块互相集成，也要用代码测试，不能截图；最终验收时要跑出轨迹，要截图，确保看起来一次真实游戏是正常合理的。但是即便做了所有这些，只要架构没设计好……你看到我们说从 intent 到 spec 到 implementation，这个金字塔会漂移，从第一节课我就开始讲了。当 design 没做好时，项目就直接引向某种程度上万劫不复的深渊。

当然，你们现在是本科生，最重要的就是试错。去 Vibe 很多东西，看着这个屎山最后是怎么倒塌的，回头再想：原来老师上课讲了，真正决定质量保障的是架构。所以重构才是改进代码质量的最佳途径。

为什么我们喜欢 functional design，喜欢函数式编程？就是因为 pure functions。你随便写一个函数，只要引入一个全局变量，比如有一个 `foo`，有一个 `global.get`，过一会儿再 `global.get`，写出这样的代码，程序的正确性就要求：对于所有可能的全局状态，里面所有执行路径都正确。它会隐含地引用全局状态。

这意味着，如果是一个 CS:GO，你可能需要把全局状态构建出来，或者 mock 出来，才能测试这个函数。这就是成本、代价，虽然可以让大模型做，也是需要付出的成本。一旦涉及全局状态，会不会跟人并发？中间会不会有人改掉，在两次 get 之间改掉了？全局状态有哪些可能，哪些状态可能、哪些不可能，需要考虑到什么程度？这些都是测试这个 `foo` 时要想清楚的，是很大的思想负担。

但如果是一个 pure function，所谓纯函数就是数学上的函数，没有任何副作用。输入 `x`，只要 `x` 不变，输出永远不会变。只要写这种 functional code，这个函数就非常好测试，正确性完全由自己负责。理论上，只要有足够的单元测试，就可以保证 `f` 的正确性，甚至可以更容易地证明 `f` 是正确的。

比如 Rust，为什么我们喜欢 Rust？不完全是喜欢它那个非常恶心的变量生存期，而是它会强迫你重新思考：什么样的状态要放到全局去？因为它那个非常恶心的编译器，会使你不由自主地倾向于写出 functional design，或者正确性非常显然的代码：我把对象 hand off 给你，你再还给我；或者一些比较常见的模式，比如用 reference count 管理全局变量的生存周期。这些代码更容易测试，更容易保证正确。

当然，functional design 不是万能的。很多时候函数需要组合，就会写出 higher-order function：这里传一个函数，返回一个函数，甚至返回一个 lambda。当它变成 higher-order function 时，就和其他函数的 specification 产生关联：这个函数到底对谁负责？我返回的这个东西对谁负责？负责的 scope 有没有改变？Functional design 不是说什么问题都可以解决，但是平时写代码时更 prefer 这种设计，就会获得一定收益。

所以对我来说，第一最重要的原则就是架构决定质量。只要架构做好，剩下只需要把软件工程教科书丢给 Agent，它就能做好。除此之外，质量保障和任何编程一样，都需要一点灵光一闪。当然架构本身也需要灵光一闪，需要一点品味，这是现在 AI Agent 还没完全学会的东西。我相信，软件工程教科书已经有这么多了，理论上说，应该是这个反馈回路比较长：只有当屎山堆起来以后，才能理解好架构的好处。

如果像 DeepSeek 刚才那样急速堆屎山，代码生产效率随着需求增长，大概是这样的：到某一刻就维护不下去了。如果有好的架构，开始时效率可能比较低，因为搭了很多脚手架，做了很多验证和测试。只有到很晚时才可能超过它，并且有持续增长的潜力。所以反馈信号来得比较晚。对强化学习来说，毕竟完成任务就得到奖励了，所以你会看到，现在 DeepSeek Flash 会像刚才那样选择：“我不管了，反正你要我就给你，就这么地吧。”

我举几个例子。其实所有理论都是失效的，在测试或者质量保障方面，只要有想法，就可以去许愿。比如我们许的一个愿是 differential testing。教室里有多少同学做过这个实验？计算机和 AI 会做，软院好像不做。还记得折磨大家的 NEMU？你们要写一个 RISC-V 或者 x86 的全系统模拟器，一个虚拟机。这个虚拟机真的带声音、带图形，什么都有，是一个完整的计算机系统。

我可以讲点故事。大概 2013 年的时候，余子濠同学在毕业设计里实现了第一个版本的 NEMU，并且光速把它变成第一年计算机系统基础的实验。你就知道，同学们一定一片哀嚎，因为想把它调对，简直……没有人做过，只有余子濠手上有一个可能也不是 golden version 的版本，可能也有 bug。但它至少能工作，能向你展现《仙剑奇侠传》，所有固件都打好了，请你运行它。同学们在没有任何辅助的情况下，一定惨不忍睹。

大概某一年，2013、2014，可能 2014、2015 年的时候，我在计算机学院楼下的咖啡厅聊天，说同学们苦不堪言，让我们许个愿。当时许了几个愿，这些架构现在都已经实现了。我向余子濠许了个愿：CPU 可以像动态链接库一样，就是一个接口。总线接口、一个握手协议，加上总线数据进出、一根中断线，代码上的接口也要表现成这样，CPU 就可以插拔。

插拔完以后，我有一份 memory，core 和 uncore 是分开的。Uncore 的外设模拟，可以在上面挂两个 CPU。同样的状态，往这送一份、往那送一份，但是接口的输出只保留一份，一个周期。当时选的是 QEMU，可以把 register 和内存状态往 QEMU 里面一放，让 QEMU step 一条指令，再把结果 dump 出来。那时候是 x86，现在 RISC-V 的架构稍微有点不一样。有同学应该做过 x86 版本，那个 x86 QEMU 就是 golden version，什么都能跑，能跑一个 Windows 虚拟机，它就是对的，或者我们就相信它是对的，只要跟它做到百分之百一致就行。它跑一步，你跑一步。

自从有了这个机制，找 bug 就太容易了。为什么？还是这个调试理论。你有一个程序，跑完看起来是对的，但是如果 EFLAGS 有一个差错……有一个 flags 寄存器，比如上一次运算结果是不是零，有个 zero flag。还有一个叫 parity flag，你错了，但刚好测试蒙对了一条。如果测试指令只有一个测试用例，unit test 刚好蒙对了，或者两条指令组合时弄错了，你是不可能把复杂程序调对的。两三千行代码也不算多，每条指令看起来都一样，怎么译码、行为是什么，再执行它，你不可能找到。

但是 differential testing 可以提前暴露问题。你看，所有东西都在这个调试理论里：它可以最大化地暴露程序里面的状态。比如现在有 EAX、EBX，还有 EFLAGS，这些都是你内存的状态。曾经你不知道它对不对，反正算出一个值，没 crash，就只能假设它对。但如果有 golden version，我说你这个 EFLAGS 算错了，你马上就知道上一条指令哪里算错，查一下手册就可以修复。

用这种方式找编译器的 bug 也可以，但编译器稍微麻烦一点。比如 C、C++ 有 undefined behavior，有未定义行为的程序，执行结果就可能不同。同一个程序用两个编译器编译，输出结果不一样，不代表编译器有 bug，也可能是程序有 undefined behavior。所以这变成了一个带条件的生成问题，会稍微难一点。

昨天我突然看到这个朋友圈，致敬了一下。包老师不知道，这个 differential testing 是当时我们一起聊天时许了一个愿做出来的。当然 QEMU 的实现是余子濠实现的。当时聊了一下，回去他就去实现了。最早设计不是用来打龙芯杯比赛的，而是用来拯救大家计算机系统基础课程实验的。2019 年被用在第一期“一生一芯”里面，然后不断改进。今年他们拿到一个非常快的、可以上 FPGA 模拟的版本。刚才说模拟 CPU 执行，可以用软件模拟，也可以用硬件模拟，来加速 golden version 的比较。

还有很多你们能想到的。比如测试是遍历输入空间，有没有可能写一个程序自动遍历？这不就是搜索问题吗？假设你们写一个有命令行的程序 `a.out`，打个比方，跟四个参数 `s1`、`s2`、`s3`、`s4`。还可以有一个环境，比如允许 `s3` 等于 `a.txt`，并且有一个 `a.txt`，内容是 `s5`。无非就是搜索五个字符串，或者五个字节序列。比如 `a.txt` 小于等于 100 字节，每个参数小于等于 10 字节，就可以把 `a.out` 的所有输入编码在一个 140 字节的输入序列里。如果能把这 140 字节的所有空间全部遍历，就能达到完整的输入覆盖，所有程序行为至少都跑过一遍。对不对另说，但都跑过一遍了。

这个过程很低效，怎样有一个更高效的搜索过程？用你们学过的遗传算法，维护一个种群。这也不能算遗传算法，就算一个 iterative search，我现在不能确定到底叫什么比较好。可以维护好多个这样的输入，每次把输入变一下：把一个字节 A 改成 B，或者把程序里面有的常量替换进去。对探索测试空间可能有效果的操作，都改一下。或者把两个输入做一个 crossover，把这个前一半拼上那个后一半，确实有点遗传算法的感觉，又得到一个新输入。这样不断生成新的输入。

什么输入比较好？覆盖了以前没覆盖的代码的比较好。可以有一些反馈，这整个叫反馈制导的。此时就疯狂搞一个 100 台服务器的集群，没日没夜为软件生成测试用例，看有没有安全漏洞，当然也可能有功能性的新问题。这个非常有效，比如 Linux 内核的 syzkaller，已经找到非常多的 bug 和安全漏洞，而且很多 bug 现在没法复现，可能修都修不了。

甚至如果要在开源供应链上投毒，也必须想办法绕开每天的 OSS-Fuzz。开源软件不停发布，但发布出来不会立即进入下游，这太危险了。除了开发者自己要做以外，第三方也不断扫描漏洞，fuzz test 这个软件。直到 fuzz 通过，你看到日志：测试了多少时间、多少用例，都没有问题，就可以一定程度上对 release 有信心。如果要供应链投毒，就要想办法把 fuzz test disable 掉，或者 hack 一部分功能才行。

所以在生成式软件工程时代，你们更多需要的是知识，knowledge：架构、测试的基本理论原理，再结合你的经验，看过的软件系统，别人 30 年里到底怎么做软件质量保障。学会了，就可以 generalize 到自己的项目。自己的项目未必是一个 differential testing、DiffTest，也未必用 fuzzing，但会给你一个启发：也许确实可以写一个更好的、定制的测试输入生成器，覆盖很大的测试空间。

把这件事情想清楚以后，你可以许愿。现在 AI 可能还干不到你认知之外的事情，尤其你们学这个领域，作为领域专家，它还干不了你认知之外的事。所以你需要为 AI 提供一个认知。

比如我很喜欢《Android》里面讲安卓初创团队的这个例子，也是许愿。我们做 differential testing 也是许愿，San Mehat 就向同事许愿：有没有 a little bot to control how it goes in and out，然后接一个 little closed-loop test？他们发现 G1 的 SD 卡插槽，Linux 驱动不太稳定，后来甚至整个重写了。驱动不稳定需要测试，但没办法，就算在 QEMU 里面模拟通过了……那个时候 QEMU 还不够成熟，零几年的时候，可能效果也不够好。

所以他们就做了一个这样的物理物件，不完全是 3D 打印，有部分是 3D 打印的，可以插拔 SD 卡。软件可以给舵机送一个信号，拔出来、插进去，软件就可以去测。

今天我们也是许愿，许愿编程。这个是我家小朋友的设计，许愿许了一个光栅画。你们可能看不清楚，拉动时它是一个动画效果，把四帧动画拼起来，全部自动。只要有一个四帧动图，就可以拼成这个。卡扣已经在我这里，钥匙扣扣起来了，拉下来就可以换一张 5 cm × 5 cm 的照片。

现在所有东西都是许愿，但是许愿的前提是你有正确的概念。好，今天下课。
