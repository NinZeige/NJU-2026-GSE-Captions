我们说，软件是物理世界过程在信息世界的投影，你们看到的一切都是软件。在软件世界里，最上层有一个 intent，这个 intent 可能很模糊。比如领导说：“我要做一个好的教务系统。”但当这个软件真正要被构造出来时，我们就要从 intent 到 spec，具体到这个软件到底要构造成什么架构、长什么样，最后有一个 implementation。

如果这个 intent 和人类没有办法完全对齐，其实人类和人类也没有办法完全对齐。以前就有这种笑话：“就差一个程序员了。”一个商学院同学说：“我们有个很好的商业模式，邀请大家来入伙。”他就有个 intent，但他要做什么，其实他不知道。如果你也是一个毛头小伙子，做了一个不太好的架构，最终这个 implementation 可能就会偏移到很多地方。

所以这就有了软件工程。软件工程是在不停失败的过程中积累的各种经验，我觉得主要有三个部分：经验、流程和工具。

首先是经验。比如《人月神话》，第一件事就是先要认识到，软件是非常容易失败的。软件不是我们拍个脑袋说“就差一个程序员了”。随着软件规模的增长，或者需要管理的团队增大，软件越来越难构造。构造一个十万行的软件，肯定比构造一个一万行的软件难不止十倍，可能有一百倍，甚至更难。

在不停失败的基础上，大家还总结出来，比如应该怎么样设计软件架构，怎么设计模块之间的边界，甚至有很多失败经验，告诉我们源代码应该怎么写。我不知道你们第一门学 C Programming Language 的课，有没有讲过类似的 coding standard。这里就有一个，你看，这是 CMU 的 Software Engineering Institute，很早就发布了 SEI CERT C Coding Standard。它告诉你，各种地方应该怎么写。

随便点一个，我也不知道会有什么。比如 floating point，随便点一个实际上有的。这是一个，它说：“Don't assume numeric values for expressions with type plain character.” 它告诉你写成什么样是 portable 的，要担心哪些问题、怎么样使用各种运算符。这里有很多正例，我就不展开讲了。

这些都是因为大家发现，人类，human programmer，很容易在一些地方犯错。他们从人类世界里总结出来：代码应该这样写，就可以减少犯错。在整个软件工程里，各个方面都有很多经验。比如需求文档该怎么写，文档和代码怎么样对齐、一致。现在就算进入 Agent 时代，你也经常会发现，你让它去改个东西，Agent 很开心地把代码改了，文档旧了。两边不一致时，下一次 Agent session 比如读了文档，没有读代码，你这个项目就会不停失败，Agent 要改很多轮才能帮你改对。

除了经验，我们还总结出了造软件的流程。从最早被批判的瀑布模型，到现在用的敏捷开发，以及我们也讲过，每次 commit 之前都必须做检查，push 以后最好还做更多检查，等等。

今天我主要讲软件分析工具。实际上，软件工程里的工具很多。我们在课的一开始就讲了版本管理，因为做任何软件工程项目，首先需要管理一个 repository，它要随着时间往后演化。如果要编辑这个项目，你就需要一个 IDE，或者今天的 Agent harness。要让项目运行起来，就需要编译器、编程语言、框架、调试器等等。

今天我要讲的是另外一大类工具：有没有可能把软件作为输入？我们软件工程师说，我们的 intent 可能是造一个教务系统，或者造一个直播管理系统、录播教室的系统，有很多这样的需求。你们每个同学都会有很多想做的东西，有这种冲动，想做一个小的 side project，它就构成一个需求。但软件分析稍微有点不一样，我们的 intent 来自什么？我们说，有没有可能有一个 software，这个 software 的输入也是一个软件？它可能是一个 `.git` 的 repo，甚至就是一个 `.c` 或者一个 `.typescript`，它可以输出一些对程序员有用的结果。

理想情况下，比如输入一个 `.c`，它能输出：“这个程序可不可能有 bug？”这不就是你们在编译器或者 linter 里，在 IDE 里写完一个程序时，它给你一个红红的波浪线？这就是软件分析工具。

这样的软件分析工具，其实有一种 recursive self-improvement 的感觉。在软件工程实践里，这件事情对大家是天经地义的。你们甚至都没有感觉到：“我需要在 VS Code 里再 load 一个插件，能够帮我检查更多代码里的 misuse；我应该再加载一个插件，它可以更好地可视化 unit test 的结果。”这样，我可能可以做一个流程，在 build 时自动做 unit test。做完以后，可以看到勾和叉，可以快速地点到 failure 的 test case。

当然，好像现在 Agent 时代，这些事情你们都不 care 了。在经典软件工程时代，大家还会一直想：“有没有可能再构造一个软件，去改进已有软件的开发体验、测试体验、调试体验、维护体验等等？”所以我觉得，这是一种很有意思的人类 recursive self-improvement 的历史。因为软件工程是离开发者最近的学科，我们作为开发者，每天就在这个流程上不断 battle，就会想，有没有可能自己改进自己的工具。

这样的例子也很好玩，蛮多的。比如编译器的自举，你们有没有好奇过？听说有些 C++ 编译器是用 C++ 写的，或者 C 编译器也是用 C 写的，那不就自己编译自己吗？这也是另外一种，不能算 self-improvement，也能算吧。但一开始，你的 C 编译器没有办法用 C 来写，只能用别的语言，比如汇编语言，直接写二进制代码、机器代码。至少可以编译一个简单一点的 C 的 subset，然后用这个 C 的 subset 再写更复杂的程序。比如今天完全就是 GCC 用 GCC 自己编译，是自己改进的循环。

刚才说，软件工程有三件事：经验、流程和工具。我们的开发者，除了做码农，总有一些不安分的码农会跳出来想：“我能不能 improve 一下，把我的经验变成一个工具，放到流程里？”这很自然。你又看到，我们 IDE 的插件、软件的生态在涨，编程语言在进步，各种工具被集成到 IDE 里，开发和调试时可以更方便。

这有点像今天 Agent 时代的 RSI，只不过我们把主角从开发者换成了 AI Agent 和模型。在这个 self-improvement 里，软件开发者想要变成超级开发者，造出超级开发者。每当造一个工具，我就会学会这个工具；学会以后，我作为开发者的效率提高了，就可以更快地生产软件，生产更多工具，再提高效率，直到不能再提高为止。你看到，这和我们对 AI 想象、想要的 self-improvement——我觉得这图画得不是很准——非常异曲同工。

现在 AI Agent 可以自己造工具了。以前 AI Agent 只是可以完成任务，比如帮你实现一个前端。现在大家很喜欢的，什么鹈鹕骑自行车，反正就是生成一个 Three.js 的 3D 世界，在里面玩生成 3A 大作的游戏。

但实际上，AI 已经到达这样的临界点：它足够 powerful，不仅可以从一个需求产生实现，而且我们的 AI Agent 现在有能力理解自己，自己到底哪里出问题了。就像软件开发者，软件工程不断总结出各种经验：也许不能让开发者随便使用指针。如果使用指针，或者使用 `malloc` 和 `free`，就非常容易搞坏，所以需要按照 SEI CERT C Coding Standard 规定的方式写，指针只能这么用。

同样，Agent 也可能发现：“我的优化器在精度比较低时，每次都会指数级爆炸，那有没有可能造一个工具，或者造个什么东西来避免它？”AI Agent 也有提取经验、创造工具、改进自己的流程。所以我觉得，如果有同学未来可能做 self-improvement，可以在软件工程历史上看一看，有没有一些比较有趣的 insight，也许可以回到 RSI 的过程当中。

今天我要讲传统软件分析工具。这很有意思，可以回望一下历史。现在 AI 可以生成代码，autoregressive model 可以通过 next token 的方式吐出任何东西，包括代码、生成的图形等等。但在 Generative AI 之前，想要分析软件，是一个非常难、非常需要人类智慧的领域。

因为软件分析工具是一个程序，在大语言模型出现之前，这个程序基本上就是一个算法。你们在 Computer Science 里学什么？学数据结构。你们学的数据结构是什么？一棵 binary tree，一个 graph，你们会用算法处理这样的结构。比如树的 node 上有 weight，图的边上有 label。

那我们怎么样把一个软件……软件带了 intent、spec。如果把软件写在这儿，软件其实只是一个 implementation，我们有 intent 和 spec，但这些东西都是非结构化的。Intent 在人的脑子里，你问人，老板可能给你一句话；spec 可能也只是以自然语言记录。我们在数据结构课、数据库课、编译原理课上，整个 Computer Science 学的东西，都不具有处理这个东西的能力。对它们来说，最多做一个索引、分词、词频统计就行，但这个信号太弱了，几乎不能指导我输入一个程序，就输出一些有用的信息。

非常有趣。我今天先讲一点历史，再讲 Generative AI 时代，软件分析会变成什么样。在这之前，如果想实现一个能分析软件的软件，人就必须把想检查什么、想做什么，转化为非常明确的，比如数据结构问题、明确的规则，一般来讲是 rule-based，工具才能执行。

哪怕做了一个非常通用的检查器、linter 框架、软件框架，这些框架也需要你配置参数，或者写一段额外的程序。比如有个东西叫 CodeQL，我们可以看看什么是、怎么用它。

这都是先人非常聪明的发明。它提供一个通用框架，使你可以写一个像 SQL 一样的东西。SQL 是什么？你有一个数据库，可以 select 什么东西。同样，我也可以 select 一个语法树节点，比如能不能 select 一个 `malloc`，然后必须在同一个函数里看到它的 `free`？可以写一小段代码，检查某种东西。

CodeQL 就好像把源码编译成一个关系数据库，用另外一种查询语言查询程序的各种性质。在这个语言里，可以引用代码里的函数、表达式、声明，对应的关系、函数调用，甚至还有控制流之类的东西，然后就可以写规则。

打个比方，极端一点，比如我的每一个表达式里都不能有括号，我就可以在 CodeQL 里写一个这样的查询，实现一个 linter 规则。

这件事对于你们的项目，可能是有意义的。人们做了很多这样的工具，基本上软件分析工具只能运行程序、查看结果，只能处理语法或者形式语义上的一些问题。

但我觉得，从软件分析工具怎么构建的过程中，其实可以看到一点：在 AI 时代，软件工程或者自动化的软件工程，到底会变成什么样。所以今天我还是要花一点时间，相当于再把前两次课讲的相关东西往后推进一点。

刚才说，软件分析的基本原则，就是把软件当成一个数学对象。程序是数学对象，这是 Computer Science 非常重要的根基。我们说 Everything is a state machine，在计算机世界里看到的，完全就是状态驱动的。

这里展示一张图，叫编程语言的形式语义，看起来很怪，你们不需要真正理解它。这里有个符号是西格玛，这个西格玛就是状态。看这里，如果要执行一个赋值，比如 $x = e$，就需要把 $x$ 的值换成这个表达式求值以后的值。看起来很奇怪，基本上就是说，程序的任何一条语句、指令或者 whatever，都是一个函数，都是一个 $f(\mathrm{state})$，会到下一个 state。

这是一条语句的语义，也意味着可以一直追问，追溯到皮亚诺算术的公理系统上面，去定义出……离散数学又袭击你们了。用数学严格的方式，定义每一条指令或者语句的行为，数学意义上严谨，而且计算机可以处理。

在这个基础上，比如有两条语句复合在一起，先做 `x = 1`，再做 `x = 2`，看到这样一个程序，它无非也是一个字符串，也是一个数学对象，就可以推导它的性质。

很大程度上，软件自动化的终极梦想，就是可以分析，给你一段程序，你就知道它对不对，是不是符合 intent、spec，这个 implementation 里有没有什么问题。这是软件工程的终极目标。因为在大语言模型之前，这几乎是我们唯一有的工具。它没有办法和人类世界对齐，但是在上面发展出了非常有趣的应用。

像前面讲过，软件质量保障第一次课讲软件测试。既然程序可以在机器上执行，人肯定可以写 test，你可以写一个 software。还记得吗？我们讲了一些笑话：测试工程师走进酒吧，点各种奇怪的东西，酒吧都还好；但顾客来了，问有没有洗手间，酒吧就烧掉了。人类测试工程师会写很多测试。那如果要做一个 self-improve 的软件，就希望能不能自动从软件里生成测试用例。或者至少，人类已经有了 test 1、test 2，好多个测试用例，我们能不能评估测试做得好不好？

你看，这些都和软件到底好不好相关，但是没有直接联系，不能直接回答软件是不是满足了 spec 或 intent。但是，它给你增加了一些对软件是对的的信心。

举个例子，eventually，我们会要求——可能现在，尤其项目早期，不会做这么严格的要求——所有单元测试要对代码实现百分之百的覆盖率。这是很有意义的事情，是一个经验，也就是我们说的“未测代码永远是错的”。那如果要得到软件覆盖率，怎么办？

有没有发现，大家有了测试和覆盖率的概念以后，完全可以跟 AI 许愿：“帮我做一个 CI 流程。如果单元测试覆盖率到不了 100%，就直接拒绝。”这个时候，AI 会调用很多奇奇怪怪的软件工程工具，加上一个比如 `.github`，在里面写配置，说我要一个什么样的 gatekeeping。运行发现到不了 100%，到了 100% 以后，Agent 就会自动开始加假测试用例。

有没有想过，测试覆盖率是怎么得到的？理论上，可以在 GDB 或任何一种语言的调试器里打开程序，单步调试。每次单步调试，你都知道程序停在第几行，每次就记下现在第几行，最后比一下是不是所有行都覆盖了，这就是覆盖率。某种程度上，你们可以用这个方式实现覆盖率，当然效率会比较低。

实际上，为了实现比如测试覆盖率统计，我们专门的编译器有这样的选项。编译器本质上编译出来是一个数据流图。比如 `x = 1`、`y = 2`、`z = 3`，是一段顺序程序，有点像绑在一起。但如果有一个分支，比如一个 `if`，就可能有分支，分支完还可能有循环，再有分支时可能跳回来。当然，最终程序可能有一个出口节点，它是一个图。

统计覆盖率时，编译器会在每个基本块，就是每段顺序指令上，加一个 `counter++`。比如这块编号 ID 是一，就 `counter1++`；这一块 ID 是二，最后会编译出一个 `counter2++`。在现代 CPU 上，加这样的 `counter++`，其实没有消耗太多 CPU，尤其 CPU 可以做指令级并行，一定程度上隐藏一条指令的延迟。也就是说，在一段连续的顺序指令上，只增加了一点比较小的开销。

所以，最后得到测试覆盖率，付出的代价就是在编译器上加一个选项，让编译器帮你 instrument，插装这个程序，它会输出一个有意思的结果。

你看到，软件工程师在 self-improve 过程中做了非常复杂的事情。远比可能今天 AI 说……你们可能会看到，今天 AI 又写算子了，今天什么 GPT-6 又去操纵一个小模型的权重了。但在人类世界里，这个智慧还是很多的。仅仅统计覆盖率这件事，本身就有很多人长期研究。到今天，甚至可以用硬件上的一些东西统计软件覆盖率。

这只是里面非常小的一点：测试用例有没有满足某个条件，以及有没有可能自动生成测试用例？有没有可能自动生成足够多的测试用例，直接达到 100% 覆盖率？这不就已经相当好地完成了软件测试吗？尤其代码里有足够多断言时，就可以很大程度上增加对软件的信心。这是测试。

还有分析。我们说每条语句都有形式语义。当然，这个例子举得比较简单：$x$ 输入一个不确定的值，是 $0$ 到 $9$。如果有个数组，读进来以后，任何字节都有可能，如果执行一个 `read` 的话。但如果 `read` 完以后，把数组用 `memset` 清零，清零以后，就又知道这个值是零了。

所以，随着程序执行，我们总是可以……我们知道程序是一个状态机，所以它一定从一个初始状态出发。这个初始状态其实已经很 tricky 了。以命令行程序为例，初始状态是操作系统传给你的状态，比如有 `argc`、`argv`，还有环境。为了分析程序所有的可能性，其实在初始状态就已经有无穷多的可能性。可能是 `./a.out`，没有参数；也可能是 `./a.out a`，等等，已经有无穷多的可能性。

当然，每个可能性向下执行一步可能是确定的，再向下一步也可能是确定的。我把这个画好一点，相当于程序执行前有个状态 $S_0$，程序还没执行。如果这里有一个，比如 `x = input()`，这时状态是不是又分叉了？可能是 $x = 0$，也可能 $x = 1$、$x = 2$，像刚才的例子一样。

虽然一次程序执行只能选一个。当我只选择了 `a.out a`，就进入这一条路；下次再读 $x$，又进入一条确定的路线。你的 test，或者程序执行，就是一条具体路线，最后可能 crash，也可能没有 crash。

但如果想得到整个程序所有执行的性质，有没有可能把这些状态都捆起来，框起来合并成一个状态，合并成一个抽象状态？这个状态比较聪明，可以在形式语义的意义上，不停地假装执行它，最终能推出一些更有意思的性质。比如这里 $x$ 等于 input，$x$ 在 $0$ 到 $9$ 之间，不就得到这样一个性质吗？后面再比如 $y = x + 1$，因为知道 $x$ 有边界，知道加法语义是什么，就能推出 $y$ 在 $1$ 到 $10$ 里面。

这个方式处理顺序程序时没有问题，但如果想处理循环的东西，以及现实世界编程语言的语法、语义特性，就会非常麻烦。比如函数指针会跳到哪里？比如里面有一段汇编，C 和 C++ 都可以写 inline assembly，这个汇编调用了一条奇怪的机器指令，把数据交给操作系统了，它的行为又是什么？你不完全确定。所以真正想得到一个非常好的程序分析结果很难。

一般来说，就用它来分析，比如编译器里，你的类型匹不匹配，这是可以分析的。有些时候，变量有没有初始化？你们初学 C 时都会写这种程序：`int x`，有一条路径上直接 `return x`。你有一个未定义的值，$x$ 是没有赋值的局部变量，只是 undefined。一旦 return 它，就是非常危险的事，会得到一个奇怪的数字。甚至如果碰巧原来内存是零，调试时一直是零，看起来程序还是对的，就非常危险。

编译器可以知道，存在一个从这里到这里的 data flow，数据流，我可能会用到一个未初始化的值。所以可以拒绝这次编译，或者给你一个 warning，等等。

上节课花了一些时间讲验证。因为有这个语义，所以也许可以证明整个程序是正确的。在软件分析领域，有一个非常有趣的定理叫 Rice's theorem。虽然我并不是很喜欢它，因为其实它什么也没说。它说，如果想有一个万能的——等于给人类判了个死刑——如果想证明任何哪怕对人类有一点用的程序性质，比如程序是不是终止，是不是有一个不好的函数可达，我们肯定希望证明这样的性质。因为程序 Turing-complete，总能写出非常奇怪的程序，让你的验证器验证不了。

也就是说，如果想有一个万能程序分析器，可以分析任何程序的某个性质，哪怕非常简单的性质，你都是做不到的。

我更喜欢用这个例子来解释它。首先，你可以在 Python 里面构造无穷的 generator，可以构造一个生成所有整数的 generator。你就写一个类似这样的：`while True`，`i = i + 1`，然后 `yield i`。定义一个函数，就得到了一个 generator。假设内存无限，这个 generator 可以无限地往后生成。

那我写这样一个程序：如果有 $n > 2$ 的情况，而且 $a^n + b^n = c^n$，比如 $a^3 + b^3 = c^3$，你就 abort，这个程序就终止了。我就问你：这个程序会不会 abort？因为当我们谈论 abort 时，大部分时候都是说，这个指针会不会是空的，有没有可能是一个 null pointer？这些相对来说还是比较简单的性质。但比如我就在这里 dereference 空指针，故意在这个里面 dereference 空指针，然后问你：程序分析器能不能帮我证明这一点？程序分析当然不能。如果它能，它就可以在数学界大杀四方，比 OpenAI 的模型还要厉害。所以它就是做不到的。

但是，实际上我们人类不会写出这样的程序。虽然我们不阻止人类写出这样的程序，你作为一个人类，完全有权利写出这样的程序，故意去刁难一个程序验证器。但是，程序分析的理论，像这种说“存在一个东西”的理论，忽略了一点：我们的软件工程，讲的是从 intent 到 spec 到 implementation 的过程。整个过程里面都有人类的知识和先验。

我们说软件工程，刚才那页不在这个 slides 里。它是有经验的，它知道人类的需求有些是实现不了的。你的领导许愿说：“你能不能给我做一个万能的数学证明器，把全世界数学上的定理全证了？”回到 LLM 之前的时代，能不能做一个万能的求解器？你肯定应该说：“这个东西我做不了，这个需求做不了。”

在人类世界里，人类已经创造了一系列软件工程工具、编程方法、框架等等。通常来说，你的 intent 在你跟客户、甲方拉扯过以后，基本上已经在人类已知的范围内讨论了。你们做的东西，应该是人类世界的一个过程在信息系统世界里的投影，基本上就是一个信息系统。你大概会知道，我一定可以用数据库来表示过程的中间状态，中间状态的迁移，大概是支付、选课这样的业务过程。

所以，虽然我们没有办法阻止自己写出很糟糕、很难分析的程序，但实际上软件分析工具面对的程序，是所有程序世界里面非常小的一部分。刚才说，我们的分析工具输入一个软件，可能输出 tests，或者 analysis results，也可能输出一个 report，比如潜在风险的变化。

在软件工程领域，之前还有一个非常有趣的研究工作，叫 defect prediction，缺陷预测。也可能听课的同学还在做这个方向。它大概是说，现在有一段你的代码，或者你的文件分成好多 classes，我就给每个 class 打一个分。完全根据肉眼观察这个 class，也不看软件的其他部分，我就可以给它打分。比如数这个 class 里有多少个循环，有多少个 `int` 关键字，有多少个大括号，最大的括号嵌套深度是多少。

这不是得到了一个向量吗？什么 1、3、4、2、7、5，可能是一两千维的向量。然后不管是用启发式方法，还是用机器学习的方式，都可以得到一个函数 $f$，得到一个数。比如我有 99.9% 的把握认为这段代码有 bug，就可以猜这个函数是不是有 bug。

你不要笑。如果你事先不知道这一套流程，去看一个老的软件工程项目，预测一段代码里有没有潜在的 bug，其实是成立的一件事。你确实可能能够省下一些成本，比如找到最有可能、风险最大的模块等等。

反正很多好玩的这种东西，都建立在 trade-off 上。因为 Rice's theorem 已经告诉我们了：你要放弃对所有程序都成立的分析。但是，我们要分析的软件，刚才说了，无非就是能用数据库来表示状态，然后用 Java 语言实现等等。我们感兴趣的软件，在所有你可能实现出来的 All possible programs，或者 All possible software 里面，其实是非常小的一部分。

比如在外面，我可以写出一个每当你在支付宝下单时，都去验证一下哥德巴赫猜想的程序。你没有任何办法阻止我写出这样 make no sense 的程序。而一个 sound 的、绝对正确的程序分析器，是要对这种程序负责的。

那我们当然想，如果不需要为这部分程序负责，只需要为这一小部分程序，甚至是这一小部分里更小的一部分，比如使用了某种语法特性的程序负责，软件分析就成为可能了。所以你看到，在几十年的时间里，软件分析只要能够不断舍弃一些东西，就可以得到有用的结果。不管是生成 test case，还是一些分析结果，都会非常有用。

这些耳熟能详的东西，比如类型系统。我不知道你们有没有写过一点 JavaScript，写过就吃过苦头。动态类型，这个程序看起来好好的，跑起来也好好的，网页跑着跑着就崩了，不动了。然后你看到一个奇怪的类型不匹配，不能把某两个东西加在一起。

God is the Father，God is the Son，God is the Holy Spirit，但是 the Father 肯定不是 the Son，the Father 也不是 the Holy Spirit。在 JavaScript 里，因为 implicit type conversion，你现在打开 F12 控制台，就可以验证这一点。至今为止，你的浏览器还必须保留这个行为：你可以把奇怪的东西加起来，直接把一个 list 和一个零加起来。这听起来是非常 ridiculous 的事情，它到底应该得到什么？

这就导致，在 JavaScript 里，零等于空的 list，零也等于字符串零。这个行为已经突破了很多人能够接受的底线。零还等于一个只有一个空白字符 `\t` 的字符串。但是它们之间是互不相等的：空的 list 和字符串零不相等，空的 list 也不等于 tab symbol。

在这里吃够苦头的时候，人类发明了一个非常重要的东西，叫 type system。Type system 要求你有一定的程序员智慧，尤其像 C 和 C++ 这种 strongly typed 的语言，一直到非常后来，才有一点自动的 type inference，你可以用 `auto`。甚至应该一直要到 C++17，才能用 `auto` 去 unbox 一个 tuple 里面两个东西的类型。即便如此显然，你几乎总是知道它的类型，仍然需要手工把类型写出来。

并且写出来以后，编译器会检查你的类型写得对不对。如果你试图在静态的时候，用加法去加两个类型不匹配的东西，编译器会直接拒绝你。所以，如果随手写一个程序，让它随便证一个性质，是很困难的。那我可以让程序员承担更多代价，承担更多思维实验。

我不知道你们有没有写过一点 Rust。现在我们自己做项目也用 Rust，但是已经不太会 Rust 里面的类型体操了。我记得 Rust 刚出来不久的时候，我们为了和 Rust 编译器作斗争，使一个看起来很正常的程序能够通过编译，都是一件极度痛苦的事情。当然，通过编译以后，它给了我更好的 memory safety guarantee，这是另一件事。

在类型系统不能保证的时候，我们还有 Linter。可能你的程序类型整个都是好的，但有没有一些 bad practice？我相信你们应该都用过 Linter，或者已经在工作流当中引入了 Linter。Linter 在大模型时代也非常好用。当 AI 写出一些可能不太对的代码时，它可以先提醒一下 AI，这样不用运行。

你可以直接问。比如这个项目，你没有学过，不知道 Linter 是什么，也可以直接问一下。DeepSeek Flash 就是非常讨厌，它会过度地读项目里的东西。好，它提了几种 ROI 最高的检查：未使用、未定义、不可达，null pointer 的 safety，忘记处理的 Promise，忘记 `await` 的 Promise、异步函数，包括异常，比如可能抛出的异常没有 catch，以及危险的 API 与隐式转换。

有些操作在编程语言里是允许的，但是在项目里，从软件工程的角度来讲，可能不允许。比如 C 语言里可以做 type casting，可以随便 cast。C 的 cast 非常狂野，你可以把一个整数直接 cast 成一个指针，也就是可以写一个 `0x1234`。上课时我经常干这样的事情：去读 binary 里的信息，得到一个具体的地址，直接把它 cast 成函数指针，然后调用它。这件事情非常危险。

在 C 的语法里，C 虽然是强类型的，但可能允许这件事。但是在软件工程的意义上，因为我要做一个非常安全攸关、要上火星的火星车，那么对不起，我禁止所有强制类型转换。所以我可以写一个 code checker，或者 lint rule，说在这个项目里，不允许使用任何强制类型转换，以获得最大的代码安全性。如果有强制类型转换，必须在前面写一个注释，说清楚为什么需要做这件事。

还有很多，比如一个函数不能太复杂，`if` 嵌套层数大于三时，就必须拆分函数，保证代码在一定程度上可读。所以这就是做 trade-off：我们有很多软件工程经验，这些经验都会变成经验性的规则。输入一个软件，它会检查规则是不是满足。我们可以做各种各样的 trade-off，完美的软件分析做不到，那就这放一点，那放一点，可以做得越来越好。

也就是说，在代码上、静态的时候，我们可以用类型系统把更多难度交给程序员，让程序员为了通过编译就要绞尽脑汁。有些性质，比如用了一些好的语言特性，像 optional，就可以知道程序可能永远不会发生某些类型的 crash，这是可以保证的。有了 Linter，至少可以知道，比如在项目里说永远不能用强制类型转换，那确实就没有强制类型转换，可以一定程度上提高对软件正确性的信心。

静态的做完以后，还可以在动态运行时做出各种各样的取舍。我们要求开发者做完美的测试不行，那就用随机的方式生成大量测试，或者做 property-based testing。这是一种很有意思的测试方法。它是说，如果你的程序里有一个 assertion，说明程序要满足哪些重要的性质，我就可以根据这个 assert 写一个 generator，写一个生成器，不断生成测试用例，看看有没有一些偶发情况会触发一条不一样的路径，然后这个程序就 crash 了。

我们也可以评估测试用例集合的好坏。比如 test case，我们说要 100% 的覆盖率，刚才讲的就是一个很好的、如果希望保证软件质量就应该做的 best practice。

我们还有一些很有意思、软件工程的人类脑洞大开的东西，比如蜕变测试。这个软件可能不太好测试：有一个 input，有一个输出，但不知道这个输出对不对。很多程序都是这样，输入一个东西，输出一个东西，它没 crash，你就不知道它对不对。

那有没有可能构造两个输入？比如他们喜欢举的例子，$\sin x$，再给一个 $\sin(-x)$，这两个之间有一个负号。所以你就知道，这个软件在不同输入之间要满足一个关系，然后去测试这个程序。还有一些评估测试集到底好不好的手段等等。

这些概念可能是你第一次听到。如果不感兴趣就算了，也不重要。如果你对测试覆盖、测试准出的门槛有点兴趣，就让 AI Agent 帮你调研一下，这个世界上有什么软件测试准出的门槛。下一次就可以把它写到 `AGENTS.md` 里。因为现在可以许愿了，只要有这个概念，知道应该朝这个方向努力一点，就可以让 Agent 来做。

为什么呢？Agent 还是有一种快点完成任务的倾向。当它有迷之自信，觉得不需要测试，不需要严格的测试门禁也可以时，就会说：“那我就往后做吧。”现在的需求还在它的能力范围内，但随着需求不断增长，超出它的能力范围，它又仍然在这个上下文里，没有自己重构的动机，就会越改越慢，最后做不对了。

所以如果了解这些概念，你可能在适当的时候会让 Agent 做一个测试。当然，后面可以给 Agent 越来越多的压力：最终有没有可能把一个关键部分、关键算法，用形式化定理证明的方式证明它是对的？能不能自动写一个软件，从代码里提取出分布式系统的协议，并且用模型检查器，或者定理证明器，去证明这个协议是正确的？而且当协议修改以后，可以自动同步，再重新证明一次。这就是付出更多算力，来换取对正确性更多的信心。

所以说了那么多，就是给大家一个 list：人类在软件工程的时代，或者在软件分析领域，做了那么多东西，就是让一个看起来完全黑盒的软件，也有了可以让你改进的反馈，这点最重要。在 Agent 时代之前，我们可能都没有从这个视角来看软件，虽然直觉上肯定知道这一点。

软件生产出来，进入 implementation 以后，软件工程师交付给你的是一个 `.git` 仓库。这个仓库到底好不好，你对它有多少信心，是不知道的。但是当有了很多软件工具，这个 `.git` 被放到一个工具集里，有很多输出，比如编译通过、测试通过、测试覆盖率达到 100% 等等，所有这些东西加起来，提供了反馈和信心：这个项目一定程度上是 OK 的，满足一定的质量要求，可能还不错。

这就解释了，为什么比如研究生同学来报考我，说：“我们来做一个项目吧。”好，挺好。我说：“你去建一个 Git repo，把你做的第一个事情先放进去。”放进去以后打开一看，各种不一致的缩进，代码左右的空格也不一致，还有一堆生成的文件，什么 `a.out` 也在里面，`.DS_Store` 也在里面。

`.DS_Store` 在这个[时代名称不清]时代更加容易忽略，因为在 Mac 里看不到它，随手一个 `git add .` 就加进去了。然后又不看，commit 之前不看，就把它放进去了。所以这是一个降低信心的事情。当我看到这些，就知道你肯定没有仔细看那个 commit，在 commit 之前没有最后再看一眼，代码写完以后没有再扫一眼。

这就意味着，你很有可能不知道软件世界里的质量保障工具。因为如果知道这些东西，自然而然会遵守比它更简单的 best practice。刚才说了很多，对正确性的信心是递增的，但付出的 efforts 也在不断增加。所以，如果连最基本、只要看一眼就能做到的事情都不做，我就形成了一个后验：你对软件质量这件事不上心，所以应该写不出好的软件。

反过来，如果看到软件工具跑出了很多正确的结果，就增加了一种信心：这个软件是好的，这个项目可以继续维护下去。

更重要的是，这些工具在 AI Agent 时代给了软件非常多正确的反馈，这些反馈一定程度上可以学习。一般来说，工具给了一个反馈，比如 type mismatch，会告诉你哪一行的什么东西，type 不 match。如果说测试覆盖率不够，会告诉你哪一行没有覆盖到。这些都是强化学习非常好的短程反馈。只要 System I 训练得比较好，有一个大概的概念，就知道发生了什么事，所以它是非常好的强化学习反馈。

就跟今天看到的，不管 OpenAI 还是 Anthropic 的模型，都可以直接用鼠标画画，这也是一个反馈非常短的事情。给你一幅画，马上就知道画得好不好。程序其实也是，因为我们 build 了这么多软件工程工具，给代码兜底，所以强化学习才可能让这个飞轮转起来，让它写代码越来越强，直到任何人都写不过它。

虽然这些工具都是人创造的，但显然没有一个人能够在大量项目里，仔细阅读每个工具的每个输出，并且把每个细节都做对，这件事超出了人类的范畴。人类可以抓大放小，把最重要的几件事情做对，比如抽象要做对，这个好像 AI 还不是特别擅长。但是，当你把所有这些细节都做对时，对软件的信心已经变得很高了。

而且 AI 学会这些工具以后，自己也会写一些 Linter rules、checker、单元测试。测试失败以后，因为在训练过程中频繁地和这些软件工程工具打交道，它也知道出了错应该怎么修正。

所以我觉得，软件工程工具给了我们一个非常好的 RSI，recursive self-improvement 是怎么实现的例子。人类是怎么实现一个稳定的自我改进的？我们发明了软件工程。软件工程除了经验和流程，这些更多是口口相传、大家学得很快的东西，工具就是软件工程给人类世界留下来的最大的财富。

有兴趣的同学可以了解一下这里有什么工具，然后就去许愿。比如说：“能不能给我做一个比较完备的 Linter 规则？”它就可以做很多。说：“能不能给我写一个 fuzz testing？”它也会写。

再比如，你真的可以许愿，问它能不能证明一个东西。它很可能跑了很长时间以后，告诉你：“对不起，我做不到。”或者有些地方，它说时间太长了，也不想再跑了，这都是有可能的。但毫无疑问，随着 RSI 不断进步，这些东西都会变便宜，有一天可能会纳入标准的软件工程流程中。

所以每一种 checker、每一种软件工程工具，都给了你一些额外的信心。比如在一些采样的执行里没有发现问题，或者已经穷尽了所有可能的路径，或者在这个形式化下，已经证明了一个简化模型的正确性。当然，每个都可能留下一些没有证明的东西，但互相交叉检查，对项目的信心就增加了很多。

这是我说的好的一面：软件工程工具给了我们很多启发。但同时，如果要说软件工程工具后十年会发生什么变化，因为我自己是做这个的，可能体会更深一点。我觉得所有软工人都被困在一个基本假设里，就是软件分析是机械的。

还记得吗？我说这些软件工程工具是在 pre-LLM 时代提出的。Pre-LLM 时代意味着，软件工程工具只能接收一个程序，并且使用它的 formal semantics，形式化语义。像 $x = 1$，可以说 $x$ 有一个 type，比如 $x$ 是 `int`。你有一个数据流图，要在这个数据结构上加一些东西。你们如果学编译，要做数据流分析，其实需要在每条语句上加一点 notation：它的 type 是 `int`。你们的编译实验应该要做类型分析，需要做一个数据结构，相当于给它一个 tag。

所有旧时代的软件分析工具都是这样机械的：人必须先把意图转换为明确规则。不管是说要测试 100%，那就要在每个基本块上加入一条加一的语句；如果要遍历所有路径，就从初始状态开始，一条一条找。

但同时，我们的世界是有 intent、spec 的，我们的程序从来没有跟人真正对齐过。换一个角度，程序其实有两个角度：第一个，它是有 formal semantics、无情地执行指令的机器，严格按照 formal semantics 执行，假设它没有 bug 的话。同时，程序也是人类活动留下的一个样本，是从概率分布里面来的。

这就很有意思。我现在有一个程序，它带有老板的想法、这个世界的状态、你今天的心情、整个公司的环境、团队的氛围，所有这些东西，再加上自己的历史经验，最终输出了当前这样一个软件。它确实是一个概率分布，也就是在一个概率分布下采样，采出这样一个软件。那这个软件一定程度上跟我们的需求说明书、领导的风格肯定是对齐的，一定是对齐的。

所以代码其实带了大量人类的习惯和上下文。甚至不需要去看那个 intent，这里有一篇很有名的文章，叫 On the Naturalness of Software，说程序看起来还是很像自然语言的。

如果用自然语言处理里面的技术，比如 n-gram——那个时候还在用 n-gram——我有一句话：“This sentence is false”，很有名的悖论。比如一个 3-gram，就是每连续的三个词。你可以把它 tokenize，不用 tokenize，就给每一个词一个编号，比如 1、2、3，这又是 2。然后我就得到了一个 3-gram，是 123，再把窗口往后移一格，“Is sentences”，它就变成了 232。

我们就可以用统计的方法去理解，像 Markov chain 一样，把它们都合起来，变成一个 Markov chain。现在有一个状态，每次按照一个概率选下一个词。如果用统计的方式去理解生成的东西，可以发现，比如人类的文学著作里面，有这样的统计规律，能找到一些确定的统计规律，在代码里面同样也有。所以软件虽然是一个形式化的对象，但是它带了很多人类的习惯。

我举个例子，为什么说软件同时承载两个世界呢？我有一份代码，这份代码在静态分析器或者软件分析器里面看起来就是一样的，无非是一些 token，然后有些逻辑：`not x.foo(c1)`、`x.bar >= c2`。到底哪一个对呢？当我们把名字都去掉以后，因为用形式语义分析软件，名字确实都去掉了，我确实可以说明，这里有没有 Lint 不允许的东西。比如要求 `if` 里面条件的数量不能超过五个，毫无疑问它没有超过五个，它是对的。

但是有些东西，你不对齐到人类世界里面，是不可能知道哪一个是对的。我相信绝对没有人猜到，这段代码背后的实际程序是什么。猜一猜。对，我就开个玩笑，因为我昨天在群里面突然发现了某种 TV，没有梯子是访问不了的。当你写一个条件判断，判断 yes or no 的时候，这个条件判断到底对不对，其实是和人类世界的概念对齐的。到底哪一个对，显然一目了然。

所以你看，identifier 的名字是重要的。当你看这个的时候，什么也看不出来。两段代码看起来都完全符合编程语言意义上的统计规律，我不能 tell 谁对谁错。但是放到更多上下文、人类的上下文上，就可以看出它是对是错。

所以本质上，我觉得在 AI 的时代，我们有一个前所未有的机会，可以彻底重塑软件工程，或者说软件工程工具的世界，让我们能够创建出更好的软件。比如可能 Coding Agent 本身就会被重构，模型也可能在这个过程中起到很多作用。

大家很容易问一个问题：为什么在 AI 时代，我们还需要软件？如果模型都已经这么强了，甚至我们看到有试图用模型直接渲染一个世界给你的，为什么还需要软件？是因为 CPU 的执行是 energy efficient，我估算可能有九个数量级。这就是钱，这就是电，资源在世界上还是有限的。为了最大化资源的使用，能让 CPU 算的东西就应该让 CPU 算。

所以软件的 implementation，比如我要保存一个数据，persist 一个数据，就让数据库来帮我 persist，它的能耗非常低。但如果全部让一个智能的大脑来，你就这样想：让一个人去帮我 persist 数据，和一个 CPU、NAS 来给我 persist 数据，你一定会选 NAS，不会选人。虽然人在某些场景上可能更可靠，你可能会先让人做一遍预处理，剩下的东西让 NAS 去 persist。

所以回到这里，如果我们的 implementation 还需要，这是我们的假设，它还会很有用，因为它算得又快又准又好。一旦程序是对的，它就永远不会出错，不会概率性地受到心情或者环境这样的影响，也不受提示词注入的影响。

那我们要的，其实就是证明 intent 和 spec 是一致的，spec 和 implementation 是一致的，要把 gap 合上。所以我们理论上想得到的一个终极目标，就是 informal verification。

我们希望对于形式化世界里面的 software——刚才说 software 是个状态机，Everything is a state machine，可能是一个转换图——它对应的状态机里面，任何一条执行轨迹，可能最终绕出来就 terminate 了。我希望它的每一条执行轨迹，不再是像以前写形式化方法或者静态分析时，说我想证明每一个程序执行里面都没有 null pointer dereference，或者每一个执行里面都没有 integer overflow。这对于写在飞行器上的代码非常重要，overflow 以后会从一个极端跳到另外一个极端，整个飞行控制可能就会崩溃。

那么我们其实变成了想要证明：for all trace，这个 trace align with intent，且 align with spec。也就是说，我希望所有执行，在人类世界的意义上都是合法的。这个就完全没有办法做 formal verification 了，因为它已经超出了形式语义的范畴。比如这个输入是什么，它的意思最终是对齐到人类世界的。

今天有了大语言模型，或者足够强大的模型以后，理论上这件事情已经可以做到了。我无非就是把每一个 trace 都拿出来，交给 Agent，让它跑无穷长的时间，它应该能给我一个这样的 informal verification。

所以我觉得，在未来几年里面，软件工程会发生这样的变化。这句话是我模仿 Jim Gray 在 2006 年讲存储时说的：“Tape is dead, disk is tape, flash is disk, RAM locality is king.” 没想到这预言了 GPU 时代的 RAM locality is king。本来就是说存储的，tape is dead，disk is tape，有些东西永远就不需要了。我们的 SSD，flash-based SSD 会 everywhere，你们每个手机里面都是 flash-based SSD，然后到今天 GPU 的显存。

以前构造软件工程工具，都是说，能不能有一个东西叫 type，由程序员来保证这个 type？然后有没有比如 test case？我们说 test case 好不好，就用一个 coverage。Coverage 其实就是一种 heuristic，一种启发式的规则，不代表绝对正确，但是可以被程序化，可以写成一个程序来判定。

比如靠我的单元测试，覆盖率到底是 80% 还是 90%？加上模糊测试以后，是不是达到了 95% 或者 99%？这就变成了一个可以度量的目标。但为什么说 99% 或者 95% 就够了？你永远不能说 95% 就够了、99% 就够了，甚至不能说 99% 就比 95% 更好，因为 99% 覆盖的代码可能都是不那么重要的代码，特别重要的代码，这次却没有覆盖。

所以以前我们一直用各种机器可以表示的 heuristics。因为软件分析工具受制于人，是人写的，人类程序员在写的时候，必须把复杂的、没有办法一条条写出来的规则，用比如一个数字去替代。但是今天也许不需要了。

我认为模型有一天一定能走到做 informal verification 的能力上，或者今天我觉得，对大部分软件系统来说，已经有这个能力了。我们要做的，其实是去近似 informal verification 的过程。所有软件工程工具，都是在这一件事情上的一个投射。

我举几个比较有意思的小工作，启发大家一下。我们都知道，程序执行里面有一些是绝对的错误，比如 hit 一个 null pointer，就是一个绝对的错误；甚至比如并发程序里面有一个 data race，也是一个绝对错误。但是有些错误，不是依靠一个 assertion 就能检测到的，我们还有没有可能找到这样的问题？还真的可能有。

这个 SOSP 2009 的 paper，就叫 Detecting Large-Scale System Problems by Mining Console Logs。我看有没有图。我们有没有可能去解析程序的 log？因为本质上想做的是 informal verification，所以可以干一件什么事？可以在每一条语句上面都打一个 log。因为在写代码的时候，或者 Agent 在写代码的时候，其实知道这些语句是干什么的，功能是什么，目标是什么，边界是什么。

我前面有一次上课也说，写代码的时候，比如一个函数调用，在程序员写下这行代码时，知道它可能调向哪里。但是当把这行代码写下来的时候，这个信息就已经丢了，因为你不会写一个注释，说它可能会调向哪里。结果软件分析的人做了非常多的研究：怎么样把可能的函数调用都找回来？

至今，如果做一个 call graph，就是构建函数的调用图，都可以发 programming language 领域顶级会议的论文。就找到程序的调用图，因为形式语义很困难，编程语言里面有很多特性，这些信息丢了，你要把它恢复出来。

但反过来想，如果在软件编写的时候，给每一条语句都打一个日志，在解释这个函数调用时，解释这个函数要干什么，我把所有日志串起来，不就是一个给大语言模型做 informal verification 的 trace 吗？我运行一次，就得到了每一个语句的解释，然后问 Agent：这次有没有偏离我的原始意图？我说在常理上不应该做的事情，它是不是都没做？在常理上，这次执行接收到这个输入，根据我的 specification 和 intent，应该做成什么样？我的软件到底有没有做到？

当大语言模型可以和人类对齐时，就可以用日志来检查。我不需要程序，只需要程序所有的输出日志，就可以检查这个程序至少看起来是不是正确。

这样的一个疯狂想法，你甚至可以在 2009 年的老 paper 里面看到。它说，我们有没有可能用自然语言去 parse 这个 log？当然，它的目标比较限定，在那个时候，可能要找到一个比较好的 scope，能够做出一定的实验效果。

它说，如果是一个 distributed system，分布式系统，假设我随便画一下，log 1、log 2、log 3。如果能收集比如一千万条日志，一千万条日志里面都有 AB，或者都有 ABC，唯独有一个里面是 CBA。根据我们的假设，如果这个系统基本上是正确的，你会非常确信地怀疑：这个是不是不对？

人类也是这样的。软件每次运行都是那样的，你玩一个游戏，每次看起来都正常，突然有一次穿模了，掉到地下。你们都见过这种情况吧？你就感觉不对了。当然，这是因为你和人类世界、物理世界对齐了，知道穿模掉到地下是不对的。

但你想，如果在 CS:GO 里面，每次都把人的坐标，XY 坐标记录下来，比如用 XY 坐标，就可以提取一个，比如在 Z 轴方向、XYZ 轴方向移动的位移数量。比如一次执行是这样的，你会发现这个函数有界，一来一去，都不会移出地图。当你穿模掉到无限大以后，会发现有一次执行长这个样子，这就是一个非常明显的 outlier。然后在 outlier 里面，就会发现这个地方可能有 bug，而且会知道长得不一样的部分。

程序执行可能很长，这次 CS:GO 可能一直都很正常，突然到这个点开始不正常了。它甚至会告诉你，程序运行到这个点时可能发生了异常，你就可以回去诊断到那个 bug。

所以它干的就是这样一件事。它说，我可以提取日志，提取自然语言文本的日志。这个图稍微有点小。去做 log parsing，然后做 feature creation，再做异常检测，就可以知道这个程序是不是有 bug。

你没有发现吗？这就是一种 informal semantics，做 informal verification 的一种雏形。虽然它用的方法和做实验的领域可能比较限定，因为 2009 年有机器学习，但是还没有 LM 这种能真正理解、和人类 intent 的世界对齐的统计模型。但是这件事情的方法学是成立的，它要做一个 informal verification，所以就是这个框架的一个投射，是很有意思的一个工作。

后来还有人开始用 AI，去 mine logs。再比如，从 log 还可以对应回程序的某一个具体位置，等等。这是一种。

还有软件工程的工具。我想我应该怎么样……我觉得逻辑断了，准备的时候没有完全准备好。另一种类型的软件工具，这篇文章在当时也是……这个是 Andreas Zeller 的，是 Andreas Zeller 吗？应该是 Andreas Zeller 的成名作。

软件状态在人类意义上可视化的投射，是非常重要的软件工程工具，虽然和这些都不一样，它是帮你调试的。如果知道软件有一个问题，或者不知道这个软件行为是什么，想理解、想知道它发生了什么，就可以用可视化的方式把数据结构演示出来。

你们想想，实现二叉树的时候，是不是对着代码调到吐？要实现一个数据结构，一个不 trivial 的树，一个 AVL tree 或者红黑树。我印象中，每年数据结构课应该都会让你们实现这个东西，那就是绝对痛苦的折磨。

为什么？因为程序是错的，但是程序看起来又是对的。非常典型的软件工程的对齐问题。虽然它有 formal specification，你希望对于程序任何执行的 trace，构建出来的 tree，在任何中间过程都是合法的，满足比如 AVL 树的性质，并且所有指针的指向都是合法的，它是一个 AVL 树，没有其他奇奇怪怪的问题。

但是这些性质，想要证明很困难，甚至想看到它都很困难，尤其程序没有 crash 的时候。你们怎么办？构造一个 AVL 树，构造完以后对它做一次遍历，可以做一次中左右的，这个叫中序遍历吗？还是叫……反正做一次先……不对，应该是左中右，要先到最左的节点。反正做一个，应该是前序遍历吧，我现在不记得那个 term 了，sorry。

然后就可以找到最小的节点，应该是最小的，持续这样遍历下去，应该从小到大打印出一个递增序列。可能实现完以后，打印它，要么就 crash 了，要么打印出来的序列不递增，就知道代码错了。

那怎么 debug？会打很多 printf，越打输出越乱、越不可读，就越心烦气躁。我相信每一个同学……不过，你们现在是不是用 AI 魔法编程了？说给我实现一个 AVL 树，然后它就自动正确了。

在那个时候，这个工作还是引起了相当的轰动。你看这个界面非常 fancy，支持各种调试，用各种方式、各种 layout 来显示。这是它的架构，它就是一个 GDB 的前端。这个图没有任何实质性的意义，但是它还是画了一个看起来很不错的图。

这样的工具其实是不能用的。就是它能用，如果要调试一个平衡树，或者在课堂上展示一下平衡树的调试，真的可以用。它提取了软件状态，也是一个很有意思的对齐工作，跟之前讲的 testing、verification 不太一样。

它说，程序的状态图，这是程序所有可能的状态，我有没有可能把这个状态投射成另外一种人类可读的形式？人类可读，意味着模型是不是也更可读？Somehow，把状态投射成另外一种形式，使人类可以更好地理解这个状态里的东西。

人类是有限制的。看到一个图，可能图上有几十个节点，就认为它不可读了。每一个东西里面最好也不要太多，三五个东西。人只能读得了相对非常有限的视觉呈现。如果这个东西特别大，你就觉得，这东西跟我没有关系了。所以它做了这样的尝试，做投射。

我们在大模型时代也做这样的投射，试图把 Linux 内核这样的状态压缩到足够小的状态，不管对人还是对机器，它 somehow 都是有用的。

可以在这样的框架下做出各种软件工程工具：要做 informal verification，把每一个状态投射成一个可能可检查，或者和机器相关的东西，最终能够证明它正确。所以我觉得，整个软件工程工具的世界都要发生重大的变化。

以及，我们的软件工程很多工具要检查 trace align with intent 的时候，在传统软件工程里面，我们都说文档很重要。我知道这边有软件学院的同学，大家都说文档很重要，因为文档记录了你的设计、你的想法。

但是在 Agent 时代，很多假设也变了。像我现在就觉得，我们应该在一种 no doc 的模式下工作。什么叫 no doc？当然不是完全不写文档，但是如果一个文档可以从代码里面直接导出，就是代码的描述，就不应该写这个文档。应该用一个 skill，把它想成编译出来的 `a.out`，随着 CI/CD 流程产生出来，并且这个文档永远不会 check in 到 Git repo 里面。

可以用自己的 skill 控制文档的粒度，让文档和你能对齐，或者和你的 checker 能对齐。我可以为代码生成不同粒度的文档：有的是给人读的，有的是给新手读的，有的是给大语言模型读的。

可能我这里执行一行代码，这行代码对应文档某一块解释，执行程序的时候，会把这段解释拼到日志里。最终日志送到大语言模型里面，检查是不是和我的 intent 一致。在不同场景下，文档的功能是不一样的。

所以也许有了代码以后，除了设计上的决定，比如为什么实现这个架构，为什么不这样做、不那样做，要把其他设计排除掉，自己内心有一个道理，这个道理必须通过文章表达。除此之外，所有东西都不应该用 check in 在 repo 里面的文档来表达。

我们看到，这样的框架给了很多思考，我觉得整个软件分析领域也会发生很大变化。所以可以畅想一个未来。

这个应该是 2024 年我做 slides 里面的一张截图。那个时候其实就说到，想要的是软件的终极目标，我们有 intent、spec、implementation 的 gap。

当谈一份软件、一个软件制品时，首先要求语法正确，当然这是最基本的。在符号主义时代，就只能做到语法正确。还需要做到阅读自然：软件不仅给机器看，也得给人看。那个时候已经有大语言模型了，ChatGPT、GPT-4。那个时候它可以做一些 beam search 来生成，就像我们看 SWE-bench 那个 paper 里面那样，模型能力惨不忍睹。有一个 open problem，就是语义正确。

我们看到了什么？软件工程工具花了几十年的时间，提出这样一种反馈，可以告诉你这个程序……我们这个 open problem，语义正确，今天看起来已经解决了。今天看起来解决了，它是怎么解决的？

比如我要语法正确，要语义正确、语义对齐，这个最难，以及它可以人类可读，natural。而大语言模型本质上是在语料上训练的东西，但是它刚好越来越接近这个。虽然不能百分之百进入语法的领域，但是训练越多，就越能接近：至少在人类还 care about 的软件上面，越来越能写出合理的语法。

今天的 Agent 做的是什么？它吸收了软件工程工具几十年研究的精华。它不能保证自己是对的，但是可以越来越好地在这里采样一个点。采样一个点以后，就可以利用当前的软件工程工具。

所以可以换一种方式理解 Coding Agent：它在不知道的情况下先猜一个点，猜完以后，因为对软件工程工具有知识，就让工具去跑。比如跑测试用例、跑单元测试，你看到 Agent 会跑单元测试，会编译一下，会 link 一下，这些都会做。如果这些都对了，它就认为自己猜对了。它甚至还会截图，再看，就认为自己猜对了。

如果有人拒绝它，软件工程工具会给它反馈。模型又训练出来，能读懂这个反馈，就可以往更正确的地方再猜一个：“我这儿做错了，要把它修上。”不断猜，就从一个 initial guess，走到了语义对齐、我们今天满意了的地方。许愿编程今天突然间可以了。

但是这并不是 fundamentally 解决了软件构建、从 intent 到 spec 到 implementation 的 gap 的一个途径。首先，它初始的采样点，很大程度上决定了软件质量。这我第一节课就说了，一旦一开始架构做错，或者只是根据当前描述做了一个设计和需求，很有可能随着需求增加，这个架构就再也无以为继，软件越到后面就会失败。

所以我们也相信，第一方面，模型在发展过程中，比如采样方式会变得越来越好。也可能它自己能够进入一个理解。今天的模型还不真正理解，或者把这件事情作为它的 first principle，所以没有一些基本操作。现在就不停调用工具，往后修，然后改代码。

在这个意义上，模型理论上应该可以看到：我能不能重新换一个对 intent 的理解？有没有一个操作叫重构，或者重新理解这个软件，重做需求？有没有一种重写 spec 的操作？

当模型学会这样的事情以后，虽然这些东西的反馈信号肯定非常弱，而且代价很大，但一旦学会，它就真正理解了从 first principle 去构造软件。我觉得，经典意义上、传统意义上的软件工程，就走向了一个终结。

所以这是我从软件分析和质量保障——因为质量保障最终回到需求——所看到的软件工程和生成式软件工程的未来。我也觉得，这可能是十年以内会发生的事情。
