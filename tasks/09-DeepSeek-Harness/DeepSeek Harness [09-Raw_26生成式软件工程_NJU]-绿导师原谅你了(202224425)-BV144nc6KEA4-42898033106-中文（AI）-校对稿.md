我们已经讲了很多软件工程的概念：什么是软件工程、项目、项目管理，我已经说了一万遍，就不再说了。正因为这些概念如此基础，在今天 AI Agent Native 的时代，它们不断被重新更新。就在上周，Anthropic 说 Git 已经不够用了。刚开始讲版本管理时，我就提到，我们确实有一天会遇到不够用的情况，这很自然。

上学时，你自己就是一个 single-thread Agent，学 C++、Python、JavaScript，写自己的项目；但当你拥有 Agent 后，立即就拥有了一个和现代公司一样的架构。你就是 CTO，负责全部，但很可能不需要写代码。下面有负责架构、产品、UI、前端、后端的多个 Agent，每个 Agent 又可以带多个 subagent，甚至 subagent 还可以创建更多 subagent。其实你有一个组织架构，否则不可能管理复杂需求。做软件工程产品，面对的是各种 essential complexity 和 accidental complexity。

这时仍然需要版本控制和 repository，因为最终交付的还是一个产品，可能要经过 CI/CD 上线，为大家提供服务。任何时候，每个人收到的都是一个小任务。从 first principle 去想，这个任务一定和 repo 里的某些部分相关：可能要重构一个 subsystem，或者在某处加功能，影响一些模块。不同任务在系统里覆盖的范围也不一样。

Anthropic 的那个方案我还没有用到。我觉得最好加一个锁：有些是只读的 read-only，有些是 write，也有些是 refactor，锁的类型可能发生变化。比如 refactor 类型，或者一个 minor fix，虽然是写锁，但它对架构不产生 breaking change。多个小 fix 只要彼此独立，其实应该可以并行执行。

可以借鉴操作系统里的锁，先上锁；也可以像数据库那样先做，再做 conflict detection，也就是悲观和乐观的方式。应该怎样设计版本控制，慢慢会从组织架构上找到答案。毫无疑问，我们能看到世界在向这个方向推进。

概念已经讲得差不多了，还是应该回到具体项目，看看真正设计产品时，整个流程会怎样。肯定要选一个 Agent Native 时代的产品，我选了 DeepSeek Harness。正好前天在北京参加了他们的一次线下聚会。很多同学和你们差不多年纪，可能不像我这样写过很多代码、经历过古法编程时代，也许就是对着模型许愿编程，但他们愿意到这里和大家交流，很有意思。经过几年成长，他们可能就会成为非常核心的开发者。

有必要讲一讲：如果从零开始构建一个 Agent Harness，当然不会做得这么复杂，会遇到什么问题？从具体案例解释这件事怎样发生，里面有很多细碎的东西。今天会讲需求、架构、整个软件系统的设计，以及怎样在 DeepSeek Harness 上做二次开发。下一节课可能讲 Agent Native 开发更细的东西，因为 DeepSeek Harness 里有非常多的 CI/CD。

我看到有同学在评论里说，上节课讲了很多，但看起来好像什么都没讲，确实如此。有些事说起来简单：网上有很多 Skills，有 `grill-me`、`grill-with-docs`，有 Superpowers。但真正拿过来用时，比如用 `grill-with-docs` 做 Lab1，马上会发现，它陷入无穷多你不想让它管的事情。尤其面对未知，你不知道它在干什么。有时 Skill 会反复疯狂地 fan out subagent，做一些你觉得没有必要的测试或 validation。这些在某些场景，比如真正到公司开发产品时是成立的，但最好自己摸索，有切身感受。

今天我也为大家切身摸索一下。我已经把编译好的 DeepSeek Harness 准备好了，可以问它，应该能够正常工作。不知道有多少同学使用过一个相对复杂的开源软件，并且真的动手改过它。在 pre-LLM 时代，把它运行起来都很困难。现在我完全是许愿式运行：从昨天到今天，在这台机器部署它，包括 vibe 一些东西，全部都是许愿式的。只要知道项目可能可以编译，就让它去做。

假想我们要实现一个 DeepSeek Harness，应该从哪里开始？从上一节课的 mini-agent 开始，大家应该还有印象。这就是一个 Agent Harness。几乎所有 Agent Harness 都遵循这样的循环，因为大模型推理是 Responses API，不管返回工具调用还是什么，都是一问一答，不管回答的是人还是工具。

这个 Agent Harness 能用吗？能用，它完全可以工作。周日在高铁上，我突发奇想：既然要讲 Agent Harness，能不能让我们的 Agent 做一个真正不 trivial 的任务？这个任务可能比较长，正好新模型发布了，我就给它一句话：“我要一个比例基本真实的南大仙林校区三维图。”你们有没有试过，有没有预期到它会输出这样的结果？

这还是很不错的，虽然有些地方不对。计算机楼有十层，这里的高度明显做得不对；有些又相对正确，比如杜厦图书馆的建模比较好，尤其从 top-down 看，楼的几何形状被正确保持了。

观察 Agent 的 trace，它是怎样做到的？因为网络上有很多数据源。我上学时就发现了这个宝藏，有个网站叫 OpenStreetMap，开放的地图，能找到各种地方的地图，而且很细。比如篮球场，它真的会画出篮球场的线。它还没有用全部的模型，只是从那里爬数据，再根据自己的想法建模型。

有些想法就不对：地图上可能没有东西的部分标成绿色，它说这是一块绿地。绿地可能是小公园，或者有椅子、可以休息的地方，但它把大门进来的地方铺满了树；大门也画成了楼。仔细看看，这可能不太好，需要给它更多提示词，比如：“把每一块区域单独划定出来，仔细思考这块区域的功能、应该是什么样，再精确建模。”它会花更多 token，比如十倍 token，把这些地方再修一点，就能得到更好的版本。

网上很多人不管用 GPT、Opus 还是 DeepSeek，说新版 DeepSeek Flash 的图形能力很强，也都是用这种方式。有一些 Skills，不停追着让它一遍遍验证。通过烧 token，从还不错的基础上，最终能得到想要的结果。我相信很多同学都梦想做一个南大版 GTA，在里面身临其境地突突突。如果想做，这就是很好的 starting point：已经有了三维模型，还可以 instruct 它，规定什么地方能走人、什么地方可以蹲点，构建游戏逻辑。

它完全可以工作，但不能作为产品。作为我在课堂给大家玩一把的东西，肯定可以。上一个版本假设网络服务不会中断，如果只是一两轮对话，感受不到这个问题。但在高铁上，它给我来了这么一出：已经跑了比较长的时间，有一些中间结果，突然网络断了，进程直接终止。150 行的 mini-agent 没有会话保存、恢复功能，也没有写网络中断后的重试。断了以后，只能从零开始让它继续，或者重新做一遍。这其实就是 essential complexity。

再往后想，如果做真正的 Agent 产品，比如 DeepSeek Harness，怎样应对 API 中断？首先需要重试，你们都见过 coding agent 各种重试的行为。这时又要考虑重试间隔。如果在美国数据中心访问 OpenAI 的服务，和在中国挂一万层梯子访问 OpenAI，是不同的网络环境，timeout 等设置也不一样。API 中断后，怎样设置重连、重试或连接中断的时长，又变成复杂问题。

一次失败后，第二次应该等同样时间再试，还是逐渐拉长间距？学网络时都知道 exponential backoff 这种探测特性。一秒后失败，再过一秒失败，大概率下一秒还是失败，可能就要等两秒、四秒、八秒，直到网络以分钟级恢复。像刚才出现物理世界故障，启动可能需要两三分钟才能重新回来，这都是很大的复杂性。

我让 AI 帮忙总结，它还说出了更多莫名其妙的东西：实际产品中，还会面临更大挑战。比如服务端和客户端可能不一致。客户端发起支付请求，服务端收到支付就把订单下了，因为还涉及和其他系统的确认，不能等所有事情做完后，再由客户端 close transaction，也就是等你收到后才 commit，它做不到。这可能是下淘宝订单、买机票，钱交给银行或航空公司时，transaction 就已经结束了。所以它会在服务端完成，服务端有非常复杂的架构支持订单的可靠完成。

但订单发出去后，手机突然断网，怎么办？设计这个产品时，就会看到手机上转圈圈。手机应用不能 crash，得告诉你网络中断了，现在订单处于未知状态：可能下单成功，也可能失败。因为和服务端缺少同步，客户端不能确定到底是什么状态。所以软件系统设计有很多 essential complexity，它就是复杂的，无法避免。

如果要设计 Agent 产品，而不是一个 150 行的 Agent，还涉及项目管理。Agent 可能同时在好几个工作目录工作，不管用 DeepSeek Harness 还是其他 coding agent，都可以做到。这就需要一个 dashboard，能在多个项目间切换。Agent 还要访问项目相关的工具、Skills，运行中工具调用需要沙箱和权限。回想平时 coding agent 向你请求 approve 时的产品设计，就会知道这会带来非常长的产品需求规格说明书。

我又让 AI 假装自己要做一个 WorkBuddy。这可能是老板的要求：“公司今天要出一个产品，对标现在卖得最火、和人交互的 Agent，调研 DeepSeek Harness、WorkBuddy，谁卖得最多。WorkBuddy 卖得最多，那就去做一个吧。”

AI 还是挺有智慧的。虽然今天讲的 DeepSeek Harness 走了完全不同的设计路线，但 AI 确实想到了一些有趣的东西。它先想典型应用场景、用例图，比如：“把这个文件夹里本周项目记录整理成周报，列出延期事项，生成 Word 文件。”这是普通人在办公管理中很常见的场景。

在这个基础上，它列举潜在应用场景，开始疯狂列需求点：历史检索与任务复用，这是 Agent 产品很典型的功能；还有模板与偏好、执行预算与用量、账号与数据管理、外部内容与指令隔离、用户反馈与问题诊断。实际上还会多得多，还有很多非功能性需求。

直接让 AI Agent 实现这些需求，大概率就会陷入 slop 状态，因为 Agent 有很强烈的倾向，要直接把任务完成，不会动脑子想未来还会发生什么。所以做产品和做 MVP 不一样，但 MVP 可以帮助你看到产品真正有什么需求。使用 MVP 时，假设会不断被 validate。像我的小 Agent 做了不切实际的假设：网络和 API 都稳定。一旦假设不成立，需求就相应膨胀了。

设计 Agent Harness 面对的真正挑战，其实是需求改变。刚才已经做了一份面向 WorkBuddy 办公场景的详尽需求报告，带着 Agent 写了五十万行代码，已经上线，突然今天 Grok Bot 火了。Grok Bot 是一种新的交互方式，可以把 Agent 当人，每个人有自己的记忆，可以拉群，让两个人协同工作，也可以规定每天什么时候做什么事。

Grok Bot 火了以后，会发现它的交互方式和刚才的需求完全不同。原来的详细需求规定左边栏是项目，右边有几种 view。突然有一天老板说：“下一个版本就按 Grok Bot 做吧。”怎么杀死一个程序员？改需求三次就可以了。之前所有需求的假设都崩塌了，交互模式的根基崩塌了。应对需求改变非常有意思。

不管大厂做了多好的架构，性能可能达到极致，也非常好地满足上一版的功能性、非功能性需求，但一旦这种摧毁性的事情来了，就必然开始疯狂拉通对齐、闭环沉淀复用，最后到下一个版本。这确实没有办法，因为大厂有交付质量要求，作了一个选择，希望极高质量地交付需求，所以架构可能相对保守。

相比之下，DeepSeek Harness 我没有装这个，但光速就不止一个人 release 了 `dsh-bot`，看起来和刚才那个像素级复刻：可以设置多个 Bot，拉群，群还有像群一样的图标，非常真实，可以和它聊天。甚至在这个基础上，可以 vibe 出很多原来没有的功能。

比如觉得 Grok Bot 哪一点不好？它希望给普通人用，不开放编辑和配置的权限。但对我这个 programmer 来说，就是想把 `config.yml` 拿出来改一下，或者把 prompt 给我改一下，因为我懂得怎样改提示词。可能 99% 的人不知道怎么和模型对话，所以 Grok Bot 是很成功的产品。但如果不满意，可以 vibe 一下，加上别的功能，比如 multi-agent 交互的 dashboard。

想象一个老板视角，又回到了这张图。本质上 Grok Bot 想构建这样的组织架构，以项目组组织人和项目。你可以做 CEO，每次只要和项目组或 CTO 交流：“去把这件事做了吧。”它再把任务一级级分下去。

有没有可能左边不做这样的竖栏，而是做成树状结构，代表你管理的部门，让你有老板的沉浸感和体验感？右边也不要这样聊天，压缩小一点，做一个老板视图，好像坐在办公室里，提供一点情绪价值。马上就有人可以 vibe 这种需求。

为什么讲这个故事？把时间倒回 2026 年 6 月 10 日，那时 coding agent 已经让大家意识到要变天了，有一些主流产品，比如 Claude Code、OpenCode，还有字节系的产品。那时没有 WorkBuddy，有 CodeBuddy。后来我知道，WorkBuddy 和 CodeBuddy 共享了整个 Agent 层编排的底层架构。

就在这个时候，我特意看了：2026 年 6 月 10 日晚上 11 点，谁说 DeepSeek 不加班？一个神秘项目启动了，里面什么也没有，连那时候还有 `CLAUDE.md`。这也是很恶心的需求点：一个项目想同时支持多种 Agent，就需要用它们都理解的方式组织项目文件。好消息是，今天不需要用 `CLAUDE.md` 了。

然后有一个“Link MVP requirement analysis”，有一个 microkernel architecture。你看，从第一天，6 月 10 日晚上 11 点，就想做操作系统、造航母。这艘航母究竟怎样造出来？就要回到架构。

直接对着需求文档，让 Agent 帮你做架构，它的注意力就会放在需求上。比如需求里有“工作区”，Agent 很自然会在架构设计中为工作区做一个 class，因为它不能设计一个什么也没有的架构，那样就没完成任务。然后会涉及工作区和其他东西的交互，这些设计肯定需要，比如和模型、Agent 层的交互。

工作区可以链接到 Session，也就是会话；Session 可以向 Agent 发送 chat；Agent 自己调用 Agent Loop 或工具做事，也可以把结果，比如绘图的 canvas，放到 Session。这里应该用数据库存放 Session，存什么东西？架构就开始出现了。这是非常自然的架构设计方式，大厂也经常这样设计。

但架构意味着没有免费的午餐。不管是这样的架构，还是 DeepSeek Harness 那样的架构，都是在受限和自由之间达成平衡。架构确定后，模块边界就有了。开发一个模块时，不用知道或只需知道比较少的系统其余部分如何工作。第一天把需求分成架构后，每个模块可以独立开发，架构一搭好，马上能启动大量 subagent，把产品堆出来。

但这些限制也限制了自由度。未来需求改变，比如 Grok Bot 这样的需求出现，如果架构不能适应，就会不断出现抽象泄漏，项目很难维护下去。

如果做得太自由呢？你说不喜欢这种非常典型的软件系统架构，要做创新架构：每个模块都是一个 process。不管工作区、Session、Agent 还是 UI，每个都是进程，进程之间通过 message passing 发消息。架构非常干净、自由，可以随便发消息。

它自由，但这个架构没有任何用，就是一个 Actor Model。说得对，可能确实能这样实现，但没有约束，比如消息该怎样管理。原来的架构规定工作区和 Agent 之间通过某个 API、某个队列，比如 Session 的 message 队列管理。接口确定后，就只能做这件事，比较容易开发。但自由的架构没有确定什么时候发什么消息，等于没有架构。越自由、越不受限的东西，越不好开发。

受限有受限的好处，自由有自由的好处。带着这个想法去理解所有系统架构，每一层架构设计都有取舍。

比如，操作系统上面的进程就是一个非常好的抽象，而且很自由。它就是为了让你能在上层搭建各种应用程序：浏览器、coding agent、虚拟机，任何东西。操作系统要提供这样的功能。但这种自由也意味着，仅仅为了到底用什么编程语言开发，人类就吵了几十年：什么语言才是最好的编程语言？现在“PHP 是最好的编程语言”这个老梗好像已经见不到了，在我上学的时候还非常流行。

高级语言也是如此。像 C 这样的语言越自由，就越能控制机器，但也会带来内存泄漏等各种麻烦。受限和自由没办法完美兼顾，只能在这个 spectrum 里取舍：限制做到什么程度，自由做到什么程度。每一种架构都有这个问题。

比如经典的 LAMP：Linux、Apache、MySQL、PHP。PHP 是世界上最好的编程语言。这是一整套方法和架构，引领了整个互联网世界至少十几年，WordPress 就是典型。这个架构很好，但要服务一亿人、十亿人时，它就扛不住了。从单机到数据库，每个点都是瓶颈。为了把它拆开，就有各种抽象泄漏：数据库先分库分表，让一个服务器扛着；最后服务器也扛不住，再把服务器拆开，架构就演进到下一个版本。

再比如 Event Sourcing。我们说它可能比较好：所有东西都是事实，以 append-only 的方式记录下来，其他人看到的都是事实的一种 derivation，概念很干净。但它也不是没有代价。当前状态完全由过去的历史推导出来，首先，要把性能做好，难度会更大；其次，有时我们真的只是想 hack 当前状态。

比如，教务员没有理由地想让你强行毕业。在一个月黑风高、没有人知道的时候，原本毕不了业的你悄悄就毕业了。这种操作在真实世界里可能是一个合适的需求，但在 Event Sourcing 里很难办到。你需要加入一个特殊的 event 和一套特殊的处理规则，叫“强行毕业”。这件事又在 persistent history 里面，会被审计到，不能再用“我也不知道那个时候怎么回事”来搪塞为什么这个同学能毕业，因为当时就知道是谁 commit 了这个 event。这好像也是一件有趣但有点危险的事情。

所以，每一种架构都有取舍：牺牲一些东西，得到一些东西，可能是系统解耦，也可能是完整持久化带来的好处，例如能回退到任何一个历史版本。总原则是，如果架构与需求匹配，你就会方便。LAMP 在单机还能处理应用需求时，就是最合适的架构，PHP 就是最好的语言；但假设改变时，架构就可能成为阻力。

我觉得某种程度上，人类社会的进步也是不断打破旧假设的过程。新产业诞生，旧产业消亡，新旧交替时有人才流转，有些人自然被淘汰，老登们就被淘汰了；大家接纳新事物时，又会有新机会。你们每个人都要经历很多身边发生的事情，才能真正理解。我小时候经历过很多次，包括国企改革，你们可能只是听说过；后来有房地产的崩盘，再到 AI 时代来临。从互联网、云计算到 AI，每一波浪潮都有新旧交替，这也是一种架构变化。

架构与需求匹配就便利，假设变化就需要更新的架构。在 AI 成为产业超级加速器的今天，这些变化可能会更有趣。这些是 AI 帮我补充的，你们有兴趣回去看 slides 就行。

我要讲一个具体的架构变化案例。不是 2010 年，是 2004 年，Jeff Dean 和 Sanjay Ghemawat 发表了一篇文章，某种程度上改变了 LAMP 中心化服务器的浪潮，叫 *MapReduce: Simplified Data Processing on Large Clusters*。这篇文章非常好读，只看例子就行。

如果要做大规模分布式计算，不要去写很长的代码，只要遵照一种受限的代码模式，叫 map 和 reduce。Python 里也有这样的 functional programming。Map 是说，我有一个 list，再有一个 function，就能把它变成另一个 list。Reduce 是拿着一个 function，不断应用：先拿第一个元素，再拿第二个，继续往下。如果这个函数有比较好的数学性质，例如结合律，就能先 parallel reduce 两部分，再 reduce 它们的结果。如果能把计算写成这种形式，就可以用这个框架。

它做了架构上的取舍，限制你的编程模型：只能先 map，再 reduce。当然，reduce 时有一些聪明设计，比如按 key 排序，中间有一个排序、shuffle 的过程。其余的系统实现藏在后面，不需要知道具体是什么。好处是只要写非常简单的程序。早期 Google 内部用 C++，`include` 一个 `mapreduce.h`，写一个 class，在里面规定 map 和 reduce 是什么，就像写普通程序一样。

只是你使用的不再是 pointer、list 这样的基础抽象，而是系统包裹起来、可能运行在不同机器上的抽象。可以在分布式文件系统上做计算，告诉它：“我要做 MapReduce，最多用 2000 台机器，每台机器每个 task 用 100 兆内存，跑吧。”它就能自动在很多台机器上跑完。

这是一个引领世界的设计。大家发现，有这样的抽象层，写分布式程序真的变容易了，而且还可以容错。Google 当时遇到的最大问题是，机器一多，整个系统就不可靠。运行一个很长的任务，例如给整个互联网的全部数据建索引，几乎一定有机器掉线或出故障。

以前 LAMP 的基本假设是机器是好的。你们在自己的电脑上做大作业，基本假设也是机器不会突然消失。如果机器突然消失，就摆烂，跟老师说“对不起老师，我的……”——用社会工程的方式解决。但 Google 不能这样，必须通过系统抽象解决问题。

它成功了，也失败了。这个限制只适用于离线任务，用起来也不是那么方便。如果想处理实时到来的数据，例如银行订单，当这些需求也走向分布式时，MapReduce 就没办法支撑，需要更高效的架构。今天的答案有 Spark 这样的计算引擎，还有 Flink 这样的流式数据处理。当然，Flink 与 Event Sourcing、functional programming 也有千丝万缕的联系。这是一个具体的历史案例。

讲了这么多，其实就是说：架构是受限和自由之间的平衡。如果要设计一个 Agent Harness，你的 first principle 是什么？我们看到第一个提交说，要做一个 microkernel，要做一个操作系统。操作系统意味着什么？它不需要知道每个进程是干什么的。UNIX 诞生时还没有桌面浏览器，也没有图形用户界面，它不需要管这些，但能把进程组合起来，让进程互相组合、互相使用。

所以它的 first principle 是：Everything is a plugin。所有东西都可以通过插件解耦。每个 plugin 有点像 actor model，但它并不是 actor model。可以把每个插件想象成一个进程或一个人，让它们互相发送消息，理论上就能实现任意架构。这个架构只是希望每个模块的 private state 都封在自己内部；模块需要交互，就发一条消息，对方可能给一个返回。

理论上，任何程序、任何软件系统，都能把模块当作进程提取出来，把模块间的函数调用换成 remote procedure call，也就是远程过程调用，任何软件都能变成这样。所以，光是这个架构是没有用的。

大家谈论 DeepSeek Harness 时，会提到它先发过一篇叫 Cordis 的论文，里面有大量公式。虽然 Cordis 也是架构的一部分，但今天不讲这部分。Cordis 负责服务解析、依赖激活，以及插件的 load 和 unload。如果把 DeepSeek Harness 想象成操作系统，这上面的东西就是进程。

我们知道，操作系统有进程管理。进程退出时，它持有的所有资源都应该回收，这已经是大家默认很久的事情。就像你们写 OJ 题，从来不回收里面的内存，因为知道操作系统会回收。Cordis 的设计也是这个想法，当然不可能把所有 side effect 都回收。

理想情况下，进程可以 declare 自己需要的资源，或者对系统产生的 side effect。比如，它依赖一些东西，这些依赖就应该自动加载；插件 unload 时，依赖的东西最好也能自动卸载。就像创建进程时会分配内存，进程被 kill 掉时，这些内存也要自动回收。这显然属于 plugin 的管理。

但整个 Harness 设计真正的难点在于协同。如果让插件随便发消息、随便协同，整个系统就乱了，没有实际好处，和每个模块都是函数、硬链接在同一个地址空间里没有区别；不协同，又没有用。

所以，真正有意思的设计，是要构建一个 Agent Harness 的世界模型。DeepSeek Harness 里还有一个非常重要的共享空间，相当于所有进程共享的空间，关键数据结构都存储在上面。基于进程，DeepSeek Harness 又构建了更多抽象。它没有特权内核，所有东西都是 Cordis 的插件，但里面有更细一层的世界模型，比如 core 下面的 Session。

如果要做 LLM Agent，应用无论如何还是以大模型为中心。它的 append-only Session Event 日志是唯一的 ground truth，模型历史不是存储下来的，而是通过 `deriveMessages` 派生。也就是说，它有完整的事件日志，这就是 Event Sourcing，它也用了 Event Sourcing。

在进程的基础上，它又做了一条 event bus，各种插件可以挂上去、监听它。这个世界有一份持久化的历史，其他能力都在这个基础上长出来。它还会做类型检查，有 service 的 definition、provider 和 consumer，以及一系列权限管理。

最重要的是，事件是扩展点，按领域分类。系统里每个插件都可能产生事件，放到 event bus 上。上面那些代码大部分是在规定消息格式、谁能往 event bus 上放东西，以及类型是否匹配。不匹配，TypeScript 就不会编译这份代码。就像禁止你任意往别人那里发消息，架构要施加限制。

发完消息后，还允许插件监听另一种消息。事件进入 event bus 后，监听它的插件会收到事件的 body，甚至可以修改事件本身。它相当于赋予了一系列原子能力，是一个小操作系统。每个插件在 bus 上都能看到 LLM inference 的状态，例如这次大模型输出了多少 token。

当然还有一些设计：有些大模型事件实际上还没有 commit，history 中可以有一个 open entry，代表这次还没结束，大模型不断往里面送新 token。这个状态还没有持久化，但依然能被看到，这样就可以实时显示。比如你们可以看到这里的 thinking，思维链在动态变化。这也是一个事件，但事件是动态的。这些是实现上的小技巧。

收到 LLM inference 这样的事件后，有的插件就能统计 token cost 和 cache hit。UI 又做了一层基于 slot 的抽象，可以把统计绑定到这个位置。最早内测时这些东西都没有，真的是白板一块；但第一天开发者群里就有同学说，来做一个 token 统计、上下文统计吧。他就能做出来，完全不需要干扰系统其他部分，因为这是一个不侵入的功能。只要观察 event bus 上 LLM 输出 token 的情况，相应更新自己内部的状态就行。

所以还是这个模型：希望大部分 state 都留在插件内部，只有希望别人看到的事情，才以事件的方式放到 event bus 上。这是一个还算自然的设计，但显然为 LLM 做了更多 specialization。

它有几大抽象：Session 是 `list[Event]`，Agent 接收输入、推动执行，还有用于装配的 UI slots。基本上有这些东西，你在 WorkBuddy 里想实现的功能就都能实现，比如把它改造成一个 bot。

DeepSeek Harness 有什么好特性？如果对这个聊天框不满意，想换一种更 fancy 的方式展示，完全可以。这个窗口本质上也是从 message history 中导出、计算出来的东西。你可以把它设为不可见，再放上自己的东西。在 DeepSeek Harness 里还有 trajectory。你看，这是整个 Session history 的两种不同投影：可以投影成给人看的 UI，也可以投影成给 developer 看的 trajectory，用来调试。

我随便让它调用一下 Bash。你可以看到工具调用的 payload 是什么、它干了什么、调用结果是什么，还有一些额外信息。它就是白板一块，但上面第一方的设计很重要。如果 event 或 Session 的设计崩了，后面的整个 DeepSeek Harness 就不可能维护下去。如果概念体系建得好，使上层插件绝大多数时候只需要 consume 很少、没有侵入性的事件——虽然它也有侵入的能力——就能在上面实现任何东西。

它发布后，我看完就说“震惊瘫坐，原子弹爆炸”。大家可能没有意识到，一个干净的架构能带来什么。它看起来很平常，例如 API 就是 Session：可以在 Session 上 append，也可以注册某个 event 的 handler，在 event bus 上监听；或者从事实中生成投影。刚才展示了 `session.deriveMessages()`，从持久化历史里导出 Agent trajectory 或 chat，光这个功能就非常好使。

还可以向 Agent 提交输入：`followup`、`inject`、`steer`。这些都是你们使用 Agent 产品时用过的。比如 Codex 正在推理输出时，你可以继续提问，但这个提问是应该等工具全部完成、这一轮全部完成后再 inject，还是等下一次工具调用，也就是大模型一轮 chat completion 或 response 后，就立即把新 prompt 注入？还是按 Esc 停下来再来？这是对 Agent 的操作。

还可以持续贡献动态上下文。通过 `ctx.on`，例如 `session/event` 这样的事件，可以 hook 一些还没有持久化的事件。有的事件刚进入系统时，我可以篡改。这种能力是整个设计里非常关键的一环，不再只是看完再推一条自己的新事件，而是可以把一个东西扔掉，或者在 `agent/pre-step` 这样的节点做一些事情，甚至往 Agent loop 里 inject 一些 prompt。

你们想想，如果在做需求时，会怎样实现？我希望每轮对话都把当前时区信息注入上下文；比如 Anthropic 要干坏事，还可能把电脑的指纹等信息注入模型上下文。这显然是一种需求。可以把它写进需求说明，然后直接写在 `build_context` 里。如果实现一个 Agent，肯定会有这样的东西，我那 150 行代码里也有。但也可以在 Agent 的 pre-step 时挂一个 hook，把内容改掉。

整体架构就是插件挂在总线上，有少量协作接口，每个插件的绝大部分状态都留在本地。但因为能感知全局 Agent loop、Session，又能看各种 projection，基本上每个插件都能按需得到想要的信息：当前 LLM inference 到了什么进度，其他插件做了什么。当然，还是以大模型推理为核心。

这个设计的一切都是为了插件生态。你们看到的 trajectory，只是第一方原生发布的一个非常 plain 的特性，但对开发者 debug 很有用。地基打好后，做任何东西都会很容易。

比如，想为它做一个 text UI。DeepSeek Harness 原生设计是 Web UI，因为里面有装配 UI 的 slots 等关键抽象，Web 能呈现对人类很友好的界面。但如果偏偏剑走偏锋，不喜欢 Web，就喜欢命令行，像我上课这样，那 text UI 是什么？把所有装配 UI 的 slots 扔掉，只要 Session 和 Agent。在 event bus 上听到所有 Session 相关事件，包括还在输出 token 的 open chat completion，然后投射到自己的命令行终端上。整个 Web UI 都不用动，甚至可以做一个与 Web UI 共享状态的 text UI。

比如我在这里说一声“hi”，它输出的同时，在另一个终端能看到一模一样的东西，是一个非常舒服的 text UI，还挺好玩。内测最早时，DeepSeek Harness 是有 TUI 的，官方 repo 里有一个，后来直接被移除了。现在有第三方的 text UI。

像 pdf-reader 也是 hook 一些生命周期。比如加载 tool 时，就把自己的 PDF reader tool inject 进去，通过 event 的方式管理。但这些都不是插件生态真正好玩的地方。

真正好玩的地方是：如果让你们来做，你们会想做什么插件？你们可能会说，这不就是 Codex、OpenCode，全部都长这样，我们还能干什么呢？你能干任何事。如果脑洞比较大，就可以想象，能不能把它武装成一个像 VS Code 一样的东西。

VS Code 的基本假设是一个工作区，也就是一个目录。在这个目录里，左边栏可以动态配置很多小块的边栏，比如 editor、browser，当然也有自己的插件生态。我们为什么不能做一个呢？这些是插件内部的状态，一个插件可以维护很多 UI 状态，这是它自己的事。我想打开一个工作区，就可以用这种方式管理它，还可以放在底下。

这是 Better Sidebar。想得到 VS Code 的体验，我可以在这里放一个 terminal，完全一样。这不就是 Cursor 的 Agent Mode 吗？它主要是一个聊天窗，而所有这一切跟插件生态系统里的东西都不冲突，因为它只是不断地看主 Session，维护一些自己的状态。我可以加 Git、加 side chat，还可以再加一个 chat，这不就是 Cursor？一个开发者用许愿的方式，就可以做任何他想做的东西。

这才是释放插件生态系统、或者说一个好架构真正能力的地方。DeepSeek Harness 专门给了一个 Creator Mode。它就和 WorkBuddy 这样的产品不一样：WorkBuddy 说，我有一个预设的需求，请所有人都在我的需求里面工作；而 Creator Mode 给了 Cordis 的权限。

一般一个 Agent 的 Session 只有 Agent 的权限，比如工作区目录的读写、Bash，后面可能还套一个沙箱。在全火力全开的 Creator Mode 里，它能看到这个世界，可以把插件拆了，也可以往里面加插件。也就是说，它可以在 Agent 一边运行的时候，一边往 event bus 上挂东西。这个能力一定程度上来自 Cordis 的动态特性：它要求插件的生命周期是全动态的。类比操作系统，我可以随时启动一个进程，也可以随时把一个进程杀掉。所以看起来它是一个白板，实际上是一个核弹。

为什么不做许愿式插件呢？你可以许愿，发明插件，这就是 Creator Mode。你们现在有想许的愿吗？还是回去再许？比如我对现在的 UI 不太满意，我试一下：“能不能在 token 消耗旁边放一个超大号的……”为了快，我把思考调成 off 了，还是调一个 low，让它思考一下。这些都可以用插件实现。

这里有 Token Usage。因为我们有所有的事件，所以还能实时统计近期的推理速度。现在这个“梁文峰时间”，推理速度比我早上还快一点。早上我 vibe 一些东西时，大概是 200 左右，现在已经到 250 了。它有很好的 dashboard；如果对这些东西不满意，都可以改掉，可以动态改变插件的行为。我们来看看它会做成什么样，我现在也不确定。DeepSeek 也有“雷霆大思考”的倾向，所以我把思考调低了。它开始了，不过我的上下文有些污染，有点糟糕。

你看到的这也是由插件管理的功能：是立即把消息放进去，还是 steer queued message，我可以打断它。现在它需要非常危险的权限，需要安装插件，我就 allow。这就是真正的许愿式插件。因为我在上课，所以要求它快一点，不要雷霆大思考。你可以在这里加入任何想要的功能。它并不是绝对可以随便插进去、随便组合，但这个能力对创造者来说，设计理念是不一样的，也更适合开发者。一会儿再看看有没有惊喜。

所有好处都是有代价的。代价是什么？我们虽然在 event 这一层做了统一对齐，要求都使用同一组 event，类型不匹配就不行，但插件自己的状态管理还是在自己内部。像刚才 Better Sidebar 的窗口、终端如何表示，都在它自己里面。当然，它也可以创建自己的事件，推到总线上，让别人看到。

但是插件和插件之间的语义可能冲突。比如我可以 hook，实现一个上下文压缩插件，把每一次的输出都压缩到一半。插件之间可能互相 interference。如果我加载十个自动上下文压缩插件，每个都压缩到一半，十次以后就大约只剩千分之一。任何输出都压缩到不能看，信息就全部丢掉了。

虽然它们可以组合，但先后顺序怎么办？一个检查输入，一个改写输入，到底检查在前还是改写在前，我们并没有规定。这与应用语义相关，essential complexity 永远不可能就这样解决。插件只是减少了一些 accidental complexity，也让做动态 UI 生成这样的事情变得更开心。

系统里还会有冲突的语义，比如两个 Hook，一个要求停止，另一个要求继续。Hook 运行到停止时，就被停掉了。这种架构并不解决这些语义冲突，你可能需要另一个机制，比如再放一个 blackboard，在需要时共享状态。有这种需求时，抽象就有局限，就发生了抽象泄漏。插件不是万能的，架构也不是万能的，但好的架构会给我们带来很有趣的启发。

只有这个吗？它还在思考。好吧，那就认为这也是一个驾驶舱。

真正的架构给我们带来的，是一整个软件生态。前面一直讲一个简化模型：确定需求，把产品 release 出去，然后挣钱。但 DeepSeek Harness 走了一条不太一样的路线：release 时，它 release 了一个 nothing，或者说只有一些基本的抽象和第一方的东西，剩下的交给开源生态。

上周北京有一个开发者活动，完全由开发者自行组织，跟官方没有关系，没有 DeepSeek 的人到场。我正好要去北京，就顺便到会场闪现了一下。接口简单、复杂性低、可以随便 vibe，就意味着在 DeepSeek Harness 的基础上可以长出一整个生态，你想要什么就有什么。

所以我自己对这个开源社区的感觉，是开发者被带歪了。如果我在第一方发布 DeepSeek Harness，可能不会拿这么好的东西来 vibe 一个高达驾驶舱，显然会 vibe 一些更了不起的东西。这样的 event bus 真正的能力，不在于接一些 fancy 的小东西、hook 一个事件来增强 UI，而在于一整个生态可以互相增强，比如很多工具可以接进来，工具之间还可以组合。

我第一个想接入的是 super app。它只需要一个非常小的抽象层。当然，super app 可能需要改造：首先要有 Web UI；没有也行，可以用一个 bridge 把它和 DeepSeek Harness 连起来。Super app 里总是有对象的。打个比方，我在 WPS 里做幻灯片，第一个操作是把一些对象锁住，比如第二页现在先别编辑；第二个操作是把这个对象 hand off，从总线上送到模型的上下文里；第三个操作是把修改后的对象从模型上下文里拿回来，替换回 super app。

只要对 WPS Office 做这样最小的改造，就给一个超级应用赋予了 AI 原生的能力，而且可以享受 DeepSeek Harness 插件生态里所有东西的好处。这是一个非常恐怖的能力：dsh 是一个很小、很薄、什么也没有的内核层，但它底下有一整个大的 AI 插件生态，同时任何 super app 都可以接入。

我今天花五分钟 vibe 了一个东西。当然没有改 WPS，但这个 demo 可以告诉你，任何 super app 在这个上面都可以。大家用过 Excalidraw 吗？可以拖各种东西，也可以输入“hello”。你就把它想成 WPS 这样的 super app，任何能嵌在网页里的都可以。我做了一个 bridge，能干什么呢？点击 AI，让它“在框里画一个 turtle，用一些元素和文本标签”。

这时候 AI 开始工作。所有编辑都可以照常进行，但这个对象被锁住了。所以对 super app，我的接口只需要能锁住一些对象，把锁住的对象 hand off 给模型，模型再把结果送回来。注意，因为放到了总线上，整个生态都归我。

有了。一个没有任何 AI 能力的 application，可以把任何对象以最合适的形式接入 AI。你想想 WPS：不知道你们有没有用过 Kimi、WorkBuddy 之类的产品，让它做 PPT。做了以后，产品团队自己还要做一个 PPT editor，让你拖框、加 comment，不满意再让它改。为什么不反过来做？这是一个生态，直接把它接进去就完了，这才是真正 AI Native 的东西。

你看，所有东西都可以编辑，这是 Excalidraw。不满意还可以再改，不满意这个龟壳还可以删掉。做得不错，这是 DeepSeek 的 Flash 版本。这样空间就大了，你还可以做一个 Blender 的 bridge。何必一定要 MCP 呢？只要做一个很小的 protocol，它甚至可以成为 DeepSeek Harness 的一个原生插件，专门做对象的 bridge。

你甚至可以切换到聊天。我只花了五分钟来 vibe，做得比较简单，就是这样的 AI 聊天框，完全可以把它和这里 bridge 起来。我可以回到这里继续编辑，画 turtle 的 Session 还在，高达驾驶舱也依然生效。这是第一个方向：大型 App 的 AI 增强。

第二个方向，因为 event bus 的特性，我们可以随便 hook，所以可以建立 Session 和模型之间的双向通道。只要允许模型输出一个 HTML 加 JS 的卡片，就可以把卡片放到界面的任何 slot 上。这个能力在哪里？卡片有 JS，意味着可以放按钮、输入框，甚至放一个 Excalidraw、WPS。理论上可以写一个 React component，把非常复杂的东西放在这里。

放进来以后，我允许某些 JS 调用往 event bus 注入事件，就能把东西注入模型上下文。我可以生成动态 UI，把 UI 里的鼠标点击事件和状态，通过一段 JavaScript 重新注回上下文；模型拿到上下文，又可以指导 UI 更新。这不就是 Generative UI 的一个应用吗？这个我也做了，虽然也是五分钟 vibe 出来的，还有很多细节。

只要做好一组约定，比如约定一个带特定标记的 `div`，输出里碰到这样的 `div`，就以卡片方式显示出来。我完全是许愿式的，跟插件说我要做这件事。稍微缩小一点，就能看到全部。它会生成一段带 JavaScript 的代码；现在所有代码每次都重新生成，所以长度会比较长，但总可以设计 DSL，以更好的方式复用已有东西，把它做得很短。

比如我现在可以跟 AI 玩成语接龙，以“惊弓之鸟”开局。看模型对话的过程：点击按钮以后，JavaScript 会往模型上下文里注入这样一句话，只需要字符串拼接，代码就可以做。模型开始输出，接“鸟语花香”，接完后可以生成一个界面的 patch。不过我现在生成的不是 patch，而是直接生成新卡片。有些 bug 不要紧，因为我关闭了思考。这个状态是带着的，带着“鸟语花香”。不思考确实还是有些问题。

完全是 vibe。想 vibe 任何东西，比如“做一个五子棋，要求五子棋状态在 UI 里，但所有下棋落子都是模型思考以后做的”。为了让它快一点。这里是“鸟语花香”“香火不绝”“绝处逢生”，我再来一个。

它的好处是可以配合一系列与 dynamic UI 相关的插件，比如怎样压缩上下文、管理上下文，甚至做上下文的 fork。插件生态一方面让我更好地与 UI 交互，省下上下文；另一方面，我甚至可以把整个 Session 的聊天框都不要了，针对一个任务生成真正好的 Generative UI。

来看，这次可以了，虽然有点 bug，五子棋下到线上来了，但我们试一下。它开了低的思考。这肯定不是成熟产品，但回想 ChatGPT、GPT-3.5 那个时候，我就算让它从 50 数到 100，它也会“50、51、51、51……”你会觉得现在这个东西又慢又不好用。但看到一种可能性，它能做到一点，就意味着一定有办法把它做得非常好。这就是架构。你看，它在这里下了一子。在创造模式下，这个东西能做出什么，完全取决于你的想象力，你就是许愿式地做这件事。

我们也可以了解一下：“不要再做了，你能看一下插件实现，到底是怎么注入的，对主干到底有多少侵入，有没有改动？”这样就可以深入架构。先许愿，达到预期效果，再让它告诉你，这是怎么办到的。我们再开一个 coding agent。这也是完全许愿，一把出。你别说，你很好奇，整个应用和 dsh 之间到底如何通信。现在需要的就是相信，从 first principle 上这件事做得到，然后大胆让模型做。

它是一个 Cordis 插件，被 dsh 放到宿主进程。工具调用不直接改画布，只是暂存到 store；点 begin 生成一个 job，把选区 ID 锁在画布上。这相当于一个非常薄的应用改造层，要支持对象的选择和锁定，并把它们 hand off 到里面。把应用做成 Agent 宿主插件，画布等于 Session，编辑请求等于 tool call，提交等于回合结束的 commit。完全没有侵入其他部分。

能和其他插件的能力组合吗？给模型注入上下文，这个有意思。因为 vibe 了动态 UI 插件以后，我需要给每个 Session 注入提示词。这个插件的使用有条件，需要生成一个带特别标记的 `div`。也可以理解为做一个 DSL，让它生成一个 `div`；模型必须知道，生成这样的 `div` 才能变出正确的动态 UI。

所以首先要给模型注入上下文。这就是 Cordis 整个生态——不只是 Cordis，还有 DeepSeek Harness 核心层设计的能力。它只要一个 context 的 system prompt 事件，在这里插入一段 1.5 KB 的协议说明，hook 住这个 event。这是插件唯一写进主动模型上下文的部分。

然后，从模型输出到 UI 状态的提取，不新增消息类型，靠标记加投影，也就是 event sourcing，完全是事实。我可以根据事实的历史读到输出里有没有这样的内容。插件同样检查 event，当模型输出结束，就知道里面有没有；有的话，就改变我自己的状态，比如 UI。我不知道具体怎么实现，可能是在某个 slot 里插入界面，或者其他方式，但显然不会侵入整个系统的实现。

它有一些服务依赖、Session projection 的回调和 system prompt。这里有点侵入，它加了一些自己的 library，浏览器、remote session、prompt、打包 profile，但完全没有动底层架构，只是依靠系统架构完成。

这个也类似，没有侵入。而且 DeepSeek Harness 通过 scope 机制加以限制：插件如果想干坏事，匹配不上它所声称的东西，就会自动 fail，相当于隔离开了。同样，它只注册一些事件，比如旁听全局的 assistant stream 事件，并做对象同一性过滤，别人的 Agent 不匹配。它在后台启动一个 inference session，只从里面拿结果，送到 Excalidraw 的画布里。现在没有刻意组合其他能力，是因为我完全只是许愿。

所以我为什么说看到了核弹爆炸？我看到了这样一个世界：在 DeepSeek Harness 上，一方面对接开发者。我觉得很多开发者，尤其群里的，是些无所事事的大学生，这也挺好。大学生显然没有我这么多 experience，我见过这么多软件系统的设计和实现，能知道它该怎么用，最大化发挥效能。但他们有时间，我没有时间 vibe code 各种奇奇怪怪的东西。开发者会开出很多神奇脑洞，有些可能比较小，比如高达驾驶舱，或者把 UI 做漂亮一点，像 Better Sidebar 就是很好的想法。

另一方面，可以有更严肃的厂商介入。剩下就看愿不愿意，谁能在这里挣到钱。至少这些东西全部是 open source。可以预见，在 AI Native 时代，如果我有一个做得没那么好的 WPS Office，功能可能只有它的百分之七八十，但能接入原生的 Agent Native 能力，我到底愿意用 WPS，还是愿意用这个？

因为应用接入系统以后，我面对的是个人的 Agent、个人的数据库、自己用得顺手的所有东西和内容生成器。就像我自己，是用 Agent 管理个人数据库的。昨天小红书被迫删帖，说是要保密。我需要填一些表格，那个表很讨厌，要填从 2021 年到现在发表的所有论文。你想，WPS 要填这个表，或者今天用 Codex computer use 填，还是要花一些时间。

如果插件生态里接了个人 database 插件，可能是我自己 vibe 的，就可以向模型提供必要的个人信息、发表论文、管理的学生等信息。Super app 需要填论文列表时，把任务往总线上一丢，剩下由这个生态里的工具、电脑、记忆和 Bot 一起协作，把必要的数据拿回来，一把把表填好。中间不需要 computer use，不需要多余的 token 消耗，不需要疯狂截图。这就是一个操作系统，可以在这里闭环完成非常多的事情。

这是我为什么喜欢 DeepSeek Harness 的架构，大家可以想一想，思路打开了，就能做很多有趣的事。而且在 AI 时代，不仅是这一层，每一层都可以。比如我现在还有一个要保密的项目，在做 Agent OS，你们可能看到了我发的招人帖子。我们和 DeepSeek Harness 的思路有点像，也是 everything is a plugin，但我们的 Agent OS 在它下面，可以和它保持并行，为它提供更多能力。在它之上，每一个 super app 怎么设计，可能今天又有今天的版本答案。
