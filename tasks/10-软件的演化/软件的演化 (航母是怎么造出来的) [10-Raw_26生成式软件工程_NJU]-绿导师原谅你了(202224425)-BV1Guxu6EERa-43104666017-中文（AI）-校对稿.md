今天继续讲 DeepSeek Harness。上次讲了怎样扩展它，从代码结构看到插件设计、Event Bus 上的设计，以及怎样用许愿的方式 vibe 各种插件。今天继续进入 DeepSeek Harness，不过感觉最近眩晕、瘫坐的频率又变高了。

今天早上起来，发现 OpenAI 声称找到了一个证伪 Exponential Time Hypothesis 的算法。本来说大概 $2^n$ 是 3-SAT 等问题不可能突破的界限，但它说找到了一个算法。它没有找到多项式算法，如果找到了，世界就崩塌了，P 就等于 NP 了。没有，但它把这个界限往下压了一点，颠覆了很多人对这件事的认知，同时还有一些非常大的结果。

所以我有一种感觉：上数学课、理论计算机课时，我们追求一种数学的美。再往后想，可能这种美是一种幻觉。它肯定是美的，有一个非常小的内核，从内核可以推导出有趣结论。举个和 Exponential Time Hypothesis 相关的例子，P 和 NP 的关系。什么是 P，什么是 NP？大家回想一下，保研面试时老师可能会问。N 是 not 吗？N 是 nondeterministic，在非确定性图灵机上。

很自然的问题是，为什么用 P 刻画 efficiently computable？为什么 polynomial time 被认为是有效计算，NP-complete 就是难的计算？中间还有没有别的？为什么用 P？想想 $n^{100}$，它没有任何意义，$n=10$ 时，就不可能在现实计算机上、reasonable 的规模下跑出有用结果。$n^2$ 和 $n^{100}$ 在 P 上等价，或者说都属于 P，这是因为我们追求数学的美。

定义 polynomial time 的好处是，在一个多项式时间算法里，比如几重循环，可以调用另一个程序，相当于做函数调用。只要被调用的函数也属于 polynomial time，而调用方在 polynomial time 里只能生成 polynomial 长度的输入，把这个输入交给另一个函数，再经过 polynomial time，可能是平方、立方、四次方，返回的结果依然是 polynomial 的。

这种美感是，可以自由使用已有算法库中的算法，无论多少次，只要整体还是 polynomial time。它在 composition、函数调用的意义下封闭，允许我们简化很多数学运算，推出很多结论。但某种程度上，这是人类为了弥补大脑只能想这么多、只能装下这么多抽象，而做的 workaround。

试图理解某些问题是否必须用 $2^n$ 才能解决时，其实不知道算法里有什么有趣的 trick 可以压低复杂度。像前几年，人类解决了一个近似 linear time 的网络流问题，会觉得这是非常 surprising 的结果。本质上网络中任何两个节点都相关，却能用近似线性时间得到结果。我们对各种数学问题结构的理解，其实有很大缺陷。

理论计算机科学真正想问的问题是：给定一个计算模型，比如 RAM Model。虽然它和今天有 memory hierarchy 的计算机还不一样，但可以设定一个 CPU，有 load、store、加、乘等指令，每次花一个周期从 RAM load 或 store。这样的计算机可以 formalize。我希望你们学完离散数学，就能写出“这台计算机是什么”的形式化数学定义。

问题也是 well-defined 的：在这个计算模型里，允许计算机运行 $k$ steps，能解决的所有问题是什么？这才是真正关心的。造一台计算机，到底什么问题能做、什么不能做？但研究算法用的 polynomial time，是非常粗犷的近似，很多细节被抹平了。

用这种计算模型时，每条指令必须精打细算，小心考虑数据放在内存什么位置。位置可能没关系，但怎样排布、要不要压缩，都会对 $k$ 步产生很大影响。对 polynomial time 这种松散、仿佛随便调用别的函数都不付代价的计算模型，就无所谓了。所以人类很大程度上一直在解决比较干净的问题。

生物学有分类，门、纲、目、科、种、属，其实这也是不对的。人类花了很长时间构建物种的 family tree，这个网站建得很漂亮，代表人类文明。但从现代生物学意义上，这样的树状模型受到很多挑战。猫和狗、某些植物，在现实世界容易用分类学区分。我不是这方面的专家，但仔细看微观生物，界限就很模糊。要定义它们是否来自同一个祖先，甚至可能不是 tree，而是 graph。

实际世界的结构可能很差。有一种可能：我们在物理世界里，恰好处在非常平坦的区域，或者在某个宏观尺度上它变得比较平坦。这种平坦使得我们能够压缩。

昨天我和 GPT 聊天，想一个问题：对称性推导出了能量守恒。物理规律在不同时空应该保持一致，只要这个 first principle，就可以推出什么叫能量。应该说，总会有一个守恒量，我们现在叫它能量。但如果世界结构很差，可能只是我们恰好处于有守恒量的区域，经验能够被压缩，压缩就产生智能。有一种因果关系是，正因为处在这个区域，scaling law 才给我们带来各种东西。很有意思，AI 带着我们想到很多夸张的东西，当然今天不讲这个。

我有一个暴论。最近刷我的小红书，会看到我发了很多暴论，要解释一下。以前上大学，是家庭投资教育。中学时也是某种投资：疯狂学习，考上大学；大学培养人才，企业再把你们买走，你们的劳动力有用。但现在这个循环越来越困难。如果 senior 带上 Agent 超过 junior，资本家可能就不想招应届生了。为了面对竞争，先稳定优势，后面交给后人的智慧。

毕业时的职场压力会很大，慢慢大家会发现，招一个 Agent 也可以，为什么要招新人、花很长时间培养？我知道大家很焦虑，有一个答案：可以用 AI trajectory 证明自己。

从现在开始，所有 AI trajectory 可以做压缩，去掉不必要的信息，比如 tool call 的输出；保留生成的图片等有用 assets，得到属于自己的时间轴，上面有做过的所有事情。现在干任何事都问 AI：今天吃什么，南大和园有没有开新店，都可以问。我上周去 CNCC，到了别的城市想走一走，就让 ChatGPT 帮忙找，告诉它位置、偏好、想找什么，让它做尽可能 comprehensive 的搜索，给出选项。

AI trajectory 上首先能看 facts：今天聊物理，明天聊天文，你的想法是什么，AI 给了什么，你的反馈是什么？最终生产的代码能不能运行？哪些想法来自你，哪些来自 AI？这些 facts 都可以审计。

当然，上有政策，下有对策，总有办法抵抗。但这种不可变日志应该更方便用人单位审查。它可以随便挑：“2026 年 3 月 10 日，你和 AI 讨论了这个东西，还有没有印象？用今天的眼光怎么看当时的对话？”随机采样时，如果对这件事有记忆，能说出正确的东西，几乎就肯定是自己做的。就算伪造 trajectory，最后进入面试，也一下就被打回原形。

不可变记录成了非常好的人物画像，甚至能评估成长潜力。现在难以区分两种人：同省同卷，高考分数一样，各科或题目分布可能不同，但都进入南京大学。真正想评估的是潜力：起跑线相同，有的人进大学就是人生巅峰，此后再没学进什么；有的人能力不断增长，发现一些模式，比如怎样与 AI 交流更好，把 Skill 沉淀到 Harness，找到好的方法。日志中可以看出方法学、人生观发生的改变，这些细节都能在 trajectory 上发现。

如果愿意，学生没有商业机密，学习的都是人类已有的东西，可以把学习历程交给用人单位，全面评估能力和潜力。这好像没有隐私。现在觉得脱了衣服就没隐私，实际上 AI 时代的 trajectory 对内心有点像思想钢印，在窥探内心，知道 potential 在哪里，甚至预知未来。仔细想，这非常恐怖。

但在现在这个时代，它又非常 seductive。保存下来，用合适方式投影成简历，至少短期内会得到回报，相当于和魔鬼订了契约，出卖自己的灵魂。如果把我所有和 ChatGPT 的 trajectory 全部拿出来，也有把灵魂出卖给魔鬼的感觉。某种程度上，我知道 OpenAI 能对我做到什么程度：我在世界上的位置，它真是了如指掌，因为所有生活都交给它了。

再往后想，以后也不需要通过见面聊天交朋友了。我经常有这种体验，有同学找我聊对 AI、Agent OS 的看法，聊着聊着开始收敛，最后达到“英雄所见略同”的状态：“原来你也是这样想的。”有些分歧，最后达成一致。

以后有了 trajectory，不需要花很长时间和别人辩论，只要派出双方的 Agent 先聊一聊，立即就知道观点一致和不一致的地方，再展开辩论，之后由 Agent 增强。我现在想任何问题时，都觉得 AI Agent 代表这个领域里的所有知识。我有一个比较粗糙的想法，AI 能补全无数细节，甚至告诉我哪些已经被别人想过、论文是什么，哪些想得不周到，哪些可能大家还没想过。人类扩充知识的速度会非常快。也不知道哪天突然全人类都被斩杀了，那再另说。

我觉得它带来一些好的 side effect，可能成为颠覆性产品，比如匹配交友。Personality、人格已经编码在 AI trajectory 里，只需要由 OpenAI 分配对象就行了，开个玩笑。这是非常恐怖的世界，但至少对我而言，有种无法抵御的倾向，想把自己交给这样的 AI，因为能在过程中获得优势。AI 一方面窥探内心，另一方面不断给正向反馈、强化我，可能让我在竞争中获得优势。这值得大家思考，也算来上课的一点小 reward。

至少可以这样保持隐私：只和 OpenAI 或 DeepSeek share 秘密。最终可能需要好的 Skill，把 trajectory 蒸馏成简历或网站，让用人单位眼前一亮，给一个好 offer。当然，一旦大家想到这件事，就会烂大街，进入恶性内卷，又会 reward hack。但如果作为世界上第一批意识到的人，竞争者还没涌入，提前做了，就能少一点 reward hack，更多追寻内心。

我觉得上学本身就是期货投资，把青春都给了大学，毕业却找不到好工作，会有很大落差。以后真有可能贷款上班：先承诺超过 AI，交保证金；一段时间里，在 mentor 带领下超过 AI，给公司带来价值，就得到回报。如果最终评价是始终不再成长，保证金可能就不退了，真有可能发生。也许会走向类似核不扩散条约的东西，AI 能力不能再增长了。Anthropic 和 OpenAI 就在讨论这件事，但好像没有更缓和的趋势。这是一些有意思的思考。

回到 DeepSeek Harness，刚才是今天看到新闻临时加的内容，和大家分享。说它是操作系统，Everything is a plugin 意味着内核不带实际功能。操作系统是什么？是 process 的 API，通过 spawn 或 fork 创建进程，有处理系统对象的指针，比如 handle 或文件描述符，通过文件描述符 read、write 文件内容，管理 persistent 数据。

DeepSeek Harness 有点像这种操作系统：什么都没有，但有 Event Bus 和原生插件，规定怎样和 Agent 交互，比如 `agent.inject`，怎样和模型上下文交互等。这个航母很有意思，已经造好，但上面的飞机还在试验，不知道能放什么武器，现在只有一些试验飞机，还没有类似今天航母战斗群的概念。

我愿意期待这个生态怎样长大。最终成功的未必是 DeepSeek Harness，但围绕 Agent 产生的生态会让每个人用得更方便。好像 DeepSeek Harness 要发移动端应用了。如果 PC 长期开机，移动端和 PC 建立通道，PC 就能一直后台工作，像 Grok Bot 一样，只是用自己的 PC。我觉得这在中国是很好的模式，一定是我们的未来。

比如回去在 DeepSeek Harness 上许愿做一个 Agent trajectory、人物画像。Everything is a plugin，很容易监听各插件行为、人和插件的交互、插件与上下文的交互，包括把模型的上下文 persist 下来，再做投影，做一个功能叫“实时简历”：每天自动更新，不需要自己维护，属于自己画像的简历，可以有很 fancy 的界面。

在 GitHub 点开一个人，能看到贡献墙、时间轴，一块一块的，颜色越深表示贡献越多。比如今天提交五次就是深绿，提交两次是浅绿，摸鱼什么都没干就是空白。当然也能作假，让 Agent 提交。我现在的墙非常绿，因为提交都是 AI 帮我做的。可以把简历实时投射成这样的东西。

插件生态像操作系统。UNIX 诞生那一刻，做梦都想不到今天会写 `cat` 什么，再管道给 ChatGPT 这种用法。用法一直在演进。以前可能是 too long, don't read，管道给 pager 查看手册。生态的未来很有意思。DeepSeek Harness 未必是活到最后的产品，也许是商业公司产品，但构建生态、航母的生态肯定是未来。所以今天要讲航母的故事。

造航母很难，中国第一艘航母严格说不是百分之百中国制造，买了一艘苏联航母，再做改装。我什么时候意识到这件事？2019 年去了 San Diego，那边有博物馆。我有一张同位置的照片，从这里看 USS Midway，中途岛号。它 1945 年下水，下水时好像二战已经结束，日本投降，不需要再去太平洋战场打日本人。后来服役很长时间，1970 年代应该经历现代化改造，应该是 1992 年海湾战争的旗舰。

当时走进航母，第一感觉非常震撼。我做软件，这样复杂的系统，不知道怎样能构建出来。这是内部老照片，基本是 1945 年下水时的状态。里面管线要走蒸汽，不像现在可能大部分都是电器，有电就能驱动一切，只要电线就可以。那时还有蒸汽、通信线路、电，更重要的是损管。航母是战争机器，随时可能受鱼雷、轰炸机袭击。

我记得当时的志愿者，其实是曾在航母服役的老兵。我很好奇，问这样一个系统出现故障，该怎样维护？当然他肯定不知道整个系统怎样构建。老兵亲口告诉我：设计都是非常天才的人做的，他们完全不需要知道怎么做，但每人会拿到一本操作手册，明确写着遇到什么情况应该做什么。

就像飞机，玩过模拟飞行就知道，有非常长的操作手册，什么时候做什么，发现什么做什么。比如某处起火，要把几号阀门从什么状态改成什么状态。设计者已经推演各种可能，使航母能真正发挥战争作用。那时也理解了，中国有那么多船，为什么造航母显得那么困难，它是战争机器。

真正最有启发的是，2019 年在航母甲板最底层，有一个陈列柜，展示从美国海军最早的第一艘航母到今天最先进航母，怎样一代代演化。所有航母都不是第一天马上造出来的，追溯到最原初的点，那个点可能非常简单，再不断演化。今天就是讲软件演化的故事，当然也会看 DeepSeek Harness 的演化。

先看航母怎样演化。这是 1945 年的 USS Midway，再往前推，古代文明都有桨船、帆船。长期几千年演化，有足够好的材料、足够多的经验，发现把船造成这样，就可以海上长途航行。Santa Maria 原来是商船，1492 年成为哥伦布首次发现新大陆的旗舰。这个船大家还可以理解，了解一点会发现上面都是机械装置，某种程度上是人类可以驾驭的复杂性。

再往后，你们有没有看过《泰坦尼克号》电影？没有，我们有代沟，这是我们那个时代最火热的电影之一。Titanic 之前，比如 1811 年的 New Orleans，新奥尔良号，沿着 Ohio River、密西西比河，1812 年抵达新奥尔良，是高压蒸汽的汽船。轮船为什么叫轮船？因为轮子在外面，不像今天螺旋桨藏在水里看不到。

世界上这些东西都是平滑演进的，有点像人类的局限。Everything is a state machine，我们总是从一个 initial state 开始，不管 repo 也好，受大脑和物理世界实验的限制，任何时候只能往前做一个小 delta：发现一个结构有用就加上，没用就减掉。

可能某个时期，桨和帆一直并存。后来远航时发现桨没用了，就去掉。也可能某个时期，外面的轮和螺旋桨同时存在，终于发现不需要这样的轮子，只有螺旋桨就够，轮子就消失了。不管航母演化史还是什么历史，人类都是一点点平滑地把大的东西造出来。

汽船越来越好，因为能挣钱，大家就会研究更好的汽船。那是 1811 年，从 1492 年、1811 年，再到 1913 年。

这张图是我那天收获最大的一张。它讲了美国第一艘航空母舰、试验型航空母舰 USS Langley。它并不是现在这种真正意义上的航空母舰，而是直接从运煤船改来的。所以，航母不是一天造出来的。

看运煤船，你可以想想泰坦尼克号，两者很像。再看泰坦尼克号和这样的蒸汽船，烟囱在这里，又是平滑演进的；继续往前看，也是这样一点点演进。然后出现了一个很天才的想法，又是一个很小的 delta：运煤船反正能载重，能不能把上层运煤的部分换成木质甲板？这不就成了跑道？一句话：能不能把机场搬到运煤船上？

接下来就是推理模型——人类工程师模型的推理，然后做实验：计算跑道多大才够，飞机放在哪里。如果是机场，在边上修个厂房就可以，但船上肯定不行，应该放在中间。船的空间有限，要尽可能利用，所以甲板在上面，飞机放在下面。这时就需要电梯。

电梯一般在航母甲板的某个位置。现代航母一般放在侧面，或者有多台；那时是在甲板后端有一部，用来上下运输飞机，运上去后就能起飞。一直到二战，航母飞机的起飞速度都是很大的瓶颈，因为要先从中间的机库运到甲板，才能起飞，没有很大的并行“算力”。

这是一些有意思的老图。USS Langley 的升降机把上下层连接起来，运输飞机。这是一个实验性的想法：把机场放到船上。等到第二次世界大战，日本人和美国人在太平洋战场上证明了航母的作用。这里也能看到电梯，侧面应该还有一部，这应该是使用钢甲板的航母。

演化过程里，不仅有比较大的、significant 的架构改变：重构，加上一个之前所有船都没有的巨大 feature，把它改造成机场；也有很多小改动，例如管线设计。甚至两个管路谁在左边、谁在右边，都可能影响船的可靠性。某条管路通高热蒸汽，保温不好，可能会影响其他东西。第一版设计没考虑到，第二版就把它做了。所以，不仅有架构改变，也有比较小的 bug fix、子系统重构。

看起来我讲的是航母故事，其实是任何系统设计时都会经历的通用过程。当然，我们也在造航母了。这个链接是什么？这是我在造航母的链接。我们也想造一个像 DeepSeek Harness 一样的东西，不能打太多广告，毕竟是上课时间。

我们大概处在这个阶段：造出了一条可以起降飞机的航母，但还有很多问题。AI 时代很有意思，造航母的方式变了。以前人类用了几千年，从独木舟开始，一块木头挖掉一块，人坐上去就是船；然后发明桨、帆、舵，发明各种东西。今天有了一个能力无限的 chain-of-thought 模型，可以从一个起点开始，直接大跨步往后跳。

不需要把完整的东西都做出来，可以先做 MVP。原型试验成功后，随时能回到之前的点重新构造。这是 AI 时代的软件开发，是许愿式编程：直接许个愿，先看它造出什么，再一点点沿用比较严格的过程，把每个东西做好。

所以，我们也在造航母，承诺做一个和 DeepSeek Harness 一样好的操作系统，一个真正能支撑生态的操作系统。有兴趣的同学可以读一下我公众号的征友帖，再找我聊一聊。属于夹带私货了，开玩笑。

我讲了一个软件的故事。那天在 USS Midway 上的收获，可以说是那些年都没体会过的、突然顿悟的时刻。每个人都是这样，又回到 Everything is a state machine：你是随着时间轴成长的人。一开始可能没展现出什么，突然有一天领悟一件事，就不断提高。

相信你们每个人都经历过这种顿悟，也许记下来、写一篇日记，后来记忆就尘封了。经过三五年，可能想不起那一刻；有天突然回想起来，又重新想到当时的启发，在积累知识中不断进步。人是这样，软件也是这样，任何复杂的东西都是这样。

软件早期通常只有一个很简单的 idea。看到一块木头，能不能挖掉一块，从河这边到那边？一句话的解释，试一试，就发明了船，再继续往后。我们印象中成功的软件，一般都是解决了真正的问题，而想法可能很简单。比如 Linux：“我就是想克隆一个免费的 UNIX，供大家用。”功能就是 UNIX 的功能，一个简单想法。如果走在正确道路上，确实能解决真实问题，就可能通过刚才那种不断改造的方式，一点点成功。

AI 有一个问题：它能往后跳得很远，也会设计一些架构，但在之后的维护里，每次修改都越来越难。随着 essential complexity 增加，一开始的架构可能就是错的。你们跟 AI 编程时，应该经常有这种体验。人类历史上，很多架构经受住了时间考验，同时也有很多部分被重构。就像船从真的有轮子的“轮船”，发展到今天仍叫轮船，却没有轮子。

这就是软件的时间维度。你们上大学学 computer science，为什么要上基础课？很大原因是，要学习一些软件系统早期的设计，以及它们怎样随时间演化。

我觉得调度器、Python 的例子都不是特别好，AI 还是没办法共情。当我想谈软件演化时，航母显然是更好的例子，Kubernetes 可能也不是很好的例子。但不管怎样，你们入学时可能就没见过 Python 2，也没用过 Python 2.7。我是从那个时代过来的。Python 2 和 Python 3 不兼容，其中一个很有意思的语法是，Python 2 的 `print` 后面是空格，它是一种内建语法。

最开始可能就是“我这么随便一做吧”，但 `print` 加空格给 parsing 还是带来了一点麻烦，比如 `print 1`。到 Python 3，`print` 必须是函数，不再是类似 keyword 性质的东西。你能看到，第一天设计一个最小软件系统、想做一个人类好用的编程语言时，设计师觉得 `print` 一定要好用，因为最早几乎除了 `print` 就没别的功能。他不会想到今天整个人工智能生态都安在 Python 上。

如果学习时跟过一个软件的发展，就能体会到，这个世界一直在做同样的事。其实我们一直用简化版本理解软件。Linux 0.11 真的很简单，网上到现在还有教程。现在你们学操作系统，应该从 xv6 开始。Linux 0.11 什么都没有，没有所谓 advanced technology。

很多课会讲今天什么东西多牛逼。我们是什么时候开始不怕比较现代、比较困难的东西？当隐约知道今天的航母虽然复杂、厉害，但中间一定有平滑演进的过程时。如果不知道厉害的东西怎么做出来，就回到还没有它的版本，回到独木舟，再看一点发展历史，看它怎么被加进来，马上就知道了。

某种程度上，我觉得“定义、定理、证明”这种学数学的方式有点反人类。它直接告诉你“这个东西自己去悟”，却不告诉你人类走了多少弯路、失败了多少次，最后才突然发现正确路线。

倒回去看 Linux 0.11，就很简单，直接能看懂。所谓系统调用，`read` 像一个函数调用一样进来，执行 A、B、C 三个操作，再回去，像 xv6。我大概在 Linux 2.6 时期进入这个世界。到今天，Linux 已经非常复杂，人类也理解不了。但我理解它时，很多时候还是回到最原始的 Linux 2.6：如果在那里做这件事，会怎么做，好在哪里、不好在哪里，今天又应该怎么做？甚至绝大多数问题都可以回到 Linux 0.11 的模型上考虑。

比如，想通过系统调用向操作系统要一些信息，是不是一定要穿过操作系统边界？有没有可能，操作系统直接给一页数据，把这页同时映射给应用程序，双方共享访问？当然应用程序最好不要写它。哪些信息可以这样做？在进程地址空间放一页，比如 CPU ID、当前时间的秒数。操作系统每秒写一次秒数，进程创建或切换 CPU 时，把当前所在 CPU 的 ID 等信息放进去，再把这页共享给用户进程。

可以先在 Linux 0.11 里把这件事想清楚，再考虑这个 feature。这有点像 Git 和版本管理。怎么理解复杂软件系统？直接看今天的某个 feature 看不懂，没关系，想想能不能在最早、或者某个能理解的版本上加上它。然后做一个 `git rebase`，不停把这个 feature、这个提交往后挪。

这样就能知道，在历史演化里，加上某个调度算法，对这个 feature 有没有影响。没影响，就过去了。你会发现，历史里引入的大部分东西，都与这个 feature 没关系。因为如果全部搅在一起，软件根本没法维护。架构设计得好，就一定把复杂性分解了。Essential complexity 有交互，但一个新 feature 与软件绝大部分的耦合通常相对松散。

只需要知道，在几个关键提交上，这个 feature 与谁打架了。那就不能只用最简单、理想的模型理解，而要理解它们怎样打架，冲突怎么解决。就像数学，人类走了几百年弯路，最后发现某两个东西应该连在一起用，于是发明了很多东西，例如 group theory。

这也解释了为什么 pre-LLM 时代说程序员有三大浪漫，应该是这三个：自己做操作系统、编译器、数据库，当然也可能是做 CPU。

今天的答案变了。你们看那些投 AI infra 的简历，同学都说在 nano-gpt、nano-vllm 上改了什么，比如迁移到多卡；哪怕只有几个树莓派，或者 RK3588 这种带 NPU、带加速器的小卡，拿四张卡做并行推理加速，接上魔改过的 nano-vllm，也是有意义的，都可以去做。只是你们可能没有意识到自己在做什么。我今天把造航母和你们的学习，都用一个 Git model 解释了。

我觉得这其实是人类的局限。回到一开始说的“震惊瘫坐”，人类只能理解简单的东西。如果航母、软件、DeepSeek Harness 就以当前状态摆在那里，让你去看，尤其作为新手，会感到无尽的复杂性。但通过理解发展历史，再 rebase 想了解的 feature，就能理解任何东西。这很有意思。

自然，软件演化就成了研究对象。Git history 是一个宝藏，因为有了计算机，我们才可以从初始状态开始，完整记录人类创造东西的过程，虽然人类很早就一直在做这些事。

AI 时代，作为还能守住人类最后一点创新、创造力的人，我们真的应该做些更大的事。比如，能不能构建数学发展历史的 Git？我不知道 OpenAI 或 Anthropic 有没有在做类似的事。能不能构建造船、造航母的历史脉络，或者把人类知识历史整理成像 Git 一样的东西？虽然比喻不太恰当，但也许能整理出分支间 rebase 的关系。透过软件工程能看到任何工程，不过这是软件工程课，还是讲软件。

今天讲了这么多，带来一个推论：不管历史是不是线性的，这些东西都是一个个提交组成的，每个提交都是一个小任务。这是一个非常关键的基本假设。绝大部分提交都是 bug fix、小 feature request 之类的任务。很自然地就会问：AI 能完成吗？

SWE-bench 是这个系列里知名度最高的工作之一，也有 Pro 等版本，现在还有 Terminal-Bench 这样的基准测试，衡量模型在软件工程、GitHub issue 任务上表现多好。我不知道这些论文作者有没有意识到，SWE-bench 这样的工作在历史上的地位。它问的是：大模型能不能把一件小事做好？当时答案肯定是不能。

这应该是 2023 年的 paper，GPT-4 的时代。你看，还是给模型一份输入，而不是 workflow。那时还没有真正能跑起来的 Agent，虽然已经有一些想法，想试试能不能成，因为 GPT-4 能力很强，但幻觉也很严重。Model input 说明要做什么、issue 是什么，有一个 gold patch、一个 generated patch，以及一系列测试用例。

测试用例也不能说完美。我们仔细研究过 SWE-bench，它绝不是完美的 benchmark。很多任务是 fix 一个 bug，而 bug 来自代码源头的一些小设计问题，以至于要不停修。作为人类，我更倾向于 refactor 代码，而不是只 fix 这个 bug。但不管怎样，它是明确的任务，有明确反馈，能评估做得对不对，因此能评估大模型做好一件小事的能力。

我们看看历史里的 Table 5。Claude 2、Claude 3 Opus 在当时都是顶流模型，虽然 Claude 只能声称自己在某些专业、垂直领域比 OpenAI 好一些，因为当时 OpenAI 的 GPT 如日中天，没有人能打过。你看这个惨不忍睹的比例：Claude 3 Opus 的 resolved rate 只有 3.779%，结论是完全不行。

我觉得这个方向最有 vision 的地方，不是又做了一个 benchmark。听课的同学可能有人在课题组研究 benchmark，每年也能看到浩如烟海的 benchmark paper。但站在人类的高度回看，真正的问题是：做好这件小事，价值有多大？

在软件演化、工程演化的意义上，如果小事能做得非常好，就意味着演化路线里的绝大部分东西都跑通了，因为绝大部分任务都是小事。从 GitHub 某种意义上随机采样，大多就是一个 issue：“今天程序 crash 了，能不能修？”“日期原来用这个格式，但计算可能不精确，没有算闰秒，最好再加一个星期。”能不能对功能做一点改进？日常开发绝大部分时间都在干这些。

所以 SWE-bench 很好地代表了这些小工作。它告诉我们，如果有一天 SWE-bench 被解决，意味着工程里绝大部分 tedious 的事都被解决了。它其实隐含了一句话：如果 SWE-bench 刷完，初级工程师就被斩杀，低级工种全部被斩杀。它预见了今天大家焦虑的情况。

我们还可以问：软件工程流程里，哪些东西没有被 SWE-bench 覆盖？比如 initial state、initial commit 时，都会有一个计划。要造航母，脑子里大概有个想法，想造这样的航母。决定后建一个 repo，放入初始状态和计划，这件事不好 benchmark。

软件发展到某个程度，也会有这样的情况：代码写得像 Slop，逻辑非常复杂，是因为设计时两个模块没解耦，写代码必须同时带着它们的状态，写出来就很恶心。为了评价方案，我们会把整个模块一起重构。重构完，bug 就消失了，那个 issue 根本不需要再 fix。

小事解决后，还有刚才说的大事：终于有一天，做太多琐碎 bug fix，受不了了，开始重构。重构意味着架构变化，可能只是局部。代码总体有一个设计架构，可能很难改；比如 Claude 以前把 Bun 从 Zig 全部迁移到 Rust，是非常疯狂的事，竟然没有闹笑话。我当时觉得，这可以吗，不会留下两个非常糟糕的 bug 吗？没有。当然也与项目结构有关。如果迁的是 MySQL 这种，我估计就不行。

有顶层设计架构，也有每段代码里的架构。甚至一个函数写成 functional code，还是 imperative code，也是一种微架构。相对大的、达到 subsystem 级别的架构改变，应该什么时候发生，怎样才算好？这种任务首先在人类世界里就不多，非常稀疏，模型就没办法通过大量反馈信号或样本学到。

人类是非常好的 few-shot learner。大家都希望模型也有这种能力，这可能是下一个真正的研究热点：能不能用很少的样本泛化？就像我在 San Diego 看到航母，想到一件完全不相关的事，展开很长的思维链，刷新认知。

有没有一种模型，看到一个或几个案例，就开始重构自己的权重？不是只像 GRPO 那样，原来做一件事这样做，后来发现那道数学题用三角函数、列方程还是数形结合更好，于是预测 next token，决定下一句话怎么说更好；而是能根据一个案例重构整个模型，有种“三观尽毁”的感觉，真正学到一两个案例表达的东西。

比如，软件为什么能在那个时刻想到要做这件事，而且做对了？Linux 为什么那个时候这样做，最终成功？又为什么在 4.0——大概 3.3、3.4 左右——要重构 USB subsystem？为什么大家都觉得整个子系统维护不下去了？刚开始觉得不重要，只有几种设备，后来不行了，必须全重构。这些都是架构变化。

所以，现在需要足够好的 taste-bench。今天讲的任何演化历史，数学、造船、造航母、软件系统，大部分由小事组成，小部分由大事组成。小事已经解决，那能不能把评价从 Yes/No、打一个分数，变成多维度相对比较？

Taste-bench 与 SWE-bench 不一样。SWE-bench 就是测试用例，当然模型不能看到。虽然现代模型如果要刷分，会偷偷、间接地泄漏一些信息到训练好的模型，让它做任务时表现更好，又看不出来。不是直接泄漏测试用例，而是泄漏方法，比如看到 SWE-bench 型任务就疯狂地自己多写测试，这种倾向就能把分数调高一些。

但一件小事就是要么做完，要么没做完；重构要么对，要么错，就能以此为奖励。到了大事，强化学习的反馈已经很稀疏。而且回头看，Linux 当时做出那样的设计，未必就是最好的，后面还有更多经验。

重构时可能有多个架构选择：要不要换成 Event Sourcing，干脆把底层架构也换掉？要不要在数据库里加缓存？还是换其他方法，或者通过 scale 解决性能？每个选择都不是严格谁比谁好。最终当然可以像高考试卷，几张卷子各有一个总分，再加起来。但这里很微妙，不同科目，甚至不同题目，代表不同能力。能力画像是一个 vector，有没有一种 human vector，能根据 AI trajectory 得到真实画像？总分最高，不代表最适合这个项目。

尤其真实项目需要 trade-off，有些东西不可调和。比如架构大改，改成 Event Sourcing，重构代价和风险就都增加。想降低风险，架构和代码改动应该平和一点，但工期就拉长，这次重构可能到不了目标。面临十几个目标的权衡，就没有绝对的好坏。这也是为什么现在 AI 还做不好这件事。

所以我觉得，只要有一个足够好的 taste-bench。像解数学问题，可能已经不是小事了，它已经涌现出了我们无法理解的能力。也许有一天，出现下一个 benchmark 时，我们就可以见证“人类的末日”。我觉得挺有意思。这是软件的时间维度。

上节课说，DeepSeek 还是太慷慨了。给大家看过，2026 年 6 月 10 日的第一个提交，它向我们展示了整个航母构建的过程。你们马上就可以好奇，比如今天这样问：“今天老师用造航母的比喻，讲了软件系统是如何从一开始演化的。”我可以给它更多信息，现在还没有 summary，所以还得打几个字。你们可以直接把我 wiki 上的 lecture notes 贴进去，说老师的观点是什么。

简化的核心观点是：航母很复杂，但从人类历史上看，从帆船到汽船，再到第一艘航母，每一个演化决策都是非常连贯的。大部分是 minor 的小改动，有些涉及比较重大的设计决策变更。照这个思路，去看重大的设计变更和机制引入。甚至可以把它当作模型的考题，这就是某种意义上的 benchmark。长期和 Agent 交互，就知道它应该是什么样的。

它应该要思考比较长的时间，不过没关系，我也给大家准备了一些材料。我拿到 DeepSeek Harness 以后，干的第一件事就是整理提交。这里有最早的 1000 个提交。初始化就相当于真正决定造航母，有一个 initial state。刚开始做 minimum viable product，也就是 MVP，有微内核、需求和架构的场景。

你看，第四个提交以源码形式 vendor in Cordis 框架包。很有意思，DeepSeek Harness 初始化之前，Cordis 已经存在好几年了。Cordis 其实是个人项目，开发者想管理一些 QQ Bot 插件，发现每次加载、卸载都很麻烦，干脆做一个架构。它也经历过这个过程：一开始自己管理插件，没有什么章法；突然有一天，发现了一种方法，这个发现就很重要。原始的几个架构设计 commit 成了很重要的东西，最终形成 Cordis。

DeepSeek Harness 在第四个提交里 merge 了 Cordis。它的原则是 everything is a plugin，把 plugin 放到 Cordis 上，再开始大量实现：先实现 LLM 的 inference，再做 Agent Loop，一点一点往前走。每一步都是小的。如果愿意追溯整个发展历史，在 AI 的帮助下，基本上任何东西你都应该能学会。

这么快？它还真的给我打了一个航母的比喻。看一下：2026 年 6 月 10 日到 20 日这十天，把可回放的会话做成唯一的 source，event sourcing、Cordis，Loop 与适配器分离。它用了航母比方，这是我不想要的。“把一个能跑的循环，变成一个在真实机器上安全地跑的循环；不是新增多少工具，而是把进程、文件、终端、云服务器做成抽象”，再增加 guardrails，包括超时、取消、溢出。

然后有一次重要的改变，从 7 月 19 日到 8 月 6 日，从终端走向浏览器。这是非常重要的决定，一开始可能没有想到。虽然 everything is a plugin 肯定是对的，但当时没想到，用浏览器框架加 DOM tree，会让界面变得非常容易扩展。这个比方还是有点对的，就像飞行甲板：船很通用，可以载货、载人；放上外部甲板以后，变成航母，就可以在上面试验各种飞机。

不过这个总结肯定还有问题。如果真的一个提交一个提交去看，它还是漏了很多有趣的东西。提交历史里有非常多的宝藏。这里也是 AI 总结的，我让它总结演化过程中好的工程实践。

第一个是“设计有由来”，从 RFC 到 ADR、Agent Notes。你们知道什么是 RFC 吗？网络里经常有，比如 Internet Protocol 的总架构、IP 包等。RFC 是 Request for Comments，实际上类似于草稿。要做一个重大的决定，比如是不是要扔掉 TUI，event bus 应该怎样设计，这是很重要的设计。任何人做重大架构决策都可能错，所以先放一个 RFC 上去。

项目内部也可以有 Request for Comments，内部几个小团队开始讨论。我们自己的项目也有，会放在飞书共享文档里，大家先 comment，需要开会就坐在一起讨论。甚至可以做 MVP。现在比以前好，以前开发成本很高，现在一有想法，就能另开一个分支，直接 vibe 一个版本，看看效果，再把所有东西砍掉，回头慢慢来。讨论完，最后形成 ADR，也就是 Architecture Decision Record。

举一个从 RFC 到 ADR 的重要例子，看看有什么有意思的。我完全没有准备。它在读，比我想象的慢一些。它有一个问题：“系统提示词 system prompt 存在 request header 里，其他消息存在 Session 的事件里。”我知道了，这是架构问题。设计时一开始可能觉得就这么做，做完以后发现最好用统一的抽象处理。

它遇到一个需求：支持在对话中途替换 prompt 的模型，需要往历史里追加一条 system role 消息。之前放在 header 里的架构就没办法解决，所以需要重构。这看起来相对小一点，比起在航母上加一层飞行甲板，肯定小一个量级，但对于管理模型上下文这个 subsystem，也是非常重要的设计决策。

这时不改代码，大家先讨论应该怎样做。后面到 9 月 5 日，我猜可能已经在内测了，提升为 ADR，再做实现，进入 implemented 阶段。它有一个状态机。对于不确定、需要长程运行的任务，有 Agent Loop 的状态，这个状态也放在整个 Git repository 里。设计有由来，然后是“协作有边界”。

现在一共有多少提交？以前做这件事要写多少脚本。我们还自作聪明地用人脑计算，想应该 grep 什么，再 word count，发现这么多生命都浪费了。当然，某种程度上，这也是防止脑子生锈的练习。我一直说，打开 UNIX Shell 时，你就是程序员；一直练习编程，确实得到了一些 practice。你看，有两万两千个小提交。

它有自己的协作模型。比如我们现在团队小，用 linear history，没有 merge，带来的好处是每一个都是单独的提交。但如果以后有 external developer，就会很麻烦，因为 main 每次动了，所有分支都要 rebase，再触发所有 CI 流程，会有一些小麻烦。

还有验收的层次：逐文件百分之百覆盖率，真实产品与发布产物的验证等。提交历史里有非常多的宝藏，就不一一讲了。

但是所有这些由人类保证的东西，都无法阻止 AI 生成 AI Slop，谁用谁知道。你不说清楚时，有两种情况：如果用了 `grill-me` 那种技能，它就疯狂问你，一遍一遍问到你烦；如果不说，Agent 还是会猜，想着完成任务，去做很多事，甚至做很多不必要的测试验证。事情本来是实验性的，它缺少你的上下文，做了一堆东西，让维护和修改变得很复杂。

所以最终 DeepSeek Harness 还是由人驾驭的。人显然不可能在短时间内做成这么大的东西，有点极速造航母的感觉。为了防止 AI 毁掉整个项目，上次课讲过国际化、i18n 的例子：README 有中文、英文，两个文档严格保持一致，靠一个我觉得很脏的 YAML 来处理。至少阻止了文档不一致，但也付出代价：repo 膨胀，多了一大堆意义不明的 YAML 文件。

当然可以在 IDE 里配置不显示这些文件，眼不见为净，但它们实际上存在。这也是我前面说的，软件项目不应该用目录来存储。项目里有很多复杂的东西，它们之间有关联，应该把关联存下来。现在用 YAML 存这些关联，用文件可能只是一个 workaround。

DeepSeek Harness 做了非常大的工作，去生产与人类对齐的好代码。办法是什么？没有好办法，找到所有不好的特征，一个个强行排除。没法真正阻止 AI 生成 Slop，就想到它会生成什么 Slop，写一个验证器，在 commit、push 到 remote 以后，或者每次运行时，检查 AI 有没有犯错。有错误，就可以阻止这次提交等。

很有意思，我让它总结 DeepSeek Harness 的 gatekeeping，怎样阻止不合适的代码逃进 repo，它就激活了 `dsh-prose-standard` skill。看一下，这是文字编写规范，有点 unslop 的感觉，要删掉推理过程、重复和修饰。

用 AI 写文档，会发现它把思维链里的东西都写进去：自己想这个东西怎样设计、怎样验收、不要什么，全写进文档。这是非常糟糕的行为。为什么？它写“我做了 A、做了 B，又不是 C”，这些 A、B、C 实际上就和某个实现，比如 `实现.ts` 关联起来。实现改掉时，文档也必须同步修改，引入了同步修改的代价。

AI 编程迭代几轮，可能 A、B 的代码确实没有了，但“不要 C”却错误地留下来。很多不该留下的东西，在软件演化中留在了 repo 里。所以它有这样的规范，甚至还有一个判定基准。

我们来看 DeepSeek Harness 里的 checkers，一共有七类，包括代码与类型质量、架构与依赖约束、行为正确性、持久化和兼容性、文档、构建交付，以及评审。

首先是所有项目都应该使用、虽然你们可能不用的 Lint 和类型检查机制，可以发现很多低级错误。模型能力强，不代表不会犯低级错误，尤其在比较大的代码库里。比如改接口，所有调用方都必须一起改，编译器本身可以找到这种问题；还要检查所有东西都能编译。

我相信你们自己开发项目，不会做这么严格的检查。可能自己编译过，发现有个地方要改，改一下就 push 了。但真实项目为了防止 Agent 干这种事，还是会做各种检查：不同用途的 ID 不能因为都是字符串就混用；让同一份代码遵守同一套 Lint 规则。可以介绍一下项目对 Lint 的使用，在自动检查中会检查什么。

你们学第一门程序设计课时，老师有没有教用 Lint 工具？我觉得不教，显然有很大的问题，就会让你们写出“A 等于空格一”这样的代码，过不了 Lint。

类型安全和异步正确性，可以检查丢失的 Promise、异步不回收、危险断言，以及 no-deprecated。自己的 hobby project 可以用不安全特性；但严格项目的某些包不允许引入 unsafe，比如 Rust 就可以加一条 rule，禁止使用 unsafe。第一次实现或 Agent 做实验性实现时可能用了，但它永远过不了 Lint 检查，推不到远端，必须再改，直到做好。

`no-unused-vars` 是非常有用的 Lint 规则，对人有用，对机器现在也还好。变量定义了不用，很可能是 typo。你们都写过 `for` 循环里 i、j 混用的代码，比如定义 `int i, j`，循环里初始化、判断和递增时用错了变量，有一个 uninitialized，编译器和 Lint 都会报错。比如写了 `if (j)`，这些 i、j 的错误，Lint 可以帮你找到。还有 `prefer-const`、`no-var`、`no-unused-expressions` 和作用域检查。

你看，还有很多严格要求：检查导出文档，每一个非第三方库的导出必须有 JSDoc；禁止硬编码 UI 文案；还有 runtime closure、domain graph、Cordis config 的验证等，都是和项目相关的。

整个流程中，pre-commit 会做一系列检查，包括刚才说的 i18n 配对，中文、英文文档必须一致。如果不一致，commit hash 对不上，pre-commit 直接拒绝。Pre-push 做 type check，CI 做更复杂的检查，还有其他很多规则。

这些检查防止 Agent 不小心破坏架构。今天的 Agent 也可能这样：说要实现一个功能，功能实现了，却不遵循项目架构约定，莫名其妙完整地另写了一份，直接在现有代码里添一行函数调用，第二天就回来了，破坏架构。可能因为提示词里没说“请严格遵循我的架构，所有东西都要这样用”。这句话对人类显然没意义，因为做了干净的架构，就默认所有人都遵守。

所以要么把这句话写进去。写进去可能会污染上下文——也不能这么说，可能确实有用，让指令遵循更好，但会让文档对人类更难读。总要做这种取舍。也可以做控制流检查，要求所有控制流都由插件发起；如果 Agent 不小心硬编码一个直接函数调用，就能拒绝。

基本上是靠开发者的经验和直觉，一点点把每一个细小之处写好。比如浏览器代码不能无意依赖 host 实现；浏览器应用的请求要相对于当前文档解析；网络调用不能悄悄绕过用户代理；vendor 更新应该怎样处理。测试后面会专门讲，它也做了一系列测试的 gatekeeping 文档。

这是 DeepSeek Harness 里我觉得做得很好的地方，给大家一些启发。我没办法在课上一个个讲过来，因为这些和具体项目、语言，以及项目功能绑定，讲起来会很枯燥，也不是每个同学都对 DeepSeek Harness 有兴趣。我展现的更多是一种方式：如果遇到一个感兴趣的项目，比如你做 bioinformatics，真的要靠它拿 PhD，就用我的方式打开它，总结文档的质量保障怎么做，再总结提交，画成 commit 时间轴，也许能帮助你更好理解想学的东西。

最后，虽然我们和 DeepSeek Harness 都尽了最大努力，仍然有很多问题没有解决。刚才说，小事已经解决，大事还需要 taste-bench。今天 AI 能力很强，但分不清轻重，有时过度自信，觉得事情搞定了，其实没达到我的预期；有时又过度小心，事情不用那么小心，却做了很多测试。

如果纠正它，就糟糕了。你但凡说“不要这样”，它就把“不要这样”写进文档，再在代码、注释里各写一份。不断膨胀的上下文不断抢夺注意力。“不要放蒜”的例子：每一个出现在上下文里的词，在模型眼里都很重要，但世界上还有无穷多的词，理论上也应该出现，只是没写进去。它们的权重和“不要放蒜”一样，比如不要放韭菜、不要放蘑菇，你就给我炒一个番茄炒蛋。但模型不理解重要性的区别，或者说有自己的想法。我们每个人都有自己的偏见，人类社会就是靠这些偏见向前进的。

这里有个启发。我以前做 program synthesis，也就是程序合成，和许愿编程有点像：给一个 spec，希望得到正确实现。比如有函数，知道 `f(1)=2`、`f(2)=3`、`f(3)=4`，就会生成 `lambda x: x + 1`。这种程序合成技术，大概在 2011 年引起过一阵小热潮。

Excel 有一个智能填充功能，以前我上研究生课都会拿它当案例。比如从邮件、报表收集到很多不规则电话号码，025 是区号，但有人写 `02512345678`，有人写 `025-12345678`。怎样让不会编程的人自动把区号、电话号码整理出来？这就是程序合成，叫 programming by examples：给一些例子，能不能生成一个程序？对于字符串，可以生成基于正则表达式的程序。还有 programming by demonstration，做一遍，能不能给出程序？今天这两个问题已经完全被大语言模型解决。

那时有一个非常热门、到今天还有人研究的技术，叫 counterexample-guided，跟今天和大语言模型交互很像。我给一个 spec，可能是刚才那样，但还有别的，比如 `f(4)=6`，只是还没告诉模型。模型先生成 `x + 1`，我就告诉它，对不起，`f(4)=6`。它再生成，可能就加一个 `if`，单独处理这个例子，其他时候返回 `x + 1`。这样就陷入一个问题：取什么样的 counterexample，才能让它生成正确程序？这很难。

所以“番茄炒蛋不放蒜”是一个很糟糕的提示词。说不放蒜，就意味着还有同样重要的不放香菜、不放韭菜、不放辣椒。刚才看 DeepSeek Harness 有处理文档的 skill，大家可能也用过 unslop。如果写英文论文，这个 skill 非常有用。我不知道是不是 GPT 的口癖，到现在可能都有 ensuring、highlighting。以前写文章不用这些词，像 framing 有时也不太用，虽然严格说也没错。比如 ensure 就太重了，我们要谦虚一点，几乎不会 ensure something。还有 showcase，以及一些 AI vocabulary：additionally、interplay、intricate，还有“not just X but Y”。

这是典型的 counterexample-guided：观察到 AI 做 A、B、C、D、E，就要求它 not A、not B、not C、not D，但 high-level guideline 到底是什么，其实还不知道。

我做过一件有意思的事。我们讨论有没有一个 prompt 或 skill，能更好阻止 AI 生成 Slop。我的问题是，我有所有回复过的 email，但到目前为止，AI 自动帮我回邮件仍然失败。比较简短的可能还行，长的就不行。即便把我回过的所有邮件都放进上下文，说“照我的风格来”，它也做不对。模型没有提炼这种东西的能力。

所以我做了一个 recursive self-improvement loop。我希望有一个像 unslop 或 write-email 这样的 skill，但不知道它是什么。现在有一个可检验过程：写出来的东西像不像我。我有很多 email，或者人写的文稿，可以知道回复有多长，也有词频、句子长度、标点使用等统计信息。

我给它的 prompt 是：你可以 evaluate，用 unslop 或 write-email 技能去回复我过去回复过的所有邮件，但不要看我的实际回复。然后算出每个 metric，到底离我更近，还是更远。如果更近，就留下这次结果；如果更远，就要求提炼一条 general guideline。不是简单写“不要用‘不是……而是……’句型”，而是想一条覆盖广的原则。

比如我确实不要蒜，但你能不能看透，“不要蒜”的本质是不要无关的东西，还是别的什么？能不能把这样的 guideline、principle 加回 skill，让品位提升？今天还做不到，但我是乐观的。今天讲了人类的一个 isomorphic 的过程，不管做软件还是做工程，都有这样的流程。有没有可能，有一个 self-improvement loop，最终在把小事干好的同时，也把大事干好？今天下课。
